24 · 虚拟化与资源限制 ​

概念简介 ​

多台服务挤在一台物理机上，怎么保证它们互不干扰、不互相拖垮？两个层面的机制：虚拟化（虚拟机 KVM/VMware 或容器，隔离运行环境）和资源限制（cgroup/ulimit，限制每个隔离单元能占用的 CPU、内存、文件数）。前者解决"跑得开"，后者解决"不抢资源、不失控"。

前端对资源限制其实有直觉——浏览器给每个标签页独立进程，一个标签页崩了不会拖垮整个浏览器；Web Worker 有配额限制。本篇讲 KVM 虚拟机的本质、cgroup 的 CPU/内存限制、ulimit 文件描述符、以及命名空间隔离，重点是理解「资源配额」的配置方法与常见坑。

核心内容 ​

1. 虚拟机 vs 容器：两条隔离路线 ​

  • 虚拟机：用 KVM/VMware 虚拟出完整的硬件（CPU/内存/网卡），里面跑完整的操作系统。隔离最强，代价是每台几 GB 内存、分钟级启动。
  • 容器：共享宿主机内核，通过命名空间隔离进程/文件/网络视图，通过 cgroup 限制资源。秒级启动，但隔离弱、内核共享。

两者不是竞争关系而是互补：虚拟机隔离"不同的客户"，容器隔离"同一客户的不同服务"。云厂商的"云主机"本质是虚拟机，而 k8s 里的 pod 是容器。

2. cgroup：CPU 与内存资源限制 ​

cgroup 是 Linux 内核的资源配额机制：把进程分组，给每组设定 CPU/内存/IO 上限。Ubuntu 22.04 使用 cgroup v2（挂载在 /sys/fs/cgroup）。

生产中最常见的用法是通过 systemd 单元文件限制服务（第 11 篇已学 systemd）：

ini
# /etc/systemd/system/myapp.service
[Service]
ExecStart=/opt/myapp/bin/server
# CPU 限制:最多使用 2 个核的算力(200%)
CPUQuota=200%
# 内存硬上限:超过 512MB 直接 OOM(内存放不下时会被内核杀掉)
MemoryMax=512M
# 文件描述符上限(见第 3 节)
LimitNOFILE=65535
# 进程数上限:防止 fork 炸弹
TasksMax=128
bash
sudo systemctl daemon-reload
sudo systemctl start myapp
# 查看实际限制是否生效
systemctl show myapp -p CPUQuota -p MemoryMax -p TasksMax
# 运行时查看该服务的 cgroup 实时用量
cat /sys/fs/cgroup/system.slice/myapp.service/memory.current

cgroup v2 也可以手工建控制组（了解机制，生产上用 systemd 即可）：

bash
# 手工创建控制组并限制 512MB,把当前 shell 进程放进去
sudo mkdir /sys/fs/cgroup/myapp
echo 536870912 | sudo tee /sys/fs/cgroup/myapp/memory.max   # 字节数
echo $$ | sudo tee /sys/fs/cgroup/myapp/cgroup.procs        # 放入当前进程

3. ulimit：文件描述符与其他进程限制 ​

一个进程能打开多少文件（文件描述符 fd）默认只有 1024——高并发的 Web 服务（Nginx/Node）瞬间就会 too many open files 崩溃。ulimit 是 shell 级限制，systemd 托管服务要配 LimitNOFILE：

bash
# 临时提升当前 shell
ulimit -n 65535
ulimit -n          # 查看当前值

# 全局持久化:所有用户默认 65535
echo '* soft nofile 65535' | sudo tee /etc/security/limits.d/99-nofile.conf
echo '* hard nofile 1048576' | sudo tee -a /etc/security/limits.d/99-nofile.conf
# 注意:ssh 登录的会话才读 limits.d;systemd 服务读的是服务文件里的 LimitNOFILE

其他常用限制：ulimit -u（最大用户进程数）、ulimit -v（虚拟内存上限）。

4. 命名空间：进程眼中的"独立世界" ​

容器"看起来像独立机器"的原理是命名空间（namespace）——Linux 给一组进程提供独立的资源视图：PID 命名空间里进程以为自己是 1 号；Mount 命名空间里 / 是另一棵文件树；Network 命名空间里有自己的 IP 和端口空间。这也是容器里 systemctl 无效、ifconfig 看到的不是宿主机网卡的原因。

bash
# 快速体验:在干净的命名空间里跑一个进程
# 每个字段是"ns"类型,$$\ 表示"所有可隔离维度都开新的"
sudo unshare --pid --fork --mount-proc bash
ps aux    # 现在只看到自己,没有宿主机的进程
exit

5. 实战组合：Docker 容器的资源限制与诊断 ​

容器（23 篇）本质就是「命名空间 + cgroup」，所以给容器限资源就是直接操作 cgroup——这是最容易上手、也最容易踩坑的组合场景：

bash
# Docker 对容器的资源限制,本质是给容器的 cgroup 配额
docker run -d --name limited \
    --memory=256m \        # 容器内存上限 256MB(超限即被 OOM 杀)
    --memory-swap=256m \   # 禁止容器使用 swap,避免性能雪崩
    --cpus=1.0 \           # 限制 1 个核的算力
    --pids-limit=64 \      # 限制进程数(防 fork 炸弹)
    --ulimit nofile=65535:65535 \
    nginx:alpine

# 实时看容器资源占用(docker stats 展示的正是 cgroup 统计)
docker stats --no-stream
# 深入容器自己的 cgroup(容器内看到的限制文件)
docker exec limited cat /sys/fs/cgroup/memory.max

# 诊断当前进程受限情况的三件套命令
ulimit -a                 # shell 级限制一览
cat /proc/self/limits     # 当前进程实际生效的限制(最权威)
systemctl show myapp -p MemoryMax -p CPUQuota   # systemd 服务侧

要点：资源限制三件套——systemd 服务的 CPUQuota/MemoryMax/LimitNOFILE、/etc/security/limits.d/ 登录用户限制、cgroup 内 OOM 时内核杀进程的行为预期；诊断一律以 /proc/<pid>/limits 和 cgroup 文件为准。

常见陷阱 ​

  • cgroup v1/v2 路径不同：老教程里的 /sys/fs/cgroup/memory/memory.limit_in_bytes 在 Ubuntu 22.04（cgroup v2）上不存在，v2 是 /sys/fs/cgroup/**/memory.max。先 mount | grep cgroup 确认版本。
  • ulimit 配了不生效：在 shell 里 ulimit -n 65535 只对当前 shell 生效；SSH 登录会话读 /etc/security/limits.d/；systemd 服务读服务文件里的 LimitNOFILE——三处三套逻辑，配错位置等于没配。
  • MemoryMax 配太低应用直接被 OOM 杀掉：cgroup 内存超限时内核会杀进程（dmesg 里能看到 OOM 记录）。排查"服务莫名消失"先看 journalctl -u myapp 和 dmesg | grep -i oom。
  • CPUQuota 与真实核数：CPUQuota=100% 是 1 个核，不是"单核的 100%"里可以随便调——配额内 CPU 是共享的，配额外会被节流（throttle），性能表现是"锯齿状"。
  • 容器里看资源限制：容器进程的 cgroup 限制来自容器运行时，ulimit -n 默认被 Docker 设成很大但受宿主机限制约束，容器内自己 ulimit 改不动上限。
  • 误解 swap 限制：cgroup v2 里 memory.swap.max 是独立项，只配 memory.max 不配 swap 时，swap 可能被用满导致性能雪崩。

练习建议 ​

  1. 基础：写一个多进程服务单元文件（CPUQuota=100% + MemoryMax=256M + LimitNOFILE=65535），启动后用 systemctl show 验证生效。
  2. 进阶：用 cgroup v2 手工建控制组把 yes > /dev/null 放进去，观察 CPU 被限制在配额内；把内存限制设到 10MB 运行一个吃内存的程序，观察 OOM 被杀并 dmesg 取证。
  3. 综合：开一台 KVM 虚拟机（或用 VirtualBox）跑 Ubuntu，对比它和 Docker 容器的资源开销与启动速度；再给容器加上 --memory=256m --cpus=1 限制，实测内存超限被杀的行为差异。

用 /practice linux 虚拟化与资源限制 生成更多针对性练习。
