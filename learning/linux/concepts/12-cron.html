12 · 定时任务 ​

前置：11 服务管理 systemd · 预计：1.5~2 小时

概念简介 ​

前端写定时任务用 setTimeout / setInterval——那是「页面开着才生效」的定时器，页面一关就没了。服务器上需要的是「机器永远开着、到点就执行」的定时任务：凌晨备份数据库、每天清日志、每小时拉一次数据。

Linux 的定时任务体系有三件套：cron（周期任务，最常用）、at（一次性任务）、systemd timer（systemd 定时器，cron 的现代替代）。本篇以 cron 为主线，它的语法通用性最强——CI 流水线、GitLab Runner 的 schedule 用的都是同一套「分时日月周」表达式。

核心内容 ​

1. cron 语法：分 时 日 月 周 ​

cron 表达式共 5 个字段，比 GitHub Actions 的 5 字段更早出现，两者格式几乎一致：

分  时  日  月  周   要执行的命令
*   *   *   *   *   command
bash
# 字段取值范围：
#   分: 0-59    时: 0-23    日: 1-31    月: 1-12    周: 0-7（0 和 7 都代表周日）

# 常用写法：
* * * * *          # 每分钟
*/5 * * * *        # 每 5 分钟
0 * * * *          # 每小时整点
0 2 * * *          # 每天凌晨 2 点
0 2 * * 1          # 每周一凌晨 2 点
0 2 1 * *          # 每月 1 号凌晨 2 点
30 4 1,15 * *      # 每月 1 号和 15 号的 4:30
0 9-18 * * *       # 每天 9 点到 18 点每小时

注意周与日的 OR 关系：0 2 1 * 1 表示「每月 1 号 或 周一」都执行，不是「既是 1 号又是周一」。这是 cron 与其它调度器最大的语法差异。

2. crontab：每个用户一份任务表 ​

crontab 命令管理当前用户的定时任务，与前端「每用户一份 localStorage」类似——root 的任务在 root 表，普通用户在各自的表。

bash
crontab -e    # 编辑当前用户的 crontab（第一次会提示选编辑器）
crontab -l    # 列出当前用户的全部任务
crontab -r    # 删除全部任务（小心！没有确认）

# 写入示例（用 crontab -e 打开后添加，结尾必须是换行）：
# 每天凌晨 2 点备份数据库，日志追加到文件
0 2 * * * /home/deploy/backup.sh >> /var/log/backup.log 2>&1

3. 写一个实战定时备份脚本 ​

cron 只负责「到点触发」，具体逻辑写在脚本里。cron 环境有三个特点：PATH 极简（只有 /usr/bin:/bin）、无交互终端、不加载 ~/.bashrc——脚本里必须自己写绝对路径和必要的变量。

bash
#!/bin/bash
# /home/deploy/backup.sh —— 数据库每日备份脚本
set -euo pipefail                 # 任何一步失败立即退出，别静默吞错

BACKUP_DIR="/var/backups/mysql"   # 备份目录
STAMP=$(date +%Y%m%d_%H%M%S)      # 时间戳，保证文件名唯一
mkdir -p "$BACKUP_DIR"

# mysqldump 必须写绝对路径，cron 的 PATH 里可能没有 /usr/local/bin
/usr/bin/mysqldump -u backup_user mydb > "$BACKUP_DIR/mydb_$STAMP.sql"

# 只保留最近 7 天的备份，防止磁盘被占满
find "$BACKUP_DIR" -name "mydb_*.sql" -mtime +7 -delete

echo "备份完成: $BACKUP_DIR/mydb_$STAMP.sql"
bash
chmod +x /home/deploy/backup.sh   # 给执行权限
crontab -e                        # 添加: 0 2 * * * /home/deploy/backup.sh >> /var/log/backup.log 2>&1

>> log 2>&1 这条必须养成习惯：把输出和错误都重定向到文件，否则 cron 会把输出作为邮件发到本机邮箱（root 邮箱里堆几百封信），且错误你根本看不到。

4. 系统级定时任务 ​

用户 crontab 之外还有系统级目录，按「每天/每周/每月」粒度放脚本，放在 /etc/cron.daily/、/etc/cron.hourly/ 等目录里的可执行脚本会被自动执行（由 cron 或 anacron 驱动）：

bash
ls /etc/cron.daily/        # 系统自带的每日任务（logrotate、man-db 等）
sudo nano /etc/cron.d/mycron   # 或自定义文件：格式带用户字段
# 文件内容（第 6 个字段是指定执行用户）：
# 0 3 * * * deploy /home/deploy/backup.sh

/etc/crontab 与 /etc/cron.d/ 里的任务比用户 crontab 多一个用户字段，别照抄用户格式。

5. at：一次性定时任务 ​

「半小时后执行一次、执行完就结束」——用 at，不占 crontab 条目。

bash
sudo apt install at            # 如果没装
sudo systemctl enable --now atd   # 启动 at 守护进程（必须！否则任务不执行）

echo "/home/deploy/cleanup.sh" | at now + 30 minutes   # 30 分钟后执行
echo "systemctl restart nginx"  | at 23:00             # 今晚 23 点执行
atq        # 查看等待中的任务（队列）
atrm 3     # 删除任务编号为 3 的任务

6. 排错：定时任务没执行怎么办 ​

bash
# 1. 看 cron 的调度记录（Ubuntu 记录在 syslog）
sudo grep CRON /var/log/syslog | tail -20
# 输出示例: CRON[1234]: (deploy) CMD (/home/deploy/backup.sh)  —— 说明到点触发了

# 2. 没触发 → 检查时间与时区
date; timedatectl            # 服务器时区可能和你习惯的差 8 小时

# 3. 触发了但失败 → 看脚本日志
cat /var/log/backup.log

# 4. 手动跑一遍脚本，排除环境差异
bash /home/deploy/backup.sh

要点：cron 环境 PATH 极简、无交互终端；输出必须重定向；时区必须确认；排错顺序是「先确认触发（syslog）→ 再看脚本（日志）」。

常见陷阱 ​

  • 命令用相对路径或依赖 ~/.bashrc 的环境变量：cron 的 PATH 只有 /usr/bin:/bin，/usr/local/bin 下的工具直接找不到，脚本里必须写绝对路径。
  • 忘记 >> log 2>&1：cron 会把每次输出发邮件到本机 root 邮箱，邮箱被塞满，且错误无处可见（日志缺失让排错无从下手）。
  • 周与日字段的 OR 关系：以为「每月 1 号且周一」写 0 2 1 * 1，实际是「每月 1 号或每周一」都会执行。
  • 6 个字段写成 cron 格式：把 分钟 小时 日 月 周 用户 命令（系统 crontab 格式）抄进用户 crontab，第 6 个字段会被当成命令执行而报错。
  • at 任务不执行：atd 守护进程没启动（systemctl status atd 检查），任务挂队列里永远不跑。
  • 备份脚本把磁盘写满：只备份不清理，find ... -mtime +7 -delete 必须配套，否则日志/备份把 / 占满（见 13 篇日志管理）。

练习建议 ​

  1. 基础：用 crontab -e 添加「每分钟输出当前时间到 /tmp/cron-test.log」（date >> /tmp/cron-test.log），观察 3 分钟，用 grep CRON /var/log/syslog 确认触发，然后删除。
  2. 进阶：写一个备份脚本（复制某个目录 + 保留最近 3 份），配置每天凌晨执行，手动制造一次脚本报错（如目标目录不存在），走完「syslog 确认触发 → 看日志 → 修复」的排错流程。
  3. 综合：用 at 安排「2 小时后自动停止一个临时服务」，对比 cron 与 at 的适用场景；再用 systemd timer（systemctl 系）实现同一个每日本备任务，比较两种方案的优劣。

用 /practice linux 定时任务 生成更多针对性练习。
