02 · 模块系统 ​

前置：01 Node 运行时与项目结构 · 预计：1.5~2 小时

概念简介 ​

模块系统解决「代码怎么拆分、怎么复用、依赖怎么装」。前端工程师对 ESM(import/export)很熟,但 Node 有两套模块系统:CommonJS(老牌正统)和 ESM(现代标准),受 package.json 的 type 字段支配。两套并存是 Node 独有的复杂度,也是工程中反复踩坑的地方。

核心思维转变:require 是同步的、带缓存的、运行时加载;import 是异步的、静态分析的、支持顶层 await。同是 JS,两套机制的行为差异直接影响你写代码的方式——比如循环依赖,两套系统的表现就不同。

本篇讲清:CommonJS vs ESM 的写法与行为差异、type 字段如何决定解析规则、node_modules 查找算法、npm/pnpm 包管理,以及循环依赖陷阱。

核心内容 ​

1. CommonJS:require 与 module.exports ​

js
// math.js —— CommonJS 模块(默认 .js 文件就是 CJS)
// 导出:module.exports 决定模块对外暴露什么
function add(a, b) {
  return a + b;
}

module.exports = { add };        // 整体导出
// 等价写法:exports.add = add;   // 逐个挂属性
js
// main.js
const math = require('./math');   // 相对路径必须以 ./ 开头,否则去找 node_modules

console.log(math.add(1, 2));      // 3

// require 有缓存:同一模块多次 require 拿到的是同一个实例
console.log(require('./math') === math);   // true

要点:exports 只是 module.exports 的引用,exports = {...} 会断开引用导致导出为空;导出统一用 module.exports。

2. ESM:import / export ​

js
// math.mjs —— ESM 模块(.mjs 后缀强制按 ESM 解析)
export function add(a, b) {
  return a + b;
}

export const PI = 3.14159;

export default class Calculator {}   // 默认导出,引入时自定义名字
js
// main.mjs
import { add, PI } from './math.mjs';
import Calculator from './math.mjs';

console.log(add(1, 2), PI);

3. package.json 的 type 字段:谁说了算 ​

json
// package.json
{
  "type": "module"
  // "type": "commonjs"(默认,不写就是它)
}
  • 不写 type 或 "commonjs":.js 文件按 CommonJS 解析
  • "module":.js 文件按 ESM 解析
  • .mjs 永远是 ESM,.cjs 永远是 CJS,与 type 无关——这是逃生舱口

ESM 里没有 __dirname,需要用 import.meta.url 换算:

js
// main.mjs
import { fileURLToPath } from 'node:url';
import path from 'node:path';

console.log(import.meta.url);                      // file:///Users/.../main.mjs
const dirname = path.dirname(fileURLToPath(import.meta.url));
console.log(dirname);                              // /Users/...(等价 CJS 的 __dirname)

4. 依赖解析:node_modules 查找算法 ​

require('lodash') 不带路径时,Node 从当前文件的目录开始逐级向上查找:

./node_modules/lodash        ← 当前目录
../node_modules/lodash       ← 上一级
../../node_modules/lodash    ← 再上一级……直到文件系统根

找到包后,入口由包内 package.json 的 main 字段(老)或 exports 字段(新,更严格)决定。这就是「一个项目一个 node_modules,嵌套依赖靠层级」的原因。

5. npm / pnpm 包管理 ​

bash
npm init -y                # 生成 package.json
npm install express        # 安装并写入 dependencies
npm install -D vitest      # 开发依赖
npm ci                     # 按 lockfile 精确安装(CI 环境用,别用 install)
npm run start              # 执行 package.json 里的 scripts
  • lockfile(package-lock.json / pnpm-lock.yaml):锁定依赖树的精确版本,保证团队与 CI 安装一致——必须提交 git
  • pnpm:依赖放进全局内容寻址存储,项目里用硬链接,省磁盘且安装快,同时天然规避幽灵依赖

6. 循环依赖陷阱 ​

js
// a.js
const b = require('./b');
console.log('a 加载完成, b.fromB =', b.fromB);

// b.js —— 被 a 引用后又回头引用 a
const a = require('./a');
console.log('b 加载中, a 此刻是:', a);   // {} —— 半成品!
module.exports = { fromB: 'B' };

先执行 a.js:require('./b') 时 b 又 require('./a'),但 a 还没执行完,module.exports 还是空对象——b 拿到半成品。输出顺序:b 加载中, a 此刻是: {} → a 加载完成, b.fromB = B。

规避办法:把共享数据抽到独立模块(谁先加载都是完整版),或把 require 放到函数内部延迟执行。

常见陷阱 ​

  • exports = { ... } 不生效:exports 只是 module.exports 的引用,整体赋值会断开引用,模块导出为空对象
  • 循环依赖拿半成品:拿到 {} 或 undefined,且运行顺序不同表现不同,极其隐蔽
  • ESM 里用 require 报错:require is not defined,ESM 需要 createRequire(import.meta.url) 才能用
  • 忘写 ./:require('math') 会去 node_modules 找而不是当前目录,报 MODULE_NOT_FOUND
  • import 语法在 CJS 报错:Cannot use import statement outside a module——检查 .mjs 后缀或 type: "module"
  • 双包危害(dual package hazard):同一个库被 CJS 与 ESM 各加载一份实例,instanceof 判断失效、状态不共享——库作者要小心,普通项目尽量统一模块体系

练习建议 ​

  1. 基础:建 math.js(module.exports)和 main.js(require),实现加减乘除
  2. 进阶:把同一项目改成 type: "module" 的 ESM 版本,对比 import/export 写法,并找出 ESM 里获取 __dirname 的方法
  3. 综合:故意制造一个三模块循环依赖(a → b → c → a),运行观察输出,画出加载顺序图,再重构消除循环

用 /practice nodejs 模块系统 生成更多针对性练习。
