28 · 微服务与架构 ​

概念简介 ​

微服务是把一个单体应用拆成多个独立部署、独立伸缩、故障隔离的服务。前端工程师对「拆分」不陌生——你拆过巨型组件、拆过 monorepo，思维完全同构：拆得好降低耦合、提升并行效率；拆过头则沟通成本爆炸。微服务的不同在于：组件拆分在编译期生效，服务拆分在运行时生效——模块变网络调用，局部失败变分布式故障，数据一致性从事务变成补偿。所以微服务的第一课是「拆不拆」，而不是「怎么拆」。

本篇覆盖：服务拆分原则、服务间三种通信方式（REST / gRPC / 消息队列）与选型、事件驱动架构（把 EventEmitter 放大到系统级）、K8s 基础对象、分布式事务简介。目标不是让你立刻去拆，而是具备「评审架构时能论证拆分取舍」的能力。

核心内容 ​

1. 服务拆分原则：什么时候才值得拆 ​

text
# ---------- 1. 拆分判断:至少中 2 条才值得拆 ----------
# 1. 独立演进:两个功能发布节奏完全不同(一个周更、一个季度更)
# 2. 独立伸缩:一个模块压测吃满资源,另一个长期闲置
# 3. 故障隔离:一个模块崩溃不该拖垮另一个
# 4. 团队自治:两个团队各负其责,不想互相等待

# 反模式:
#   - 按技术层拆(controller 服务 / service 服务):拆分维度是业务域,不是技术层
#   - 为了用微服务而拆:单体 + 模块化(MVC 分模块)是默认起点
#   - 拆完仍是同步调用链 A->B->C->D:一个慢全慢,等于把单体变成网络版

# 代价清单(拆前必须看见):
#   网络延迟、分布式事务、消息可靠性、部署编排、日志链路聚合
#   —— 运维复杂度是单体的 10 倍,每多一个服务都是负债

2. 服务间通信：REST / gRPC / 消息队列 ​

三种通信方式没有谁绝对更好，选型取决于「调用方、频率、是否要立即返回」：

text
# ---------- 2. 通信选型 ----------
# REST:  人类友好、调试方便、生态成熟;性能一般、无强契约 —— 对外 API
# gRPC:  HTTP/2 二进制、强类型契约(proto)、性能高 —— 服务间高频内部调用
# 队列:  异步、削峰、解耦;没有立即返回 —— 不需要结果的重活/事件
# 选型口诀:对外 REST,对内高频 gRPC,重活异步队列

3. gRPC 落地：契约即接口文档 ​

gRPC 的核心是 .proto 契约文件：定义接口和消息结构，两端共享。服务端实现契约，客户端按契约调用——就像前端和后端共享一份类型定义，只是这份契约是强制的、编译校验的。

protobuf
// ---------- 3. gRPC 契约:user.proto ----------
syntax = "proto3";

package user;

// 定义服务:一组 RPC 方法
service UserService {
  rpc GetUser (GetUserRequest) returns (User);
}

// 请求与响应结构(像 TypeScript interface,但跨语言共享)
message GetUserRequest {
  int32 id = 1;
}
message User {
  int32 id = 1;
  string name = 2;
  string email = 3;
}
javascript
// ---------- 3. gRPC 服务端实现 ----------
// 安装: npm i @grpc/grpc-js @grpc/proto-loader
// server.js —— 直接运行: node server.js
const grpc = require('@grpc/grpc-js');
const protoLoader = require('@grpc/proto-loader');
const path = require('node:path');

// 加载契约文件(契约即文档,服务端按它实现,客户端按它调用)
const packageDefinition = protoLoader.loadSync(path.join(__dirname, 'user.proto'));
const userProto = grpc.loadPackageDefinition(packageDefinition).user;

// 实现契约里声明的 GetUser 方法
function getUser(call, callback) {
  const { id } = call.request;
  const user = { id, name: `用户${id}`, email: `user${id}@example.com` };
  callback(null, user); // 第一个参数:错误;第二个:响应对象
}

// 启动 gRPC 服务(端口独立于 REST,二进制协议)
const server = new grpc.Server();
server.addService(userProto.UserService.service, { getUser });
server.bindAsync('127.0.0.1:50051', grpc.ServerCredentials.createInsecure(), (err) => {
  if (err) throw err;
  server.start();
  console.log('gRPC 服务监听 50051');
});

// 客户端调用(另一个服务里):
// const client = new userProto.UserService('127.0.0.1:50051', grpc.credentials.createInsecure());
// client.GetUser({ id: 1 }, (err, user) => console.log('拿到用户:', user));

4. 事件驱动：从 EventEmitter 放大到系统级 ​

你已经会 EventEmitter——一个进程内的事件广播。微服务的事件驱动是同一思想，只是广播对象从内存换成了消息总线（Redis pub/sub / Kafka）。核心收益：发布方不关心谁订阅，新增消费者不用改发布方一行代码。

javascript
// ---------- 4. 事件驱动:EventEmitter 的进程内演示 ----------
// events.js —— 直接运行: node events.js
const { EventEmitter } = require('node:events');
const orderEvents = new EventEmitter(); // 进程内事件总线

// 订单模块:只负责「状态变化 + 发事件」,不关心谁处理
function createOrder(order) {
  order.status = 'created';
  orderEvents.emit('order.created', order); // 领域事件,解耦后续动作
  return order;
}

// 通知模块:订阅事件,独立处理(失败不影响下单主流程)
orderEvents.on('order.created', (order) => {
  console.log(`[通知] 给用户 ${order.userId} 发送下单成功消息`);
});

// 库存模块:同样订阅,各干各的
orderEvents.on('order.created', (order) => {
  console.log(`[库存] 预扣库存: ${order.items.join(', ')}`);
});

createOrder({ userId: 1, items: ['键盘', '鼠标'] });
// 输出(顺序不定,彼此无依赖):
// [通知] 给用户 1 发送下单成功消息
// [库存] 预扣库存: 键盘, 鼠标

// 放大到系统级:Kafka 的 topic 就是「全局 EventEmitter」
//   下单服务发 order.created topic -> 通知服务/库存服务/积分服务各自订阅
//   新增「积分服务」只需订阅,订单服务零改动
//   与进程内的区别:需要可靠性(持久化/重试),见 24 篇队列与 pub/sub 的取舍

5. K8s 基础：Pod / Service / Deployment ​

K8s（Kubernetes）是微服务的部署操作系统。先只认识三个最基础的对象：Pod 是最小运行单元，Deployment 声明「要几个副本并维持它」，Service 给 Pod 一个稳定的访问入口。

yaml
# ---------- 5. K8s 三个最基础的对象 ----------
# deployment.yaml —— 声明期望状态:「3 个副本」,K8s 负责维持
apiVersion: apps/v1
kind: Deployment
metadata:
  name: task-api
spec:
  replicas: 3                      # 期望 3 个副本,任何时刻少于 3 会自动补
  selector:
    matchLabels: { app: task-api }
  template:
    metadata:
      labels: { app: task-api }    # 标签:Service 靠它找到 Pod
    spec:
      containers:
        - name: task-api
          image: registry.example.com/task-api:1.2.0
          ports: [{ containerPort: 3000 }]
          readinessProbe:          # 就绪探针:没就绪的 Pod 不接流量(优雅发布的关键)
            httpGet: { path: /health, port: 3000 }

# service.yaml —— 集群内固定入口:Pod 挂了重建 IP 会变,Service 名字不变
# apiVersion: v1
# kind: Service
# metadata:
#   name: task-api
# spec:
#   selector: { app: task-api }    # 按标签挑 Pod,自动负载均衡
#   ports: [{ port: 80, targetPort: 3000 }]

6. 分布式事务：没有银弹 ​

跨服务数据一致性是微服务最难的部分，认知比方案重要：单体里「一个事务包三张表」，拆开后变成「三个服务各自提交，第 2 个失败时第 1 个已提交」——强一致在分布式下几乎不可能，追求最终一致。

text
# ---------- 6. 分布式事务方案对比 ----------
# 2PC(两阶段提交): 准备 + 提交,强一致
#   代价: 全程锁资源,协调者单点,任一节点慢全链路慢 —— 现代项目少用
# Saga: 每个服务执行本地事务 + 发补偿事件,失败反向撤销
#   下单 -> 扣库存失败 -> 发「取消订单」事件补偿
#   最终一致,是微服务的主流方案(如 order -> payment -> inventory)
# Outbox: 本地事务里同时写业务表和 outbox 表
#   保证「业务变更」与「发事件」原子性:事件要么随事务成功,要么没有
#   再靠轮询/CDC(如 Debezium)把 outbox 里的可靠投递到消息总线
# 心法: 幂等(重试安全) + 补偿(撤销已做动作)能解决 90% 的一致性需求
#   消息消费者必须幂等:同一消息收到两次,效果与一次相同

要点：微服务是一套「以运维复杂度换独立性的架构」，决策顺序是——先论证该不该拆（拆分原则）→ 再选通信（REST/gRPC/队列）→ 再定一致性方案（Saga/Outbox）→ 最后才是 K8s 部署。顺序反了就会「为拆而拆」。

常见陷阱 ​

  • 一上来就拆微服务：单体的模块化（MVC 分模块）是默认起点；微服务是模块化做到极致后仍不够时的选项。
  • 按技术层拆服务：controller 一个服务、service 一个服务——拆分维度必须是业务域。
  • 拆完全是同步调用链 A→B→C→D：一个环节慢全链慢，还多了网络开销；长链必须异步化。
  • 分布式事务自己造轮子：手写 2PC 是事故发动机；用 Saga/Outbox 的成熟框架，或直接接受最终一致。
  • 事件丢失无补偿：业务成功但「发事件」失败（或反之），状态永远不一致；Outbox 模式解决。
  • gRPC 当对外 API 用：浏览器不能直接用 gRPC，对外接口保持 REST；gRPC 定位是服务间内部通信。

练习建议 ​

  1. 基础：跑通 gRPC 服务端 + 客户端调用，比较它与 REST 在接口契约上的差异（强类型 vs 运行时）。
  2. 进阶：用 EventEmitter 实现下单事件流（通知 + 库存两个订阅方），再换成 Redis pub/sub 验证跨进程广播。
  3. 综合：设计「订单系统拆微服务」方案——写清拆分理由（对照 4 条原则）、通信选型表、订单流程的一致性方案（Saga 补偿流程），并评审它的风险点。
