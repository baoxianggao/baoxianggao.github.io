18 · 数据库访问 ​

概念简介 ​

前端的数据在内存（Redux）和浏览器（localStorage/IndexedDB）里，后端的数据在数据库里——数据库是唯一的「事实源」。前端习惯的「数组 + filter」对应 SQL 的「表 + SELECT WHERE」，「状态管理手动同步」对应后端「ORM 映射 + 事务」。后端数据库最大的心智转变是：数据是共享的、并发的、持久的，每一步操作都要考虑多请求同时访问的安全。

Node 访问数据库有三层递进：SQL（基本功，能读懂与手写）、Knex（查询构建器：SQL 语法用 JS 链式表达，参数自动防注入）、Prisma（ORM：声明式模型 + 自动生成类型与迁移）。本篇还覆盖连接池（并发访问的命脉）与迁移 migration（表结构版本化管理，不再手改线上库）。

核心内容 ​

1. SQL 基础：建表 / CRUD / 联表 ​

sql
-- 建表：字段类型、约束（主键/唯一/外键）在 DDL 里一次定清
CREATE TABLE users (
  id          BIGSERIAL PRIMARY KEY,
  email       VARCHAR(255) UNIQUE NOT NULL,   -- 唯一约束：邮箱不重复
  name        VARCHAR(50) NOT NULL,
  created_at  TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE orders (
  id          BIGSERIAL PRIMARY KEY,
  user_id     BIGINT NOT NULL REFERENCES users(id),  -- 外键：保证引用完整性
  amount      NUMERIC(10, 2) NOT NULL,               -- 金额用定点数，绝不用 float
  created_at  TIMESTAMPTZ DEFAULT now()
);

-- CRUD
INSERT INTO users (email, name) VALUES ('a@example.com', '小明');
SELECT * FROM users WHERE email = 'a@example.com';
UPDATE users SET name = '大明' WHERE id = 1;
DELETE FROM orders WHERE id = 99;

-- 联表：查每个用户最近一笔订单（JOIN + 子查询）
SELECT u.name, o.amount
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.created_at = (
  SELECT MAX(created_at) FROM orders WHERE user_id = u.id
);

前端锚点：users JOIN orders ≈ 前端把两个数组做「按 id 关联」的合并；子查询 ≈ 先算出一个中间结果再套一层。

2. Knex：查询构建器 ​

js
// db.js —— Knex 实例全局唯一（连接池在实例内复用）
import knex from 'knex'

export const db = knex({
  client: 'pg', // PostgreSQL；mysql/sqlite 只是换 client 名
  connection: {
    host: '127.0.0.1',
    port: 5432,
    user: 'app',
    password: process.env.DB_PASSWORD, // 密码走环境变量，不写死在代码里
    database: 'shop',
  },
  pool: { min: 2, max: 10 }, // 连接池（见第 4 小节）
})

// 链式方法拼 SQL；值自动转占位符 —— 从机制上杜绝注入
const users = await db('users')
  .where('email', 'like', '%@example.com')
  .orderBy('created_at', 'desc')
  .limit(20)

// 联表查询
const rows = await db('orders')
  .join('users', 'orders.user_id', 'users.id')
  .select('users.name', 'orders.amount')
  .where('orders.amount', '>', 100)

// 多步写操作必须用事务：要么全成功，要么全回滚
await db.transaction(async (trx) => {
  const [order] = await trx('orders').insert({ user_id: 1, amount: 200 }).returning('id')
  await trx('users').where('id', 1).update({ /* 扣余额等 */ })
})

要点：Knex 的价值 = 防注入（占位符）+ 可读性 + 与 SQL 语义一一对应。适合「SQL 熟、要精细控制」的团队。

3. Prisma：ORM 对比 ​

prisma
// prisma/schema.prisma —— 声明式模型：一张模型 = 一张表
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model User {
  id       Int     @id @default(autoincrement())
  email    String  @unique
  name     String
  orders   Order[]            // 关系字段：User 1 → N Order
}

model Order {
  id       Int     @id @default(autoincrement())
  userId   Int
  user     User    @relation(fields: [userId], references: [id])
  amount   Decimal @db.Decimal(10, 2)
}
js
// 使用 Prisma：类型安全（TS 下自动生成完整类型，字段拼错编译期报错）
import { PrismaClient } from '@prisma/client'
const prisma = new PrismaClient()

// 联表查询：include 自动生成 JOIN SQL
const users = await prisma.user.findMany({
  where: { email: { contains: '@example.com' } },
  include: { orders: true },
  orderBy: { createdAt: 'desc' },
})

// 事务：交互式
await prisma.$transaction(async (tx) => {
  await tx.order.create({ data: { userId: 1, amount: 200 } })
  await tx.user.update({ where: { id: 1 }, data: { /* ... */ } })
})

选型对比：Knex = 构建器（离 SQL 近、灵活、无类型）；Prisma = ORM（声明式、类型安全、自带迁移工具、有学习曲线与抽象层）。中小型新项目推荐 Prisma；SQL 控制欲强 / 复杂查询多的项目用 Knex。共同点：都不允许字符串拼 SQL。

4. 连接池 ​

js
// 为什么必须有连接池：建立连接要 TCP 握手 + TLS + 鉴权，几十毫秒；
// 每个请求都新建连接，并发一上来数据库直接被握手打爆
// 连接池 = 复用已建立的连接，借出 → 归还

// pg 驱动直连时的池配置（Knex/Prisma 底层都这么干）
import pg from 'pg'
const { Pool } = pg

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,                // 上限：并发超过 10 时请求排队（保护数据库）
  idleTimeoutMillis: 30_000, // 空闲连接 30s 回收
})

// 关键纪律：用完必须 release，否则连接被占满 → 全部请求排队超时 → 「服务挂了」
async function getUser(id) {
  const client = await pool.connect() // 借连接
  try {
    const result = await client.query('SELECT * FROM users WHERE id = $1', [id])
    return result.rows[0]
  } finally {
    client.release() // 无论如何都归还
  }
}

要点：max 不是越大越好——每个连接都是数据库的一份资源；池耗尽的现象是「接口全部超时」，压测时最先暴露。

5. 迁移 migration ​

bash
# 表结构变更做成「版本化脚本」，按序执行，团队/环境之间结构一致
npx knex migrate:make add_orders_table
npx knex migrate:latest    # 应用所有未执行的迁移
npx knex migrate:rollback  # 回滚最近一批
js
// migrations/20260801_add_orders_table.js —— 每个迁移文件 = up（前进）+ down（回滚）
export async function up(knex) {
  await knex.schema.createTable('orders', (t) => {
    t.increments('id')
    t.integer('user_id').notNullable().references('users.id')
    t.decimal('amount', 10, 2).notNullable()
    t.timestamps() // created_at / updated_at
  })
}

export async function down(knex) {
  await knex.schema.dropTable('orders') // 回滚路径必须写，否则没法撤销
}

纪律：改了表结构 → 立即生成迁移 + 提交代码，绝不在线上库手动 ALTER TABLE——否则 5 个环境 5 个结构，部署即事故。Prisma 的 prisma migrate dev 是同类工具的自动版。

常见陷阱 ​

  • 字符串拼接 SQL：注入攻击的头号入口，一律用占位符（Knex/Prisma/参数化查询天然安全）。
  • N+1 查询：循环里逐条查库（for 里 await 查询）——一次列表请求发出 N+1 条 SQL；用 JOIN / include 一次性取回。
  • 忘了归还连接 / 池太小：连接耗尽后所有请求排队超时，服务「假死」；try/finally 保证 release。
  • 线上手改表结构不写迁移：环境之间结构漂移，部署后查询全挂；所有变更走 migration。
  • 多步写没有事务：订单 + 扣库存分两条 SQL，中途失败数据就脏了；用 db.transaction。
  • 金额用 float / 时间不用时区：浮点累积误差会算错账（用 NUMERIC），时间不用 TIMESTAMPTZ 会跨时区错乱。
  • 查询没有索引：WHERE email = ... 全表扫，数据量上来接口直接变慢（第 14 篇「慢接口」的头号原因）。

练习建议 ​

  1. 基础：用 SQLite（knex client: 'sqlite3'）建 users/orders 两张表，写完 INSERT/SELECT/JOIN 全部 CRUD
  2. 进阶：用 Knex 连接 SQLite 实现用户列表接口（分页 + 按邮箱过滤），验证占位符防注入
  3. 综合：用 Prisma 重写同一接口（schema + migrate dev + findMany include），并写一个带事务的下单流程（建订单 + 扣余额，验证失败回滚）

用 /practice nodejs 数据库访问 生成更多针对性练习。
