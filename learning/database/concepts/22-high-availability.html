22 · 数据库高可用 ​

概念简介 ​

单机数据库一旦宕机，业务全线停摆。高可用（HA）的目标是：把「数据库挂掉」从事故变成流程——通过主从复制保存多份数据副本，通过读写分离把查询压力分散到从库，通过故障切换在主机挂掉后几十秒内自动把从库提升为主库，让业务几乎无感。这不是「备份」，备份是兜底数据，高可用是兜底可用性，两者都要有。

核心手段是复制。MySQL 的主从复制基于 binlog（二进制日志）：主库把每次数据变更写进 binlog，从库拉取并在自己机器上重放，得到与主库相同的数据。理解复制原理，是高可用的第一步——延迟、断链、脑裂都从这里来。

核心内容 ​

1. 主从复制原理：binlog 复制链路 ​

text
# ---------- MySQL 异步复制链路(一主一从) ----------
# 主库:   应用线程执行事务 -> 写 binlog -> 事务提交
# 从库:   ① IO 线程 从主库拉取 binlog 并写入本地 relay log(中继日志)
#         ② SQL 线程 重放 relay log,在主库那边回放成同样的数据变更
# 关键点:IO 线程和 SQL 线程是异步的 —— 主库提交后不等待从库,
#        所以「从库数据永远可能比主库旧一点点」,这就是主从延迟的根源

# ---------- 主库配置(my.cnf) ----------
[mysqld]
server-id = 1            # 每个实例唯一,复制链路按 server-id 区分
log-bin = mysql-bin      # 开启 binlog(主从复制的前提,也是备份/恢复的底子)
binlog-format = ROW      # 行格式:记录每行变更,数据一致性好(比 STATEMENT 安全)
binlog-row-image = FULL

# ---------- 从库配置(my.cnf) ----------
[mysqld]
server-id = 2
log-bin = mysql-bin
relay-log = mysql-relay-bin

# ---------- 主库创建复制账号,并授权从库拉取 binlog ----------
CREATE USER 'repl'@'%' IDENTIFIED BY '强密码';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';

# ---------- 从库初始化复制链路 ----------
CHANGE MASTER TO
  MASTER_HOST = '10.0.0.1',        -- 主库 IP
  MASTER_USER = 'repl',
  MASTER_PASSWORD = '强密码',
  MASTER_LOG_FILE = 'mysql-bin.000123',   -- 从主库 SHOW MASTER STATUS 拿到
  MASTER_LOG_POS = 45678;
START SLAVE;

2. 读写分离：主库写、从库读 ​

复制搭好之后，应用层把写请求发给主库、读请求发给从库：

text
# ---------- 读写分离架构 ----------
# 应用 -> 路由层(中间件如 ProxySQL / ShardingSphere,或应用内数据源双配置)
#         -> 写请求(INSERT/UPDATE/DELETE): 发主库
#         -> 读请求(SELECT):               轮询发从库,可加权
#
# 收益:主库只扛写入,从库扛住 80% 以上的读流量,整体吞吐翻几倍
# 代价:从库有延迟,刚写入的数据读从库可能读不到 —— 这叫「读写不一致」
sql
-- 处理读写不一致的常见方案:关键数据强读主库
-- 场景:用户下单成功后立刻查「我的订单」
SELECT * FROM orders WHERE user_id = 1 ORDER BY id DESC LIMIT 10;
-- 如果走从库,可能查不到刚下的单(从库还没重放到这条 binlog)
-- 方案1:下单后 1 秒内的读强制走主库(按时间窗)
-- 方案2:前端交互天然有时差(下单成功页停留几秒),多数场景可接受

3. 半同步复制：牺牲一点性能换不丢数据 ​

异步复制下，主库提交后从库还没拉到 binlog，此时主库宕机——从库上没有这条数据，数据丢了。半同步复制（semi-sync） 让主库提交前至少等一个从库确认「binlog 已收到」，从而保证主库挂了数据也已在从库手上：

sql
-- 安装半同步插件(MySQL 5.7+ 自带,主从都要装)
INSTALL PLUGIN rpl_semi_sync_master SONAME 'semisync_master.so';
INSTALL PLUGIN rpl_semi_sync_slave  SONAME 'semisync_slave.so';

-- 主库开启半同步,并设置等待超时
SET GLOBAL rpl_semi_sync_master_enabled = 1;
SET GLOBAL rpl_semi_sync_master_timeout = 3000;  -- 3 秒内无从库确认就退回异步,保证主库不卡死

-- 从库开启半同步
SET GLOBAL rpl_semi_sync_slave_enabled = 1;
STOP SLAVE; START SLAVE;  -- 重载后生效

代价：每次提交都要等网络往返，延迟上升（主从跨机房时尤其明显）。半同步是「性能 vs 不丢数据」的折中，生产标配。

4. 故障切换：MHA / Orchestrator ​

主机宕机后，需要自动化地：检测故障 → 从从库中选出数据最完整的一台 → 提升为主库 → 把其他从库重新挂到新主库 → 通知应用切换连接。这一步叫 failover，人工执行会按分钟算，自动化工具能压到几十秒。

bash
# ---------- Orchestrator(推荐,提供 API 和 Web UI,业界广泛使用) ----------
# 安装后启动 agent,节点间通过心跳互相发现
orchestrator -c discover -i 10.0.0.1:3306    # 注册主库
orchestrator -c discover -i 10.0.0.2:3306    # 注册从库

# 主库宕机后,人工确认/自动触发切换:
#   orchestrator 自动做:选新主 -> 补齐缺失的 binlog -> 提升 -> 重挂从库
orchestrator -c graceful-master-takeover --failover -i 10.0.0.1:3306

# ---------- 应用层配合:切换后连接目标变了 ----------
# 数据库地址不能写死在应用配置里,应走 DNS / 注册中心 / 代理
# 切换时只需改 DNS A 记录指向新主库,应用自动生效

脑裂问题：网络抖动时新旧主库可能同时认为自己是主，出现「双主」各写各的——必须靠**仲裁（quorum）**机制：切换需要超过半数节点（或外部仲裁者）确认主库真的死了才动手，并把旧主库强制下线（fencing，如用 SET GLOBAL read_only=ON 拒绝旧主写入）。

5. 多机房容灾 ​

单机房故障（断电/网络切割）会让整条主从链一起挂。多机房容灾的常见布局：

text
# ---------- 两地三中心 / 同城双活布局 ----------
# 机房A(主):  主库 + 从库1  —— 应用主力流量
# 机房B(备):  从库2          —— 实时复制,同城专线延迟 < 5ms,可做双活读
# 机房C(远):  从库3          —— 跨城异步复制(专线不稳),只做灾备,平时不读
#
# 容灾等级:
#   机房A 挂 -> 提升机房B 从库2 为主,业务切换读流量(秒级~分钟级)
#   机房A+B 同时挂 -> 机房C 数据最旧但最安全,恢复服务(数据可能丢几十秒)
#
# 关键矛盾:复制链路越远越不稳,跨城一般只做异步复制
#         —— 所以要接受「异地容灾可丢最后几秒数据」的现实

常见陷阱 ​

  • 把备份当成高可用：备份只能救数据，恢复要小时级；主从是救可用性，切换是秒级。两者缺一不可，别用备份替代复制。
  • 忽略主从延迟：做了读写分离但没评估延迟，刚写的订单查不到——对账、刷单检测等场景必须强读主库或延迟敏感查询走主库。
  • 半同步跨机房部署：半同步要求主库提交前等从库确认，跨机房专线抖动会直接把主库拖死，超时设太小会频繁退回异步导致数据保护形同虚设。
  • 切换后应用还在连旧主库：连接串写死 IP、连接池缓存了旧连接——failover 必须配套 DNS/代理/注册中心，且连接池要能感知断连重连。
  • 脑裂不设防：没有仲裁/锁，双主同时写导致数据错乱；旧主必须被强制只读并切断应用流量（fencing）。
  • 从库性能不达标：从库承担全部读流量后先崩——从库要单独做容量规划，复制线程重放慢时优先排查大事务、DDL 在从库的锁等待。

练习建议 ​

  1. 基础：用 Docker 起一主两从 MySQL（官方镜像即可），手写 CHANGE MASTER 配好复制，验证主库 INSERT 后从库能查到，并观察 SHOW SLAVE STATUS 的 Seconds_Behind_Master 字段。
  2. 进阶：开启半同步，对比开关前后的写入延迟；再用一个大事务（如一次性 UPDATE 一百万行）制造复制延迟，观察读写分离下「读不到刚写入数据」的真实效果。
  3. 综合：模拟主库宕机（docker kill 主库容器），手动完成一次故障切换：选从、补齐 binlog、提升、重挂从库，记录每一步的命令和耗时，写出你自己的切换 checklist。

用 /practice database 数据库高可用 生成更多针对性练习。
