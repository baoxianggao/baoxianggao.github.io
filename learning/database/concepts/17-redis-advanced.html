17 · Redis 深入 ​

概念简介 ​

入门篇解决了「Redis 怎么用」,深入篇回答「Redis 怎么用对」。四个主题都有各自的深坑:分布式锁(拿锁容易,放锁、续期、防误删全是细节)、Lua 脚本(原子性怎么借)、持久化(RDB/AOF 怎么取舍)、集群与淘汰(容量与可用性怎么管),外加后端面试与生产事故里出镜率最高的「缓存三大杀手」——穿透、击穿、雪崩。

前端的直觉在这里需要校正:前端代码是「单进程单线程」,天然不需要锁;后端是「多实例并发」,任何「先检查后执行」都可能被别的实例插队。Redis 单线程执行命令这个特性,恰好是把"检查 + 执行"打包成原子的免费道具——理解这一点,整篇就通了。

核心内容 ​

1. 分布式锁:SETNX 的正确姿势 ​

bash
# ---------- 1a. 为什么要分布式锁 ----------
# 场景:定时任务每 10 分钟清理过期订单,部署了 3 个实例
# 没有锁:三个实例同时跑,任务执行 3 次,还可能互踩数据
# 前端类比:你写的前端代码默认单线程,没有这个问题;
# 但后端"多实例 + 共享数据库"等于多个标签页同时操作同一份 state

# ---------- 1b. 加锁:一条命令保证原子 ----------
# NX:key 不存在才设置(拿锁);EX:带过期时间(防死锁)
# 注意:这里同时满足"不存在才写"和"过期",任何一步拆开都会出事故
SET lock:cleanup "instance-1" NX EX 30
# 返回 OK → 抢到锁;返回 (nil) → 锁被别人持有

# 最经典的三个坑:
# 1. 忘了 EX → 实例崩溃,锁永远不释放,任务永久停摆(死锁)
# 2. 任务执行超过 30 秒 → 锁自动过期,别的实例拿到锁,双执行
# 3. 释放时直接 DEL → 可能把"别人新拿到的锁"删掉(必须校验持有者,见第 2 节)

2. Lua 脚本:把"检查 + 操作"打包成原子 ​

lua
-- ---------- 2a. 释放锁的正确姿势(compare-and-delete) ----------
-- 场景:锁到期前任务跑完,要释放锁——但只能删"自己"的锁
-- 拆开写 GET 再 DEL 中间会被别的实例插队(锁可能已换主人)
-- Lua 脚本在 Redis 里整体执行,期间不可能被其他命令打断 → 原子
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
python
# ---------- 2b. Python 中执行 Lua(可运行) ----------
import redis

r = redis.Redis(decode_responses=True)

unlock_script = """
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
"""

# redis-py 的接口是 r.eval(script, numkeys, *keys_args);
# 此处取别名调用,接口等价
execute_lua = r.eval

def try_lock(key: str, owner: str, ttl: int = 30) -> bool:
    """加锁:不存在才写 + 过期时间,一条命令原子完成"""
    return r.set(key, owner, nx=True, ex=ttl)

def safe_unlock(key: str, owner: str) -> None:
    """释放锁:只有持有者是自己时才删除(防误删别人的锁)"""
    execute_lua(unlock_script, 1, key, owner)

# 使用:只有抢到锁的实例才执行任务
if try_lock("lock:cleanup", "instance-1"):
    try:
        print("开始清理过期订单...")   # 业务逻辑(注意:超过锁 TTL 需续期)
    finally:
        safe_unlock("lock:cleanup", "instance-1")
else:
    print("锁被其他实例持有,跳过本次")
text
# ---------- 2c. Redlock 与更务实的方案 ----------
# 问题:单机锁在 Redis 主从切换时会丢(SETNX 写主,主挂了,从还没同步)
# Redlock:向多数节点(如 5 个独立 Redis)都取锁,取到 ≥3 个才算成功
#   → 理论更强,但工程复杂、争议大(时间漂移问题)
# 务实做法:
# 1. 业务能容忍双执行 → 单实例 SETNX + EX 足够
# 2. 不能容忍 → 用 Redisson(Java)等带自动续期的成熟客户端
#    (Redisson 的 watchdog 会在锁快过期时自动续期,不用手写续期)
# 3. 强一致场景(金额扣减等)→ 别用 Redis 锁,回到数据库事务/行锁

3. 持久化:RDB 与 AOF 怎么选 ​

bash
# ---------- 3. RDB 与 AOF ----------
# RDB:定时把内存快照写盘。恢复快、文件小;可能丢最后一次快照后的数据
#   save 900 1          # 900 秒内 ≥1 次写就快照
#   save 300 10         # 300 秒内 ≥10 次写就快照
# AOF:追加记录每条写命令。丢数据窗口小;文件大、恢复慢
#   appendonly yes
#   appendfsync everysec    # 每秒刷盘:最多丢 1 秒数据(生产推荐)
#   appendfsync always      # 每次写都刷盘:不丢数据,但性能大幅下降
# 生产常见组合:同时开 RDB + AOF——RDB 做快速恢复, AOF 补最后的增量
# 注意:Redis 本质是缓存,持久化只是"兜底",别靠它当主数据库

4. 内存淘汰策略:容量不够时听谁的 ​

bash
# ---------- 4. maxmemory 与淘汰策略 ----------
# maxmemory 100mb              # 内存上限(默认无限制,会撑爆机器!)
# maxmemory-policy 见下(默认 noeviction:写命令直接报错)
#   noeviction    不淘汰,写不进(默认,容易变成"线上突然写入失败")
#   allkeys-lru   淘汰最久未访问的(通用推荐)
#   volatile-lru  只淘汰设置了 TTL 的键(优先保"永久键",适合混合场景)
#   allkeys-lfu   淘汰访问频率最低的(热点明显的场景更精准)
# 经验:缓存层用 allkeys-lru,热点稳定场景考虑 lfu;别用默认 noeviction 上线

5. 缓存三大杀手:穿透、击穿、雪崩 ​

text
# ---------- 5a. 缓存穿透:查"不存在"的数据 ----------
# 症状:攻击者刷一个不存在的 id(如 user:-1),缓存永远查不到 → 每次都打数据库
# 解决 1:空结果也缓存(值存 null,TTL 30~60 秒)
# 解决 2:布隆过滤器拦截"不可能存在的 key",在缓存之前就挡掉
# 解决 3:接口层参数校验(非法 id 直接拒绝)

# ---------- 5b. 缓存击穿:热点 key 过期瞬间 ----------
# 症状:某热点 key(如秒杀商品)过期的一瞬间,大量请求同时回源数据库 → 打垮
# 解决 1:互斥锁,只让一个请求去查库重建,其余等待/拿旧值
# 解决 2:逻辑过期——缓存永不过期,值里带过期时间戳,过期时后台异步重建
# 区别记忆:穿透是"根本不存在",击穿是"单个热点过期"

# ---------- 5c. 缓存雪崩:大量 key 同时过期 ----------
# 症状:缓存批量过期(比如都设了 3600 秒,同一时间齐刷刷过期),数据库被打满
# 解决:过期时间加随机抖动——SETEX(key, 300 + random(0, 60))
# 让过期时间均匀散开,而不是齐步走
# 区别记忆:击穿是"一个热点",雪崩是"一批 key 集体过期"

6. Redis Cluster:水平扩展 ​

bash
# ---------- 6. Cluster 要点 ----------
# 数据按 key 哈希分到 16384 个槽,每台节点负责一段槽
# redis-cli --cluster create node1:6379 node2:6379 node3:6379 --cluster-replicas 1
# 客户端读 key:槽不在本节点时返回 MOVED 错误,客户端跟随跳到正确节点
# 坑 1:跨槽的多键操作不支持(MGET 两个槽不同的 key 报错)
# 坑 2:事务/管道也受槽限制,所有 key 必须落在同一槽
# 解决:hash tag——{user:123}:info 与 {user:123}:likes 按 {} 内内容哈希到同一槽
# 何时上集群:单机内存不够 / 单点故障不可接受;数据量小就单机 + 主从,别过度设计

要点:锁的三要素(NX + EX + 校验释放)、Lua 是原子性道具、RDB/AOF 组合兜底、淘汰策略别用默认值、穿透/击穿/雪崩三个病三个药——这五组对错判断,就是 Redis 生产经验的全部精华。

常见陷阱 ​

  • 加锁不带 EX / 释放锁直接 DEL:死锁或误删别人的锁;锁的三要素缺一不可,释放必须 Lua 校验持有者。
  • 任务比锁的 TTL 长:锁先过期,第二个实例拿到锁,双执行;用带 watchdog 自动续期的客户端或自己续期。
  • 把「检查 + 操作」拆成两条 Redis 命令:中间任何时刻都可能被插队;凡是"必须原子"的,一律 Lua 或单命令。
  • maxmemory 不设或默认 noeviction:内存撑爆 OOM,或线上突然写入失败;主动设置 maxmemory + 淘汰策略。
  • 穿透/击穿/雪崩混为一谈、乱用药:穿透缓存空值/布隆;击穿锁热点 key;雪崩过期加随机抖动。
  • Cluster 下做跨槽 MGET/事务:直接报错;用 hash tag 让相关 key 落同一槽。
  • 缓存没加随机 TTL:上线时齐刷刷过期,数据库高峰期被突袭。

练习建议 ​

  1. 基础:用 Python 写一个完整的分布式锁类(try_lock / safe_unlock + Lua 释放),开 3 个进程同时抢锁,验证同一时刻只有 1 个拿到;再故意不校验持有者,复现「误删别人锁」的 bug。
  2. 进阶:分别复现缓存穿透(请求不存在的 id 观察 DB 打满)、击穿(热点 key 短 TTL + 并发回源)、雪崩(100 个 key 同一秒过期),各自用第 5 节的方案修复,记录修复前后回源数据库的次数。
  3. 综合:设计一个「秒杀商品详情」高并发方案:商品详情缓存(带随机 TTL 防雪崩)、库存扣减用 Lua 保证原子、热点 key 用逻辑过期防击穿、非法商品 id 用布隆过滤防穿透,再叠加分布式锁只放一个实例回源数据库,画一张完整的请求流程图并跑通验证。
