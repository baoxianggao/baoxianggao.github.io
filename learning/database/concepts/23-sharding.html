23 · 分库分表 ​

概念简介 ​

单库单表的数据量和并发到达一定规模后（经验值：MySQL 单表几千万行、单库 QPS 几千以上），性能开始不可控——索引层级变深、锁竞争加剧、备份和恢复变得极慢。分库分表就是把「一张大表 / 一个大库」拆成「多张小表 / 多个小库」，让每个分片的数据量和压力都变小，整体容量和吞吐水平扩展。

拆分有两种维度：垂直拆分（按业务模块拆库，如订单库/用户库/商品库）和水平拆分（同一张表按分片键拆成多张结构相同的表）。水平拆分是真正的难点：分片键怎么选、数据怎么路由、ID 怎么生成、跨分片查询怎么办、以后怎么扩容——每一步都有坑，分库分表是「能不做就不做，要做就一次设计对」的方案，本篇逐个拆解。

核心内容 ​

1. 垂直拆分 vs 水平拆分 ​

text
# ---------- 垂直拆分(按业务域) ----------
# 把一个大库按业务模块拆成多个库:订单库、用户库、商品库、库存库
# 优点:职责清晰,不同业务可按各自节奏扩容,天然配合微服务
# 缺点:跨业务 JOIN 没了(只能应用层聚合),跨库事务变分布式事务(见 21 篇)
# 适用:业务域耦合度低、库整体负载高但单表不算大

# ---------- 水平拆分(按行拆分) ----------
# 用户表 1 亿行 -> 按 user_id 拆成 64 张表(user_0 ~ user_63),可分布在多个库
# 优点:单表行数变小,索引变浅,写压力分散
# 缺点:路由、全局唯一 ID、跨分片查询、扩容全是新问题
# 适用:单表行数/写入是瓶颈,垂直拆分解决不了
sql
-- 水平拆分示意:同一张表,物理上多份,逻辑上是一张
-- 分片规则:user_id % 64 -> user_id=10001 落在表 user_17(10001 % 64 = 17)
CREATE TABLE user_0  (id BIGINT PRIMARY KEY, user_name VARCHAR(64), ...);
CREATE TABLE user_1  (id BIGINT PRIMARY KEY, user_name VARCHAR(64), ...);
-- ... 共 64 张,业务代码或中间件(ShardingSphere/MyCat)负责把 SQL 路由到对应表

2. 分片键选择：决定成败的一步 ​

分片键 = 数据按什么字段散列。选错分片键的后果：热点分片（一个分片被打爆，其余闲置）或跨分片查询泛滥。

text
# ---------- 选分片键的三条原则 ----------
# 1. 数据能均匀分散:高基数字段,且每个值的访问频率大致相同
# 2. 覆盖绝大多数查询条件:90% 以上的查询都带这个字段(否则天天跨分片)
# 3. 尽量不变化:分片键改了 = 数据要搬家(迁移成本极高)

# 正确示例:订单表按 user_id 分片 —— 用户查「我的订单」天然带 user_id,单分片完成
# 错误示例:订单表按 order_id 分片 —— 「我的订单列表」不带 order_id,扫全部分片

# 无法避免的多维度查询(如按商家查订单):
#   方案A:冗余一份按 merchant_id 分片的订单表(双写,最终一致)
#   方案B:按 user_id 分片 + 商家侧查询走 Elasticsearch(见 19 篇)
#   方案C:接受全分片广播查询(分片少时可以,多了不行)

3. 分片策略：range 还是 hash ​

sql
-- ---------- 策略一:Range 范围分片 ----------
-- 按 id/时间范围分片:2023 年数据在表 order_2023,2024 年在 order_2024
-- 优点:扩容简单(加一张新表),范围扫描高效,冷热数据自然分离
-- 缺点:写热点集中在「最新分片」——刚上线的业务全部写当前表,单分片扛不住
CREATE TABLE order_2023 (id BIGINT PRIMARY KEY, order_no VARCHAR(32), ...);
CREATE TABLE order_2024 (id BIGINT PRIMARY KEY, order_no VARCHAR(32), ...);

-- ---------- 策略二:Hash 哈希分片 ----------
-- 按分片键取模/一致性哈希:order_user_17,order_user_18...
-- 优点:写流量均匀分散到各分片,没有热点
-- 缺点:扩容要迁移数据(取模规则变了,老数据读不到);范围扫描无优势
-- 实践:大多数 OLTP 业务选 Hash;时序/归档类数据选 Range

4. 全局唯一 ID：雪花算法与号段模式 ​

分片后单表自增 ID 不能用了（每张表都从 1 开始，必然冲突）。全局唯一 ID 要满足：全局唯一、趋势递增（利于索引）、生成性能高、尽量短。

text
# ---------- 雪花算法(Snowflake):业内最常用 ----------
# 64 位 long:1 位符号位 + 41 位毫秒时间戳(可用 69 年)
#           + 10 位机器 ID(最多 1024 台) + 12 位序列号(每毫秒 4096 个)
# 趋势递增,无需访问数据库,单机每秒可生成几十万个 —— 完美契合分片场景
# 注意:依赖机器时钟,时钟回拨会生成重复 ID,生产要做时钟回拨保护
sql
-- ---------- 号段模式(Leaf segment):适合需要「自增感觉」的业务 ----------
-- 一张表存每个业务的最大号段,取号时一次性拿一段,内存发号
CREATE TABLE id_segment (
  biz_tag   VARCHAR(32) PRIMARY KEY,      -- 业务标识,如 order_id
  max_id    BIGINT NOT NULL,              -- 当前已发放的最大 ID
  step      INT NOT NULL DEFAULT 1000,    -- 每次取号段的长度
  updated_at DATETIME NOT NULL
);

-- 取号段:原子地把 max_id 推进一个 step,拿到的就是本进程的可用区间
-- 两个并发请求只有一个能成功 UPDATE,天然防并发重复
UPDATE id_segment
   SET max_id = max_id + step, updated_at = NOW()
 WHERE biz_tag = 'order_id' AND max_id = 0;   -- 示例:需配合 SELECT ... FOR UPDATE
-- 拿到 (旧max_id, 新max_id] 区间后,应用进程在内存里发号,不再访问这张表
-- 优点:ID 是数字且连续(对业务友好);缺点:多一个取号服务/表的依赖

5. 跨分片查询难题 ​

分片后最痛苦的问题：所有原本优雅的 SQL 都变味了。

text
# ---------- 分片前 ----------
# SELECT * FROM orders WHERE user_id = 1;                    -> 单分片,快
# SELECT * FROM orders WHERE merchant_id = 5;                -> 全分片广播,慢
# SELECT COUNT(*) FROM orders;                               -> 全部分片求和
# SELECT * FROM orders ORDER BY created_at DESC LIMIT 20;    -> 各分片取 TOP20 再归并
# JOIN user ON ...                                           -> 应用层拼装,或冗余字段
# 全局唯一索引(如唯一订单号):单表 UNIQUE 约束失效
#   -> 方案:唯一性校验只能靠「分片键+本地唯一」或单独存一张去重表/Redis set

# ---------- 应对原则 ----------
# 1. 把跨分片操作「设计掉」:按查询维度选好分片键,让 90% 查询落单分片
# 2. 不得已的聚合:中间件做「广播 + 归并」(分片数少时可接受)
# 3. 复杂检索/聚合分析:同步一份到 ES/数仓,别在分片表上硬做

6. 扩容：分片数变了怎么办 ​

text
# ---------- 取模分片的扩容噩梦 ----------
# user_id % 64 -> 要扩到 128 张:10001%64=17,而 10001%128=17,规则全变
# 所有存量数据都要重新计算落点并迁移 —— 停机迁移或双写迁移,成本巨大

# ---------- 扩容的正确姿势 ----------
# 方案A:一致性哈希 + 虚拟节点 —— 迁移量只占 1/N,但仍要迁移
# 方案B:提前规划 —— 一开始就按未来 3-5 年的量定分片数,避免中途扩容
# 方案C:两级路由 —— 分片编号 -> 物理库映射表,扩容时只改映射、搬少量库
# 方案D(推荐):用「日期+hash 双维度」的表设计,数据按时间归档,老表只读
# 最实用的一条:分库分表 1 次设计对,比扩容技巧都重要 —— 分片数一开始就按
# 「峰值单分片容量 * 分片数 >= 5 年后的总容量」来定

常见陷阱 ​

  • 分片键选错导致热点：选了 order_id 分片，商家大促时单商家订单全落一个分片；或选了 status 这种低基数字段，数据全部堆到一个分片。分片键必须高基数 + 均匀访问。
  • 过早分库分表：单表几百万行、慢查询还没优化过就上分片——索引、缓存、归档（如冷数据按月归档）才是前三级台阶。分库分表是最后手段，会引入巨大复杂度。
  • 扩容没有预案：取模分片扩到 128 张要全量迁移，半夜出事故时只能停服；选分片数时就要想到未来，或直接用一致性哈希。
  • 全局唯一索引失效：分片后 UNIQUE 约束只在分片内有效，手机号、订单号等全局唯一要靠去重表/Redis/分段发号保证，上线后才发现重复就是事故。
  • 跨分片 JOIN 硬做：把应用层聚合写成「先查一半再查另一半」的 N+1 循环，性能爆炸；应冗余字段或同步到检索/分析引擎。
  • 分片后忘了从库：分片解决的是容量，没解决可用性——每个分片仍要做主从复制（见 22 篇），否则一个分片挂了等于全部业务缺一块。

练习建议 ​

  1. 基础：用 SQL 手工创建 user_0 ~ user_7 八张表，写清楚 user_id % 8 的路由规则，并用 SQL 分别演示「带分片键查询」和「不带分片键广播查询」的区别。
  2. 进阶：用 Python/Node 写一个小型分片路由层：解析 SQL 中的 user_id 值 → 计算分片 → 把 SQL 改写为操作具体表；再实现号段发号器（内存区间 + 更新表）。
  3. 综合：设计一个「订单表 5 年后预计 5 亿行」的拆分方案：选分片键并论证（覆盖哪些查询、热点风险）、定分片数与 hash 策略、给出全局唯一 ID 方案、列出哪些查询需要跨分片处理及对策、写出扩容预案。
