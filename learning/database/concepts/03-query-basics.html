03 · 查询基础 ​

前置：02 数据建模基础 · 预计：1.5~2 小时

概念简介 ​

上一篇把数据拆进了多张表——这是写的视角;现在学读的视角:怎么把散在各表的数据重新拼回来,并算出统计值。两个核心武器:JOIN(联表)和聚合(GROUP BY + 聚合函数)。前端工程师 80% 的 SQL 工作量就是这两件事的排列组合。

JOIN 解决的痛点是「数据被拆分后如何还原」:前端用嵌套对象天然能 user.posts[0].title,数据库里只能 orders.user_id 存着引用,必须通过 JOIN 把两行拼成一行。聚合解决的痛点是「统计」:前端要写 reduce 半天,SQL 一句 GROUP BY 搞定。

核心内容 ​

沿用 02 篇的四张表(users / products / orders / order_items),先备好数据:

sql
-- 三个用户
INSERT INTO users (name, email) VALUES
  ('小明', 'ming@test.com'), ('小红', 'hong@test.com'), ('阿强', 'qiang@test.com');

-- 四个商品
INSERT INTO products (name, price) VALUES
  ('键盘', 199.00), ('鼠标', 99.00), ('显示器', 1299.00), ('耳机', 299.00);

-- 三个订单
INSERT INTO orders (user_id, amount) VALUES (1, 298.00), (2, 1299.00), (1, 299.00);

-- 订单与商品的关联(中间表)
INSERT INTO order_items (order_id, product_id, quantity) VALUES
  (1, 1, 1), (1, 2, 1),   -- 订单1:键盘x1 + 鼠标x1
  (2, 3, 1),              -- 订单2:显示器x1
  (3, 4, 1);              -- 订单3:耳机x1

1. INNER JOIN:只留两边都匹配的行 ​

sql
-- 每个订单属于哪个用户:orders 和 users 按 user_id 对上
SELECT o.id AS 订单号, u.name AS 买家, o.amount AS 金额
FROM orders o INNER JOIN users u ON o.user_id = u.id;

-- 等价于前端伪代码:
-- const rows = orders.flatMap(o =>
--   users.filter(u => u.id === o.user_id).map(u => ({ 订单号: o.id, 买家: u.name, ... })))

INNER JOIN 只保留两边都匹配的行。o、u 是表别名,表名太长时必用。

2. LEFT JOIN:保留左表全部行 ​

sql
-- 每个用户及其订单数(没买过东西的用户也要显示,订单列为 NULL)
SELECT u.name, o.id AS 订单号
FROM users u LEFT JOIN orders o ON u.id = o.user_id;

-- 结果里「阿强」也会出现,只是订单号是 NULL —— 这正是 LEFT 的意义

LEFT JOIN = JS 里「以左表为基准做 map,右表没匹配就填空」。RIGHT JOIN 就是对称版(右表全保留),实际业务里几乎都写成 LEFT,养成习惯。

3. 聚合与 GROUP BY ​

聚合函数把多行压成一个值:COUNT(行数)、SUM(求和)、AVG(平均)、MAX/MIN。

sql
-- 订单总数
SELECT COUNT(*) AS 总订单数 FROM orders;

-- 按用户分组统计:每人下了几单、总金额多少
SELECT user_id AS 用户, COUNT(*) AS 订单数, SUM(amount) AS 总金额
FROM orders
GROUP BY user_id;

-- 等价于前端:
-- orders.reduce((acc, o) => {
--   acc[o.user_id] ??= { 订单数: 0, 总金额: 0 };
--   acc[o.user_id].订单数++; acc[o.user_id].总金额 += o.amount;
--   return acc;
-- }, {})

GROUP BY 的执行顺序:先 WHERE 过滤 → 再分组 → 再聚合。所以「只统计已付款订单」的过滤条件必须放 WHERE,不能放 HAVING。

sql
-- WHERE 在分组前过滤:只统计已付款订单
SELECT user_id, COUNT(*) AS 已付单数
FROM orders
WHERE status = 'paid'
GROUP BY user_id;

4. HAVING:给分组结果做过滤 ​

HAVING 在分组之后执行,所以能用聚合结果过滤(WHERE 里不能写 COUNT(*) > 1)。

sql
-- 只显示下单超过 1 单的用户
SELECT user_id, COUNT(*) AS 单数
FROM orders
GROUP BY user_id
HAVING COUNT(*) > 1;

5. 子查询:先查一层,再查一层 ​

子查询就是 SELECT 套 SELECT,等价于「先算出一个结果集,再拿它当输入」。

sql
-- 查「下单金额最高的订单」属于谁(两段式:先求最大金额,再按金额查)
SELECT * FROM orders
WHERE amount = (SELECT MAX(amount) FROM orders);

-- 查「买过键盘(商品 id=1)的用户」—— IN 子查询返回一个 id 列表
SELECT name FROM users
WHERE id IN (SELECT DISTINCT user_id FROM orders o
             JOIN order_items oi ON o.id = oi.order_id
             WHERE oi.product_id = 1);

6. DISTINCT:去重 ​

sql
-- 哪些用户下过单(去重)
SELECT DISTINCT user_id FROM orders;

-- 注意:DISTINCT 是「整行组合」去重,不是单列去重
SELECT DISTINCT user_id, status FROM orders;  -- (1,'pending') 与 (1,'paid') 是两行

要点:JOIN 还原结构,GROUP BY 压缩结构,子查询做多步推理。写复杂查询时,先想清楚「结果是一行还是多行」,再选工具。

常见陷阱 ​

  • LEFT JOIN 后加 WHERE 条件变成 INNER JOIN:LEFT JOIN ... WHERE o.id IS NOT NULL 会把左表没匹配的行过滤掉——过滤条件想作用于右表时,要放进 ON 子句。
  • HAVING 滥用:能用 WHERE 的别用 HAVING。WHERE 先过滤,数据量小,配合索引快;HAVING 在聚合后过滤,全量数据都要算一遍。
  • GROUP BY 后 SELECT 了非分组列:MySQL 8 默认开 ONLY_FULL_GROUP_BY,SELECT user_id, amount ... GROUP BY user_id 会直接报错——amount 每组的取值不确定,SQL 拒绝猜测。
  • COUNT(列) 与 COUNT(*) 结果不同:COUNT(amount) 忽略 NULL 行,COUNT(*) 数所有行。想数行数永远用 COUNT(*) 或 COUNT(1)。
  • DISTINCT 以为是单列去重:SELECT DISTINCT a, b 是组合去重,(1,'x') 和 (1,'y') 都会保留。
  • 子查询当性能救星:WHERE id IN (子查询) 在大数据量下可能很慢,EXISTS 通常更快(06 篇详述)。

练习建议 ​

  1. 基础:对 learn_db 的 4 张表,分别写出:INNER JOIN 查订单买家、LEFT JOIN 查从未下单的用户。
  2. 进阶:写一条查询:每个商品被下单的总数量,按数量倒序;再用 HAVING 筛出销量 ≥ 2 的商品。
  3. 综合:把「每个用户买了哪些商品名(去重)」用 JOIN + DISTINCT 写出来,然后把你原来的 JS reduce 版本并排贴在 notes.md,对比两者思路。

用 /practice database 查询基础 生成更多针对性练习。
