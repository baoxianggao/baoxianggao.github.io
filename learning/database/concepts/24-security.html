24 · 数据库安全 ​

前置：23 分库分表 · 预计：2~2.5 小时

概念简介 ​

数据库是所有敏感数据的最终存放地——用户手机号、密码哈希、支付记录。一次拖库（数据被导出）或一条被注入的 SQL，损失远超任何一个前端 XSS 漏洞。数据库安全覆盖五个层面：最小权限（账号只给够用的权限）、账号管理（谁在连、能连哪）、数据加密（传输中 TLS、存储中加密）、注入防护（参数化查询）、审计与脱敏（出事查得到、流出不带敏感字段）。

安全不是「加一个防火墙」，而是一套纵深防御（Defense in Depth）：即使某层被突破，下一层仍能挡住或止血。前端安全主要防「用户输入打进来」，数据库安全多了一层——防「应用被攻破后数据被拖走」，这也是两者思维最大的差异。

核心内容 ​

1. 最小权限原则：账号只给够用的 ​

每个应用/每类任务一个独立账号，权限精确到表和操作类型。绝不用 root 跑业务。

sql
-- ---------- 创建业务账号,只授权给业务真正用的库和操作 ----------
-- 创建只读账号:给数据分析/报表用,没有写权限
CREATE USER 'report_ro'@'10.0.0.%' IDENTIFIED BY '只读账号强密码';
GRANT SELECT ON shop_db.* TO 'report_ro'@'10.0.0.%';

-- 创建业务写账号:只给订单库,且限制来源网段(应用服务器网段)
CREATE USER 'shop_app'@'10.0.1.%' IDENTIFIED BY '业务账号强密码';
GRANT SELECT, INSERT, UPDATE, DELETE ON shop_db.* TO 'shop_app'@'10.0.1.%';
-- 业务账号不给 DDL(DROP/ALTER)权限:防误操作删表,DDL 走 DBA 评审后执行
-- 不给 SUPER/GRANT 权限:防被拖库后进一步提权

-- 清理不再使用的账号(离职/废弃服务)
DROP USER IF EXISTS 'old_service'@'%';

-- 检查当前有哪些账号、各自什么权限(定期审计)
SELECT user, host FROM mysql.user;
SHOW GRANTS FOR 'shop_app'@'10.0.1.%';

2. 传输加密：TLS 让「偷听」失效 ​

数据库与应用之间的流量明文时，同网段内任何一台被攻破的机器都能抓包看到密码和业务数据。必须启用 TLS：

sql
-- ---------- MySQL 启用 TLS 连接(生产强制) ----------
-- 1. 服务端配置(my.cnf):证书由内部 CA 签发
[mysqld]
ssl-ca      = /etc/mysql/certs/ca.pem
ssl-cert    = /etc/mysql/certs/server-cert.pem
ssl-key     = /etc/mysql/certs/server-key.pem
require_secure_transport = ON   -- 拒绝一切明文连接,防「忘了加密」

-- 2. 应用连接串显式启用 TLS
-- MySQL:  jdbc:mysql://db:3306/shop_db?sslMode=VERIFY_IDENTITY
-- Python: mysql.connector.connect(..., ssl_disabled=False, ssl_ca='/path/ca.pem')

-- 3. 验证当前会话是否加密
SHOW STATUS LIKE 'Ssl_cipher';   -- 非空 = 已加密,空 = 明文,立即排查

3. 静态加密：数据落盘也要锁 ​

拖库/物理介质丢失时，磁盘上的数据是明文的——**静态加密（Encryption at Rest）**保证即使 .ibd 文件被拷走也读不出明文。MySQL 8.0 提供原生表空间加密（TDE）：

sql
-- ---------- 表空间加密(InnoDB TDE) ----------
-- 1. 开启 keyring 插件(密钥管理)后,建表/改表指定加密
CREATE TABLE payment (
  id BIGINT PRIMARY KEY,
  amount DECIMAL(10,2) NOT NULL
) ENCRYPTION='Y';   -- 该表数据文件被加密,密钥存于 keyring,由 DBA 保管

ALTER TABLE user_account ENCRYPTION='Y';   -- 存量表加密(重建表,选低峰期)

-- 补充:字段级加密(敏感字段如身份证号,配合应用层)
-- 应用侧用 AES 加密后存密文,SQL 里只操作密文;解密在应用内存完成
-- 注意:密文列无法用普通索引精确匹配,搜索只能先查出来再解密,要接受这个代价

4. SQL 注入防护：参数化是唯一正解 ​

SQL 注入的本质是把用户输入拼进 SQL 变成代码。防护铁律：永远使用参数化查询（Prepared Statement），任何字符串拼接 SQL 都是漏洞。

python
# ---------- 错误写法:字符串拼接(必出事故) ----------
# 用户输入 user_input = "1 OR 1=1",查询就变成 SELECT * FROM user WHERE id=1 OR 1=1
# 直接把整张表返回;输入 "1; DROP TABLE user;--" 更致命
# sql = f"SELECT * FROM user WHERE id = {user_input}"   # 绝对不能这样写

# ---------- 正确写法:参数化查询,输入只当数据不当代码 ----------
import mysql.connector

conn = mysql.connector.connect(host='127.0.0.1', user='shop_app', password='xxx')
cur = conn.cursor(prepared=True)
# 占位符 %s:用户输入被数据库当作文本值处理,永远不可能被解释成 SQL
cur.execute(
    "SELECT * FROM user WHERE id = %s AND status = %s",
    (user_input, 1)          # 参数单独传,与 SQL 模板分离
)
rows = cur.fetchall()
java
// Java 端同样:PreparedStatement 的参数占位,而不是 Statement 拼串
// String sql = "SELECT * FROM user WHERE id = " + id;  // 错!
// PreparedStatement ps = conn.prepareStatement("SELECT * FROM user WHERE id = ?");
// ps.setLong(1, id);                                   // 对!

其他必须知道的注入面：ORDER BY 的字段名/排序方向不能参数化（白名单校验）、LIKE 通配符转义、存储过程里同样禁止拼接。ORM 框架默认参数化，但写原生 SQL（见 12 篇 ORM 的 raw query）时最容易回退到拼接——审查代码时优先看这些地方。

5. 审计日志：出事能追溯 ​

打开审计后，谁、在什么时间、从哪个 IP、执行了什么语句，都有记录。不是每个库都开（开销大），但涉及敏感操作的表/账号必须审计：

sql
-- ---------- 通用日志审计(性能开销大,只用于短时间排查) ----------
SET GLOBAL general_log = 'ON';
SET GLOBAL general_log_file = '/var/log/mysql/general.log';   -- 用完即关

-- ---------- MySQL Enterprise Audit / 开源替代(audit plugin) ----------
-- 只审计敏感账号的敏感操作,而不是全量,控制开销
-- 例如:只记录谁连过、谁执行了 DDL、谁读过 payment 表

-- ---------- 业务层审计(最常用、最可控) ----------
-- 关键表加「操作日志表」,应用在写业务数据时同步写审计
CREATE TABLE audit_log (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  operator   VARCHAR(64) NOT NULL,      -- 操作人(应用层用户名,不是数据库账号)
  action     VARCHAR(32) NOT NULL,      -- INSERT/UPDATE/DELETE/LOGIN
  table_name VARCHAR(64) NOT NULL,
  record_id  BIGINT NOT NULL,
  old_value  JSON,                      -- 变更前快照(敏感操作要求)
  new_value  JSON,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;
-- 规则:审计日志表只追加(INSERT),任何人没有 UPDATE/DELETE 权限

6. 数据脱敏：数据流出时不带敏感信息 ​

开发/测试/数据分析需要真实结构的数据，但不能把真实手机号、身份证带出去。**脱敏（Masking）**在数据导出的边界上执行：

sql
-- ---------- 导出前脱敏:身份证号只留前 4 后 4 ----------
SELECT id,
       user_name,
       CONCAT(LEFT(id_card, 4), '****', RIGHT(id_card, 4)) AS id_card_masked,
       CONCAT(LEFT(phone, 3), '****', RIGHT(phone, 4))     AS phone_masked
FROM user_account
LIMIT 1000;
-- 生产库本身不存明文:写入时应用层就脱敏或加密,「脱敏在源头做」是最稳的

-- ---------- 测试环境数据一律用脱敏副本 ----------
-- mysqldump 导出 -> 管道里跑脱敏脚本 -> 再导入测试库
-- 绝不直接把生产库全量导进测试环境(很多泄露事故就发生在这)

常见陷阱 ​

  • 用 root 跑业务：一次注入/一次误删就全军覆没；业务账号最小权限 + 网段限制，root 只留 DBA 堡垒机操作。
  • 忘记传输加密：数据库和应用在同内网就「反正没人看」，同网段一台机器被攻破就能抓包；require_secure_transport=ON 是底线。
  • 拼接 SQL 的手写残留：ORM 参数化没问题，但手写原生 SQL 时最容易退化成拼接；code review 和自动化扫描（gitleaks / sqlmap 类规则）必须覆盖。
  • 日志把敏感数据当审计内容：审计表/日志里存了明文身份证号，审计反而成了泄露源；审计同样要脱敏或引用 ID。
  • 备份文件不加密：备份文件是明文数据的第二份副本，被拖走等于拖库；备份必须加密存储、限制访问权限。
  • 密钥硬编码进代码/配置：数据库密码、TDE 密钥、TLS 私钥写进仓库——用环境变量/密钥管理服务（见安全规范），一旦泄露必须轮换。

练习建议 ​

  1. 基础：在本地 MySQL 里练习账号管理：创建只读账号、业务账号，用 SHOW GRANTS 验证权限边界，再验证未授权操作会报错；尝试手工构造一次字符串拼接导致的注入（先在测试表上），感受危害。
  2. 进阶：启用 TLS 连接（生成自签证书），验证 Ssl_cipher 生效；把应用代码里的原生查询改成参数化，并写一个单元测试证明注入输入被安全处理。
  3. 综合：为你设计的电商库写一份安全方案：账号矩阵（每个账号的权限）、TLS/TDE 开启步骤、敏感字段清单及脱敏/加密策略、审计日志表设计、备份加密与访问控制，并列出安全审查 checklist。
