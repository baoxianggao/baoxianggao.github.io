06 · 消息队列 ​

前置：05 负载均衡 · 预计：1.5~2 小时

概念简介 ​

消息队列（Message Queue, MQ）是「生产者」和「消费者」之间的异步管道：生产者只负责把消息投递到队列就返回，消费者在自己的节奏里消费。它解决三类问题——解耦（下单服务不用知道短信服务长什么样）、削峰（秒杀洪峰被队列缓冲，下游按能力消费）、异步（耗时操作不阻塞主请求）。

对前端工程师来说，MQ 最像事件总线：Vue 的 mitt、React 里的发布订阅、微前端的事件通信，都是「发消息的人不认识收消息的人」。区别在于：前端事件总线是进程内的、无持久化的、挂了就丢了；MQ 是跨服务的、持久化的、可重放可追踪的——把事件总线的可靠性提升到生产级。

本章覆盖：为什么需要 MQ、三大代表怎么选、生产消费模型、分区与消费组、消息可靠性（至少一次 vs 恰好一次）、死信队列。核心心智是：MQ 不保证「不丢不重」，它只保证「可追踪」——可靠性靠消费者幂等来兜底。

核心内容 ​

1. 为什么需要 MQ：同步调用的痛点 ​

text
同步调用（无 MQ）：
  下单请求 ──► 订单服务 ──► 短信服务（50ms）
                    └──────► 积分服务（30ms）
                    └──────► 统计服务（20ms）
  → 用户等待 100ms+，短信服务一挂，下单整个失败（级联故障）

异步解耦（有 MQ）：
  下单请求 ──► 订单服务 ──► 写库 + 投递「订单创建」事件，立即返回
                    │
                    ▼
              [订单事件队列]
              ────┬────┬────┬────
                  ▼    ▼    ▼    ▼
              短信   积分   统计  推荐（各自独立消费，互不阻塞）
  → 用户只等写库的时间；下游服务慢/挂都不影响下单

三大收益对应三个场景：解耦（新增一个「优惠券服务」只需订阅事件，不用改下单代码）、削峰（秒杀 10 万 QPS 打进来，下游数据库只承受 1000 QPS）、异步（邮件发送从请求链路挪到后台）。代价是引入了「最终一致」与「消息可追踪」的复杂度——没有免费的解耦。

2. 三大代表选型 ​

维度KafkaRabbitMQRedis Stream
定位日志/事件流（高吞吐）业务消息路由轻量流（不引新组件）
吞吐百万级条/s（顺序写盘）万级条/s十万级（内存）
路由能力弱（topic 只能广播）强（exchange 按 key 路由）弱（按 stream）
可靠性靠副本 + ack成熟（confirm/ack）弱（依赖持久化配置）
典型场景埋点日志、订单事件流任务分发、按条件路由简单削峰、临时任务
运维成本高（依赖 ZooKeeper/KRaft）中低（复用 Redis）

选型口诀：高吞吐事件流选 Kafka，灵活路由业务消息选 RabbitMQ，已有 Redis 且场景简单就用 Redis Stream。选型是权衡不是攀比——为「每天几百条」的消息上 Kafka 集群，是拿大炮打蚊子。

3. 生产者 / 消费者模型 ​

mermaid
flowchart LR
    P1[生产者1 订单服务] --> T[(Topic: order_events)]
    P2[生产者2 退款服务] --> T
    T --> C1[消费者1 短信服务]
    T --> C2[消费者2 积分服务]
    T --> C3[消费者3 统计服务]

核心概念：Topic（主题） 是消息的逻辑分类；生产者投递到 Topic，消费者订阅 Topic。任何服务都可以同时是生产者和消费者——服务之间的耦合从「代码调用」降级为「约定 Topic 与消息格式」。

4. 分区与消费组 ​

这是 Kafka 吞吐的关键：一个 Topic 分成多个 Partition（分区），消息按 key 哈希进分区，分区是并行与顺序的单位：

text
Topic: order_events（8 个分区）
  分区0: [order#1] [order#2] ...
  分区1: [order#3] [order#4] ...
  ...

消费者组（同组内分工消费，组间各自独立）：
  组A（短信服务，3 个实例）： 分区0→实例1  分区1→实例2  ...
  组B（统计服务，2 个实例）： 分区0→实例1  ...（与组A无关）

关键规则：
  同一分区内的消息 → 顺序消费（同组内由同一消费者处理）
  同组内分区数 ≥ 消费者数，否则有消费者空转
  不同分区之间 → 消息乱序（不同订单之间顺序无意义）

「分区内有序、分区间无序」是全局设计原则：需要保证顺序的业务（同一订单的「创建→支付→发货」事件）必须用同一个分区键（订单号），否则事件乱序会导致状态机跑飞。

5. 消息可靠性：至少一次 / 恰好一次 ​

投递语义是一个光谱，没有免费的完美：

语义机制代价适用
至少一次消费者处理成功后 ack；失败不 ack 重新投递可能重复消费默认选择（配幂等）
至多一次收到即 ack，不重试可能丢消息可容忍丢失的日志/埋点
恰好一次事务/幂等键去重性能与复杂度最高支付、账务等必须精确

生产实践：至少一次 + 消费幂等。因为「恰好一次」的实现依赖端到端事务，代价极高；更简单的是「至少一次 + 消费端用唯一键去重」：

text
消费端幂等实现：
  ① 消息带全局唯一 id（或业务键：订单号+事件类型）
  ② 消费前查「已处理表」：已存在则跳过（INSERT IGNORE / 唯一索引）
  ③ 处理业务 + 写已处理记录，在同一个事务里 → 原子

6. 死信队列（DLQ） ​

消费失败重试 N 次（如 3 次）后仍失败的消息，进死信队列，人工/定时任务介入排查——避免坏消息无限阻塞队列：

text
消费失败 → 重试队列（延迟 1s/5s/30s）→ 仍失败 → DLQ（死信队列）
                                                    │
                                          ┌─────────┴─────────┐
                                          ▼                   ▼
                                    告警：通知值班人员      人工分析/补偿

DLQ 是「系统自己兜不住」的最终防线，常见死因：下游服务长时间不可用、消息格式与代码不兼容、脏数据。死信也要监控告警——死信堆积是重大事故的早期信号（例如下单事件死信堆积 = 下游正在丢失订单处理）。

常见陷阱 ​

  • 为「快」而异步，忘记顺序：同一实体的多个事件散落到不同分区，消费端状态机乱序错乱；关键事件必须同 key。
  • 只 ack 不幂等：用了「至少一次」却没做幂等，网络重试导致重复发短信、重复加积分。
  • 把 MQ 当数据库：消息无限保留、全量查询历史，MQ 的存储不是为查询设计的。
  • 消费速度跟不上生产：分区数 < 消费者数时扩容无效；监控 lag（积压量）是 MQ 运维的核心指标。
  • 同步调用硬改成 MQ：下游要立刻拿到结果（如查余额），异步会让用户等不到响应；MQ 只适合「可以等」的业务。
  • 死信无人问津：DLQ 没接告警，消息悄悄堆积，业务缺失几小时才发现。

练习建议 ​

  1. 基础：用 Redis Stream 实现一个最小「下单 → 发短信」：生产者投递 order_created，消费者消费并打印，模拟消费失败重试。
  2. 进阶：给消费者加幂等（已处理表 + 唯一键），并用「至少一次」语义模拟重复投递，验证不会重复处理。
  3. 综合：为电商设计订单事件流：order_created → order_paid → order_shipped → order_completed，规定分区键、消费者组划分、各下游（短信/库存/统计）的可靠性要求与 DLQ 处理流程。

用 /practice system-design 消息队列 生成更多针对性练习。

前端对照 ​

前端架构概念系统设计对应
事件总线（mitt / EventEmitter）消息队列（跨服务版事件总线）
Redux 异步 action（dispatch 后不管）异步解耦：投递消息后立即返回

React 事件顺序（冒泡阶段）分区内有序消费
前端防重复提交（幂等按钮）消费幂等（唯一键去重）
