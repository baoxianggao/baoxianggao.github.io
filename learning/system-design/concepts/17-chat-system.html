17 · 聊天系统 ​

前置：16 新闻信息流 · 预计：2.5~3 小时

概念简介 ​

聊天系统（IM，微信/QQ/Slack 类）是「实时性」要求最高的系统：消息要在毫秒级到达对端。核心挑战：长连接管理、消息顺序保证、多设备同步、在线状态、历史消息存储，以及海量连接下的水平扩展。前端的 WebSocket 经验在这里派上大用场——但前端处理的是「一条连接」，后端要管理的是几十万条连接 + 消息的可靠存储与投递。

设计上的关键难点：消息不能丢（至少一次投递）、消息不能乱（会话内顺序）、消息不能重（幂等去重）。这三条分别对应至少一次投递（At-least-once）、序列号机制、客户端消息 ID 去重——任何一个分布式消息系统都绕不开。

核心内容 ​

1. 传输层选型：轮询 vs WebSocket vs SSE ​

方案实时性方向特点适用
短轮询秒级（取决于间隔）单向实现最简单；大量无效请求浪费带宽低实时性通知
长轮询秒级单向服务端挂起请求直到有新消息；兼容老环境老浏览器兼容
SSE秒级服务端→客户端单向自动重连、开销小服务端推送通知
WebSocket毫秒级全双工一条 TCP 长连接双向通信，聊天的事实标准聊天/实时协作

结论：聊天必须 WebSocket（毫秒级双向）。SSE 适合「只有服务端发」的场景（如新消息提醒），前端也常用——两者按需组合。

2. 总体架构 ​

mermaid
graph LR
    C1[客户端 A] -->|WebSocket| G1[连接网关 1]
    C2[客户端 B] -->|WebSocket| G2[连接网关 2]
    G1 --> S[聊天服务集群]
    G2 --> S
    S --> MQ[(消息队列<br>按会话分区)]
    MQ --> W[持久化 Worker]
    W --> DB[(消息存储<br>MySQL 分片)]
    S --> P[(在线状态<br>Redis)]
    G1 -. 跨网关转发 .-> G2

架构分层论证：

  • 连接网关（Gateway）：只管长连接——保活、心跳、协议解析，无状态业务。每个网关维护「连在我这里的用户列表」（内存或本地 Redis），客户端负载均衡（见「05 负载均衡」）随机接入，百万连接 = 数十台网关水平扩展；
  • 聊天服务：业务逻辑——消息校验、路由、在线判断。消息按 conversation_id 投递到消息队列（保证同一会话的投递顺序）；
  • 持久化 Worker：从 MQ 消费写库——把「投递」与「存储」解耦，网关不阻塞在 IO 上；
  • 跨网关转发：A 在网关 1、B 在网关 2——聊天服务通过「在线状态服务」查到 B 所在网关，把消息转发过去，由网关 2 推给 B。

3. 在线状态与心跳 ​

在线状态本质是「最近一次心跳的时间」：

python
import time

HEARTBEAT_TTL = 60   # 心跳 TTL：60 秒内无心跳视为离线

def record_heartbeat(redis_client, user_id):
    """收到心跳：刷新在线时间戳，TTL 过期即自动判定离线"""
    redis_client.set(f"online:{user_id}", str(time.time()), ex=HEARTBEAT_TTL)

def is_online(redis_client, user_id):
    """查在线状态：键存在即在线（Redis TTL 自动清理离线用户）"""
    return redis_client.exists(f"online:{user_id}") == 1

要点：用 Redis 键的 TTL 当「离线判定」——不需要定时任务去扫描谁离线了，TTL 过期自动消失，零清理成本。在线状态变更（上线/下线）通过消息队列广播给好友，好友端更新会话列表的「在线」标记。

4. 消息存储：时间线模型 ​

消息表设计（按会话分片，保证同一会话内数据集中、有序）：

sql
-- 消息表：按 conversation_id 哈希分片
CREATE TABLE message (
    id              BIGINT PRIMARY KEY,     -- 全局消息 ID（发号器生成）
    conversation_id VARCHAR(32) NOT NULL,   -- 会话 ID，分片键
    sender_id       BIGINT NOT NULL,
    client_msg_id   VARCHAR(64) NOT NULL,   -- 客户端生成的消息幂等 ID
    seq             BIGINT NOT NULL,        -- 会话内自增序号（顺序依据）
    content         TEXT NOT NULL,
    created_at      TIMESTAMP DEFAULT NOW(),
    UNIQUE KEY uk_client_msg (sender_id, client_msg_id)  -- 幂等去重约束
);

权衡：全局序号 vs 会话内序号。全局自增 ID（雪花）简单但不能反映会话内顺序；会话内 seq（每个会话一个递增计数）是顺序保证的标准做法——消息按 (conversation_id, seq) 排序即时间线。seq 的生成要防并发：用 Redis INCR（per conversation）或数据库乐观锁。

历史消息拉取：客户端存 last_seq，重连/翻页时拉 seq > last_seq 的消息即可——增量同步天然支持多端。

5. 多设备同步与消息幂等 ​

多设备（手机 + 电脑 + Web）是聊天系统的标配，核心机制：

  1. 增量拉取：每台设备维护自己的 last_seq，上线时从服务端拉增量——设备 A 拉过的消息设备 B 也能拉到，互不干扰；
  2. 已读回执：设备上报「读到 seq=X」，会话页展示「对方已读」；回执可只记录最新的（最终状态），无需历史明细；
  3. 消息幂等：客户端发送时生成 client_msg_id（UUID），服务端按 (sender_id, client_msg_id) 唯一约束去重——网络超时重发、多端重复提交都不会产生两条消息（幂等与重试见「12 幂等与重试」）；
  4. 乱序兜底：即使 MQ 投递乱序，接收端按 seq 排序后再展示，客户端「先收到 seq=5 再收到 seq=4」也按序渲染。

6. 消息投递的可靠性 ​

消息链路（A 发送 → B 收到）的每个环节都要考虑「丢了怎么办」：

text
A 发送 → ①聊天服务接收 → ②MQ 持久化 → ③持久化 Worker 写库 → ④网关投递 → B 确认
  ① 聊天服务宕机：A 超时重发（靠 client_msg_id 去重）
  ② MQ 是持久化边界：消息进入 MQ 即「不会丢」（At-least-once）
  ③ 写库失败：Worker 重试；重试幂等（唯一约束）
  ④ B 离线：网关查在线状态，离线则消息落库，B 上线后增量拉取

要点：MQ 是可靠性的边界——消息进 MQ 之前可能丢（靠客户端重发兜底），进 MQ 之后不会丢（At-least-once + 消费者幂等）。投递是「尽力而为」，可靠性靠「接收端增量拉取」补位：B 没收到在线推送，上线时也会拉到全量增量——在线推送只负责快，增量拉取负责全。

7. 高可用与重连 ​

  • 网关集群：某网关宕机，其上连接的客户端断线——客户端指数退避重连（见「12 幂等与重试」）到其他网关，业务无感；
  • 会话路由：客户端重连后重新注册到新网关，在线状态刷新，好友的转发路由自动更新；
  • Redis/DB 高可用：沿用「10 故障转移与冗余」的主备方案；消息写库异步化后，DB 短暂不可用只会延迟落库，不会丢消息（消息在 MQ 中）。

7. 群聊的特殊性 ​

单聊之外，群聊是聊天系统的另一个主场景，带来三个额外问题：

  1. 群成员列表：群表 + 成员表（group_member(group_id, user_id)），发消息前先查成员列表做投递路由——成员表要支持按群分片，万人大群的消息 fanout 要异步批量投递；
  2. 群消息的收件人：群消息按 (group_id, seq) 存储，每个群成员只维护自己的 last_seq——群消息不复制 N 份（否则 1000 人群 × 每条消息 = 千倍存储），靠「一份存储 + 各自游标」实现增量同步，这是群聊与单聊「收件箱」模型的关键差异；
  3. 已读回执：群聊只显示「已读 X 人」而非逐人状态——已读人数用 Redis 计数器 + 去重集合（SADD），人数统计与消息内容解耦，量大时异步聚合。
python
def send_group_message(group_service, user_id, group_id, content):
    """群消息发送：存储一份 + 广播在线成员（伪代码）"""
    seq = group_service.next_seq(group_id)          # 群内序号
    group_service.save_message(group_id, seq, user_id, content)   # 一份存储
    online_members = presence_service.members_online(group_id)    # 在线成员
    for member_id in online_members:                # 只推在线成员（离线靠增量拉取）
        route_service.deliver(member_id, group_id, seq)

8. 容量估算与扩展 ​

以百万 DAU 聊天系统为例（人均日发 20 条、其中 1/4 是群消息）：

text
消息总量：   100 万 × 20 条 = 2000 万条/天 ≈ 230 条/秒（峰值 ×10 ≈ 2300）
历史存储：   2000 万 × 1KB ≈ 20GB/天 → 年 7TB → 按 conversation 分片 + 归档
连接数：     峰值在线率 30% → 30 万长连接 → 每网关 5 万连接 → 6 台网关
在线状态：   30 万 key × 100B ≈ 30MB Redis → 单实例足够，按用户 ID 分片扩展

估算结论：瓶颈不在消息量而在连接数与状态——网关按连接数水平扩展，在线状态进 Redis，消息存储按会话分片；这三条线互不阻塞，架构自然可扩展。

9. 离线推送（Push 通知） ​

用户离线（App 被杀死）时，消息不能只躺在 DB 里等用户主动打开——要靠系统推送通道（APNs / FCM / 华为推送）唤醒 App：

python
def deliver_offline_push(user_id, message):
    """离线推送：App 不在线时走系统推送通道（伪代码）"""
    if presence_service.is_online(user_id):
        return                               # 在线：走 WebSocket 实时投递
    # 离线：消息已落库（增量拉取兜底），同时发系统推送
    token = push_token_store.get(user_id)    # 该用户设备的推送令牌
    if token is not None:
        push_provider.send(                  # APNs / FCM / 厂商通道
            token=token,
            payload={"conversation_id": ..., "sender": ..., "preview": ...},
        )

设计要点：

  • 推送是「通知」不是「消息体」：推送里只带摘要（谁发的、说了什么的前几个字），用户点开后由 App 走增量拉取拿到完整消息——避免大消息在推送通道丢失；
  • 推送令牌的维护：用户每台设备一个令牌（Token），登录/登出、换机都要更新——令牌失效（用户卸载 App）后推送失败要静默清理，不阻塞主流程；
  • 通道降级：系统推送可能延迟（厂商通道不可控），所以推送永远只是锦上添花——可靠性底线仍是「落库 + 增量拉取」（见「6 消息投递的可靠性」），推送失败不影响消息不丢。

常见陷阱 ​

  • 连接不设心跳：TCP 半开连接（客户端断网但连接不释放）占用网关资源——必须有心跳 + 超时清理。
  • 在线状态用「下线通知」判断：客户端强杀 App 发不出下线通知——必须用「心跳 TTL 过期」判定，下线通知只是加速。
  • 消息顺序靠全局 ID：全局自增 ID 不反映会话内顺序，跨设备/乱序投递时时间线错乱——要用会话内 seq。
  • 重发产生重复消息：客户端超时重发没有去重键——必须有 client_msg_id + 唯一约束。
  • 同步写库阻塞投递：消息先写 DB 再推网关，数据库抖动拖垮实时链路——存储与投递解耦（MQ 异步落库）。
  • 离线消息只靠推送：B 离线期间的推送全部丢失，上线后没有增量拉取补位——推送快、拉取全，两者都要。

练习建议 ​

  1. 基础：写一个 Python 心跳 + 在线状态判定（Redis TTL），验证「无心跳 60 秒自动离线」与「手动下线立即离线」两条路径。
  2. 进阶：实现消息幂等——按 (sender_id, client_msg_id) 唯一约束存库，模拟重复投递验证只落一条；实现增量拉取（seq > last_seq）。
  3. 综合：设计一个「单聊 + 群聊」完整系统：WebSocket 网关集群、会话内 seq、MQ 持久化、多端增量同步、已读回执、在线状态广播，画出架构图并标注每条消息的完整生命周期（发送→确认→落库→推送→回执）。
