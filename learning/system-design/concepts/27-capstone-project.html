27 · 综合实战项目 ​

概念简介 ​

本篇是全系列的综合实战:完整设计一个「百万用户电商平台」——从需求澄清到容量估算、从高层架构图到核心模块深入、从高可用方案到演进路径,把前 26 篇的概念(容量估算、存储选型、缓存、消息队列、限流熔断、分布式事务、一致性协议、微服务、事件驱动、成本优化、设计权衡)全部串成一个可交付的系统设计。它不是「写一篇文档」,而是一次完整的架构师演练:每个阶段都有明确的交付物,交付物连起来就是一份可提交评审的设计文档。

设计约束先立住:假设从 0 到 1,目标 100 万注册用户、日活 20 万、峰值 QPS 5000、99.9% 可用性、P95 延迟 < 300ms。为什么选电商?因为它的模块足够全:强一致需求(库存/余额)、读多写少(商品详情)、高并发瞬间(秒杀)、异步链路(订单通知)、外部依赖(支付/物流)——几乎每个核心权衡都能在此落地。你还会发现它和前端系统的同构:商品详情 ≈ 静态资源上 CDN,购物车 ≈ 客户端状态,订单状态机 ≈ 前端路由状态机,只是规模放大了几个数量级。

分阶段推进方式:阶段 1-3 完成「需求与架构」(全貌),阶段 4-5 深入「核心模块」(细节),阶段 6-7 补「高可用与演进」(纵深)。每阶段末尾标注交付物;全部完成后,这份设计文档就是 L5 考核的项目载体——用它发起 /assess system-design L5,考核会围绕本项目展开答辩。

核心内容 ​

阶段一:需求澄清与约束(交付物:需求与约束文档) ​

设计前先问清楚,否则一切估算都是空中楼阁。本项目的需求基线:

功能需求:
  - 用户:注册/登录(JWT)、个人资料、收货地址
  - 商品:分类、列表、详情、搜索、库存管理
  - 订单:创建(购物车结算)、支付回调、取消、状态查询
  - 营销:优惠券、限时秒杀(可选里程碑)
非功能需求(写进文档,作为后续所有决策的约束):
  - 规模:100 万注册、DAU 20 万、峰值 QPS 5000
  - 可用性:99.9%(年不可用 < 8.8 小时)
  - 延迟:P95 < 300ms(下单链路放宽到 1s)
  - 数据:订单数据至少保存 7 年(合规)
  - 一致性:库存强一致(超卖不可接受),订单最终一致(允许 5s 窗口)

要点:把非功能需求显式化,它们才是后面每个权衡的裁判。比如「库存强一致」直接否掉纯最终一致方案,「P95 < 300ms」决定了商品详情必须走缓存 + CDN。

阶段二:容量估算(交付物:估算表) ​

用 02 篇的方法,把规模翻译成资源需求:

容量估算(基于 DAU 20 万):
  QPS 估算:
    - 商品浏览:DAU 20 万 × 人均 20 次浏览 / 86400s ≈ 46 QPS 均值
    - 峰值系数 5(晚间/大促) → 商品浏览峰值 ≈ 230 QPS
    - 下单:DAU 20 万 × 人均 0.05 单 × 10 次操作 / 86400s ≈ 12 QPS
    - 峰值 → 下单峰值 ≈ 100 QPS(单操作 = 创建订单+扣库存+支付回调)
    - 全站峰值 QPS ≈ 5000(含浏览/搜索/详情/登录等聚合)
  存储估算:
    - 订单:100 万单/年 × 1KB/单 × 7 年 ≈ 7GB(轻松,但索引与查询需分库)
    - 商品快照:1000 万 SKU × 5KB ≈ 50GB(对象存储 + 缓存)
    - 用户:100 万 × 500B ≈ 0.5GB
  带宽估算:
    - 商品详情 200KB × 峰值 1000 QPS ≈ 200MB/s(主站)
    - CDN 承担 90% → 源站带宽需求骤降为 20MB/s(为什么商品详情必须上 CDN)

要点:估算的价值不是数字准确,而是数量级正确(单机、单集群、多集群三个档位),以及它直接决定架构选择:7GB 订单数据 → 单库就够,但 5000 QPS 写入 → 必须分库分表 + 缓存。

分层职责一句话各表:CDN 扛静态流量、网关统一入口与限流、业务服务无状态(可水平扩展)、缓存扛读、分片库扛写、消息队列解耦异步链路、库存独立成服务守护强一致。为什么库存要独立服务:它的写入频率低、一致性要求特殊(可上 TCC/乐观锁),与商品读流量隔离,防止秒杀把商品浏览打挂。

阶段四:核心模块深入 —— 用户与商品(交付物:模块设计文档) ​

用户服务:JWT 无状态认证(网关校验,不查库)、注册防重(唯一索引 + 幂等键)、资料读写低频直接落库。百万用户量级不需要分表,单库主从即可。

数据模型是模块设计的落点,先给核心表定稿(注释为中文):

sql
-- 用户表:单库主从即可,百万量级无需分表
CREATE TABLE users (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  phone       VARCHAR(20) NOT NULL,
  password_hash VARCHAR(100) NOT NULL,
  nickname    VARCHAR(50) DEFAULT '',
  created_at  DATETIME NOT NULL,
  UNIQUE KEY uk_phone (phone)          -- 注册防重的第一道闸
);

-- 订单表:按 user_id 分片(同用户订单聚簇,事务内联查询友好)
-- 分片键选择论证:订单查询 90% 按用户维度 → 分片键 = user_id
CREATE TABLE orders (
  id          BIGINT PRIMARY KEY,
  user_id     BIGINT NOT NULL,
  sku_id      BIGINT NOT NULL,
  amount      DECIMAL(12,2) NOT NULL,
  status      TINYINT NOT NULL COMMENT '0待支付 1已支付 2已发货 3完成 4取消',
  idempotency_key VARCHAR(64) NOT NULL,   -- 下单幂等键
  version     INT NOT NULL DEFAULT 0,     -- 乐观锁(状态机变更防并发)
  created_at  DATETIME NOT NULL,
  UNIQUE KEY uk_idempotency (user_id, idempotency_key)  -- 幂等兜底
) PARTITION BY HASH(user_id) PARTITIONS 16;

商品服务——读多写少的天堂,缓存策略是本模块的核心设计:

商品详情读链路(读多写少 → 三级缓存):
  1. CDN(静态化详情页)        命中率 ~60%   ← 兜底:静态资源
  2. Redis(热点商品 JSON)     命中率 ~35%   ← 兜底:缓存
  3. MySQL(缓存穿透时)         命中率 ~5%
  写路径:后台改价 → 删除/更新缓存 → 异步刷新 CDN
  防穿透:布隆过滤器拦截不存在的商品 ID
  防击穿:缓存重建加互斥锁(只有一个请求去查库)
  防雪崩:缓存过期时间加随机抖动,避免同一时刻大面积失效

阶段五:核心模块深入 —— 订单与消息(交付物:时序图 + 事务方案) ​

订单是分布式事务与状态机的主战场(20 篇实战化):

下单时序(核心链路):
  前端 ──▶ 网关(限流+幂等键校验) ──▶ 订单服务
    1. 订单服务:创建订单(状态:待支付)+ 本地消息表同事务写入
    2. 投递器发送 order.created 事件
    3. 库存服务消费:乐观锁扣减(version 字段,失败则补偿)
    4. 支付服务:支付回调(异步、幂等,按 payment_id 去重)
    5. 订单服务更新状态机:待支付 → 已支付 → 已发货 → 完成
       反向:已支付 → 取消(退款补偿)/ 待支付超时 → 自动取消(定时任务)
  一致性方案:Outbox 本地消息表 + 消费端幂等 + 每日对账任务
  为什么不用 2PC:下单链路 5000 QPS 峰值,2PC 阻塞与协调者单点不可接受
  (用 26 篇的 ADR 格式把这条决策写成文档)

消息服务(23 篇落地):订单事件驱动通知/物流/优惠券;订阅者幂等(事件 ID 去重表);秒杀流量用消息队列削峰(前端秒杀按钮直接返回「已排队」,真正扣减异步完成)。

本地消息表是这条链路的基石,DDL 与投递流程一起定稿(20 篇实战化):

sql
-- outbox 表:与业务表同库同事务写入,是"消息必达"的保证
CREATE TABLE outbox (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  topic      VARCHAR(64) NOT NULL,              -- 如 order.created
  payload    JSON NOT NULL,
  status     TINYINT NOT NULL DEFAULT 0,        -- 0待投递 1已投递 2失败待重试
  retry_count INT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL,
  KEY idx_status (status, created_at)           -- 投递器扫描索引
);

秒杀模块(18 篇综合):前端倒计时 → 网关限流(独立令牌桶池,不挤占普通流量)→ 请求先进 Redis 预扣(原子 DECR,防超卖)→ 落库通过 MQ 异步削峰 → 消费端事务性扣减 + 对账。秒杀与日常下单共用订单服务,但限流池、缓存键、队列分区全部隔离,保证秒杀洪峰不拖垮日常链路。

阶段六:高可用与容灾(交付物:高可用方案文档) ​

层次方案指标/目标
应用层无状态多副本 + 自动扩缩容;熔断/舱壁隔离(13 篇)单实例故障无感
数据层主从 + 半同步;从库故障自动提升;分片故障降级只读RPO ≤ 5s, RTO ≤ 5min
机房同城双活 + 异地备份;DNS 切换单机房故障 10min 内恢复
流量网关全局限流(令牌桶)+ 秒杀独立限流池;降级开关(推荐流、搜索)峰值超限时保护核心下单
幂等下单/支付/库存全部幂等键 + 唯一索引兜底(12 篇)重试不产生重复数据

容灾要点:99.9% 可用性预算拆解——单次故障可用时长大致是「每年 8.8 小时」,这意味着故障恢复速度比「永不故障」更现实:演练主从切换、演练 DNS 切换、演练降级,每次演练记录 RTO 实测值(11 篇)。

配套监控告警设计(14 篇),让高可用可验证而非靠运气:

监控四层与对应告警:
  指标层:QPS/错误率/P95 延迟/缓存命中率/队列积压 → 阈值告警
  日志层:错误日志聚合,异常模式(如库存扣减失败率突增) → 规则告警
  链路层:trace 最慢 span 告警(下单链路 > 1s) → 定位告警
  业务层:对账差异、支付回调积压、退款未处理 → 业务告警(最容易被忽略)
演练计划(每季度):
  Q1 主从切换演练(记录实测 RTO)  Q2 DNS 切机房演练
  Q3 秒杀峰值压测(打满限流阈值)  Q4 全链路故障演练(随机杀服务)

演练原则:先在预发环境演练,再在生产非高峰时段演练;每次演练必须有「故障注入清单 + 恢复脚本 + 复盘报告」三件套,否则演练就是走过场。

阶段七:演进路径(交付物:演进路线图) ​

按 24 篇的「渐进演进」设计,不一步到位:

阶段 A(0-3 月):模块化单体 —— 单仓库单部署,内部按模块划界
  → 明确不写跨模块表访问(为拆分留好地基)
阶段 B(3-9 月):按需拆分 —— 库存独立服务(秒杀需求)+ 商品详情上 CDN
  → 拆分的第一个信号是"扩展失衡"与"秒杀流量隔离"
阶段 C(9-18 月):订单/用户服务化 + 消息队列全面异步化
  → 团队 3 个以上时开始(康威定律)
阶段 D(18 月+):中台化评估 —— 只有多业务线复用需求真实出现才启动
  → 否则停留在阶段 C,继续优化成本与稳定性
每阶段完成定义:性能达标、监控告警齐全、对账任务运行、ADR 齐备

演进原则:每个阶段都能独立交付价值;阶段切换的唯一理由是「当前架构的瓶颈被真实业务验证」,不是规划里的时间表。

演进与成本预算同步做(25 篇),避免「架构升级 = 成本失控」:

成本基线(月度,按 25 篇的三层计费模型):
  稳态负载(预留实例):商品/订单核心服务      ¥18,000
  波动负载(按需):网关/测试环境              ¥6,000
  突发负载(竞价/弹性):秒杀、批处理任务       ¥2,000
  CDN 流量(商品详情占比 90%)               ¥3,000
  合计约 ¥29,000/月;每次架构变更前回答:
  "这层组件省下的资源/稳定性,值不值它的月租?"
  反例:为"统一调度"引入重量级编排平台,月成本 ¥8,000 且无人用 → 砍掉

要点:演进路线图与成本预算绑定评审——阶段 B 拆库存服务的同时必须给出它的预留/按需配比,否则演进计划止步于文档。

常见陷阱 ​

  • 跳阶段直接画微服务图:团队 2 人、日请求几百,就画 8 个服务的架构——答辩时先讲清「为什么现在不该拆」也是设计能力。
  • 容量估算只给数字不给推导:没有 DAU、人均行为的假设,数字就是拍脑袋;评审先看假设,再看结论。
  • 下单链路选 2PC:5000 QPS 峰值下直接阻塞崩盘——必须能论证「为什么 Outbox + 幂等 + 对账」更适合。
  • 商品详情不做 CDN:带宽估算阶段就应发现源站扛不住 200MB/s;上 CDN 后降到 20MB/s,这是数量级的差异。
  • 高可用只写方案不演练:RTO 写在文档里不等于做得到;演练实测值才可信。
  • 幂等只靠业务代码:幂等键必须有唯一索引兜底,代码漏判时数据库还能挡一道。
  • 演进路径等于「微服务路线图」:演进是问题驱动的,不是技术驱动的;路线图里必须写清「什么时候不该演进」。

练习建议 ​

本项目的练习就是交付物本身,按三档递进:

  1. 基础(阶段 1-3):完成需求与约束文档、容量估算表、高层架构图——每份交付物标出对应的概念出处(如「P95 < 300ms 约束 → 07 缓存」「订单 7GB → 08 存储选型」)。
  2. 进阶(阶段 4-5):完成商品三级缓存设计(含防穿透/击穿/雪崩)、订单状态机与 Outbox 事务方案(含时序图与 ADR),并写出「为什么库存用乐观锁而非悲观锁」的权衡论证。
  3. 综合(阶段 6-7 + 答辩):完成高可用方案(容灾/限流/幂等 + 演练计划)与演进路线图;把全部分阶段交付物合并为一份完整设计文档 docs/architecture.md,准备 15 分钟架构答辩(自述 10 分钟 + 质疑 5 分钟)。

用 /practice system-design 综合实战项目 生成针对每个阶段的专项练习。
