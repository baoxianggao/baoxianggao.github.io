08 · 数据库分片 ​

概念简介 ​

分片（Sharding）是把一张大表按某个键拆到多台数据库实例上，让「一台机器装不下的数据」和「一台机器扛不住的 QPS」变成「多台机器分摊」。它是数据库水平扩展的终极手段，也是最昂贵的架构变更——分片一旦落地，SQL 能力全面降级（join、事务、聚合都受限），所以分片永远是「最后手段」。

对前端工程师来说，分片最像组件拆分与代码分割：单文件太大就拆组件、拆 chunk；单库装不下就拆表、拆库。但有一个关键差异：前端拆分后组件间通过 props 通信，而分片后「跨片数据」无法优雅通信——join 要靠应用层做、事务要靠分布式事务做——拆出去的复杂度是后端的十倍。

本章覆盖：垂直 vs 水平拆分、分片键选择（最关键的决策）、range vs hash 分片、全局唯一 ID（雪花算法）、跨分片查询与热点问题。核心心智：分片键决定一切，且几乎不可更改——选错分片键的代价是数据迁移重做。

核心内容 ​

1. 垂直拆分 vs 水平拆分 ​

text
垂直拆分（按业务拆库）：先做这个
  用户库（user 表）│ 订单库（order 表）│ 商品库（product 表）
  → 每库一台机器，独立扩容；join 跨库要用应用层/冗余

水平拆分（按行拆表，即分片）：垂直拆分不够时再做
  订单表 1 亿行，拆成 8 片：
    分片0: order_id 哈希 % 8 == 0 的订单
    分片1: ... == 1
    ...
  → 每片 1250 万行，单机性能回到健康状态

顺序原则：先垂直后水平。垂直拆分简单（只是换库）、收益立竿见影（热库分离）；水平拆分才动分片键与路由，复杂度高一个量级。很多系统「垂直拆完 + 归档冷数据」就够了，根本走不到水平分片。

2. 分片键选择：最关键的决策 ​

分片键是「数据属于哪台机器」的依据，必须同时满足三个特性：

特性要求反例
高基数（cardinality）取值够多，才能散得开按 status 分（只有 3 个值 → 3 台热机器）
均匀分布各片数据量接近按 city 分（北京一片占 40%）
访问亲和业务查询尽量「带上分片键」落在单片按 create_time 分但查询都按 user_id → 全表扫描

典型正例：订单表按 user_id 分片——用户查「我的订单」天然带上 user_id，一次路由单片；写（下单）也按用户均匀散开。反例是按订单 id 分片：查询「某用户订单」时不知道订单在哪个片，只能广播到所有片（扫全库）。

分片键决定后，查询要么带分片键（单片查询，快），要么广播（全片查询，慢）——设计接口时要把「高频查询都做成带分片键的」。

3. Range 分片 vs Hash 分片 ​

维度Range 分片Hash 分片
规则按键区间切（user_id 1-100万 一片）按哈希取模（user_id % 8）
优势范围查询友好、扩片简单（再切一刀）数据天然均匀
劣势热点问题：新数据全写最新区间（尾部热点）扩片要全量 rehash（数据搬迁）
适用时间维度的日志、冷热分层绝大多数业务表
text
Range 的热点问题：按 id 范围分片时，新注册用户 id 递增
  → 所有写操作集中在「最后一个片」→ 尾片打满，其他片空闲

Hash 的扩容问题：user_id % 8 → 扩到 16 片
  → 所有数据归属变化 → 需要全量 rehash + 迁移
  → 解决方案：一致性哈希（只迁移 1/16 的数据）或 虚拟桶

权衡结论：默认选 Hash 分片（均匀性压倒一切）；Range 只用于「写模式天然均匀 + 必须范围查询」的场景（如按日期切日志）。扩容方案要在设计时就想好（预留 2 倍片数、一致性哈希）。

4. 全局唯一 ID：雪花算法 ​

分片后「数据库自增 id」失效（各片自增会撞车），需要全局唯一、趋势递增、无中心的 ID 生成器——**雪花算法（Snowflake）**是事实标准：

text
64 位 long 的结构：
┌────────────┬────────────────┬──────────────┬────────────┐
│ 1 bit      │ 41 bit         │ 10 bit       │ 12 bit     │
│ 符号位(0)  │ 毫秒时间戳      │ 机器 ID      │ 序列号     │
│ (无用)     │ (可用 69 年)    │ (最多 1024 台)│ (每毫秒 4096 个)│
└────────────┴────────────────┴──────────────┴────────────┘

三个属性一次满足：全局唯一（机器 ID + 序列号隔离）、趋势递增（时间戳在前，B+ 树索引友好）、无中心（每台机器本地生成，不依赖发号器服务）。时钟回拨是雪花算法的唯一风险（时间戳倒退会重复），工程上用「回拨等待/自增补偿」处理。

替代方案对比：UUID 全局唯一但无序（B+ 树随机写，索引效率差）；发号器服务（数据库/Redis 取号段）有序但引入中心组件。雪花算法在「唯一 + 有序 + 无中心」三角上最均衡。

5. 跨分片查询与热点问题 ​

text
跨分片查询（广播查询）的三个解法：
  ① 应用层汇总：并发查所有片，内存合并（数据量小时可行）
  ② 二级索引（ES）：分片只存数据，跨片搜索靠 ES 索引
     例：按手机号查用户 → ES 里存「手机号 → user_id」→ 再按 user_id 查片
  ③ 汇总表（宽表）：统计类需求用定时任务聚合到一张汇总表

热点问题：
  大 V 用户（单用户数据量是均值 1000 倍）→ 所在片过热
  解决：① 热点用户单独分片/单独库（超范围治理）
       ② 数据层「分片键 + 后缀」拆分（热点 key 拆成多个子 key）

分片后「牺牲查询灵活性换容量」是设计常态：能用分片键单片查的接口最值钱，广播查询要控制频率（每广播一次 = 打全库一次）。热点治理属于「事后发现、定向处理」——设计时无法预测谁是热点，但要有机制（监控热片 + 拆分手段）。

6. 路由层实现要点（伪代码） ​

分片路由是「一处定义、处处复用」的横切逻辑，必须收敛在数据访问层：

python
# shard_router.py —— 分片路由（数据访问层统一处理，业务代码不感知）
SHARD_COUNT = 8  # 分片数（扩容时改为一致性哈希，见第 3 节）

def shard_of(user_id: int) -> int:
    """分片键 → 分片号：唯一的分片路由入口"""
    return user_id % SHARD_COUNT

def save_order(order: dict) -> None:
    """写订单：按 user_id 定位分片（单片写）"""
    shard = shard_of(order["user_id"])
    db_pool[shard].execute("INSERT INTO orders ...", order)

def get_orders_by_user(user_id: int) -> list[dict]:
    """查用户订单：带分片键 → 单片查询（快）"""
    shard = shard_of(user_id)
    return db_pool[shard].query("SELECT * FROM orders WHERE user_id=?", user_id)

def get_order_by_order_id(order_id: str) -> dict | None:
    """按订单号查（不带分片键）→ 广播查询（慢，要控制频率）"""
    for shard in range(SHARD_COUNT):   # 打全库，N 次查询
        row = db_pool[shard].query("SELECT * FROM orders WHERE order_id=?", order_id)
        if row:
            return row
    return None

实现要点：路由逻辑只允许出现在这一层（DAO/Repository），业务代码永远调「按 user_id 的接口」；新增「按订单号查」这类广播接口要过评审——它是性能债的来源。

常见陷阱 ​

  • 过早分片：数据量没过亿、QPS 没过万就分片——缓存 + 读写分离 + 垂直拆分大概率够用；分片是把简单问题复杂化的最佳方式。
  • 分片键没有「访问亲和」：按订单 id 分片导致「查我的订单」变广播，性能反而不如不分片。
  • 低估扩容代价：Hash 分片没预留余量，扩容要全量 rehash + 双写 + 校验，停机窗口按天算。
  • 分片后还做跨片 join/事务：join 两片数据要应用层合并，跨片事务要分布式事务（见 20 分布式事务）——设计时就要消除这两类需求。
  • 全局 ID 用 UUID：作为主键随机写，B+ 树页分裂频繁，插入性能骤降；用雪花类趋势递增 ID。
  • 忽略路由层：分片路由逻辑散落在业务代码里（每处手写取模），后续换键/扩容全部要改；路由必须收敛在数据访问层（DAO/中间件）。

练习建议 ​

  1. 基础：用代码实现 user_id % 8 的分片路由：8 个模拟库（内存 map），实现「按 user_id 写订单 / 按 user_id 查订单」，验证单片路由。
  2. 进阶：实现雪花 ID 生成器（时间戳 + 机器 ID + 序列号），验证同一毫秒内生成的 ID 唯一且递增；再模拟「按订单 id 查询用户订单」的广播场景，对比两种分片键的查询代价。
  3. 综合：设计一个「用户 + 订单」系统的分片方案：分片键选择（含理由）、ID 生成、跨片查询场景清单（哪些接口是单片查询、哪些是广播、如何用 ES 二级索引替代）、扩容预案（2 倍预分配 or 一致性哈希）。

用 /practice system-design 数据库分片 生成更多针对性练习。

前端对照 ​

前端架构概念系统设计对应
组件拆分（单文件超 400 行就拆）垂直拆分（单库扛不住就拆库）
代码分割（chunk 按路由拆包）水平分片（大表按行拆片）
按「路由」组织代码（页面级 chunk）分片键 = 查询入口（带键单片查）
公共依赖抽包（共享 chunk）跨片公共数据单独成库（字典/配置）
组件通信靠 props（跨层级要 Context）跨片数据靠应用层 join / ES 索引
大列表虚拟滚动（只渲染可视区）分片后广播查询降频（只查必要片）
