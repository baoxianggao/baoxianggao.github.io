26 · 设计权衡与取舍 ​

前置：25 成本与容量优化 · 预计：1.5~2 小时

概念简介 ​

初级工程师问「哪个方案更好」,架构师问「每个方案的代价是什么,我们付得起哪个」——这就是权衡(Tradeoff)思维。系统设计里没有「最佳实践」,只有「特定约束下的合理取舍」:强一致性还是高可用?低延迟还是低成本?架构优雅还是按时交付?本章把架构师最常面对的四组核心权衡讲透,并给出决策方法:如何系统化地比较方案、如何记录决策(ADR)让后人理解,而不是靠「我觉得」。

为什么权衡是架构师的分水岭能力?因为每个架构决策都在赌未来——选 2PC 是赌「事务量不会变大」,选微服务是赌「团队会增长」,选事件溯源是赌「审计价值 > 实现复杂度」。赌输了不可怕,可怕的是不知道自己在赌、赌输了无法回退。权衡思维 = 显式列出代价 + 记录决策理由 + 预留回退路径。

对前端工程师:你每天都在做权衡——用 useState 还是全局 store(状态复杂性 vs 组件内聚)、虚拟 DOM 还是手动操作(性能 vs 可维护性)、引入 UI 组件库还是自研(速度 vs 灵活)。后端架构的权衡只是把同一套思维放到更大尺度:每个权衡的单位从「一个组件」变成「一个子系统」,从「一个版本」变成「三年演进」。学会把权衡「说出来、写下来」,是本次进阶的核心。

核心内容 ​

1. 权衡是架构师的主业 ​

架构决策的通用框架:列出每个方案的收益、代价、风险、失效条件,再做决策:

决策模板:
  问题:下单后库存一致性能否最终一致?
  候选 A:2PC(强一致)
    收益:瞬时一致,无对账成本
    代价:阻塞、协调者单点、事务量受限于锁
    风险:高并发下吞吐腰斩
  候选 B:可靠消息(最终一致)
    收益:高吞吐、无锁
    代价:需要补偿与对账
    风险:不一致窗口期内的业务误判(需产品确认)
  决策:选 B,不一致窗口 < 5 秒,对账任务兜底

判断标准不是「哪个更先进」,而是「哪个失败的代价更小、更容易回退」。

2. 一致性 vs 可用性 ​

20/21 篇已经埋下伏笔,这里上升到决策层:一致性是「大家看到的是不是同一个事实」,可用性是「系统是不是一直能用」。核心场景:网络分区(必然发生)时,你牺牲哪个?

场景选 CP选 AP理由
账户余额✓宁可不可用,不能算错账
商品库存✓宁可短暂超卖,不能拒绝下单
分布式锁✓双主执行是灾难
点赞数/浏览数✓丢了可以重算

决策要点:按数据分类做选择,而不是全系统一个策略——订单库 CP,热点统计 AP,「一致性等级」本身就是设计参数。同样重要的是把不一致窗口的业务后果量化:超卖 0.1% 的赔偿 vs 拒绝 1% 请求的流失,哪个贵选哪个。

3. 延迟 vs 成本 ​

低延迟通常等于多花钱:缓存层(内存贵)、多副本(3 副本 vs 2 副本)、全球节点(边缘计算)、预留容量(闲置等待)。决策的核心是给延迟定价:

延迟定价法:
  每秒 1ms 的延迟 = 收入影响?转化率下降 0.5%?
  → 转化率 × 客单价 × 日单量 = 延迟的年化损失
  → 与缓存/扩容的年成本对比,即可量化"该不该加层"
text
示例:日单 10 万,客单价 ¥100,延迟每 +1s 转化率 -1%
  → 年损失 ≈ 10万 × 1% × 100 × 365 ≈ ¥3,650 万
  → 花 ¥200 万/年把 P95 从 1s 降到 200ms,ROI 极高
  → 但若是内部工具(无转化概念),200ms 已足够,别多花一分

决策要点:延迟优化服务于业务指标,不是服务于架构师的自尊——「响应时间好看」不是付费理由,「转化率提升」才是。

4. 简单 vs 灵活 ​

  • 简单:最少组件、最直白的实现,好理解、好维护、好排障;
  • 灵活:可配置、可扩展、可插拔,能适应未来,但每个抽象都是一层复杂度与一处可能的坑。
python
# 反例:为了"灵活"给用户表预留 20 个 NULL 字段(柔性表)
user: {name, avatar, ext1, ext2, ext3, ...}   # 谁都能加,谁都不知道含义

# 正例:简单优先,需要时再演进
user: {name, avatar}
# 未来需要年龄 → 加 age 字段(数据库加列成本极低)
# 未来需要多态属性 → 才考虑 EAV/JSONB

YAGNI 原则:不为「未来可能」做设计,为「今天确定」做设计——因为 90% 的「未来可能」永远不会来,而它带来的抽象复杂度是确定的。灵活性的正确来源不是预先抽象,而是演进能力(24 篇:好拆、好合、能重构)。

5. 工程师时间 vs 架构优雅 ​

最容易被忽略的权衡:架构师的「理想架构」消耗的是工程师的「真实时间」。优雅的代价是学习成本、实现时间、上线风险;粗糙的代价是后期重构成本。决策公式:

优化决策 = 优雅收益(未来节省) vs 实现成本(现在多花)
  现在的 100 人天重构,若未来 2 年能省 200 人天 → 值得
  现在的 50 人天,若未来省 30 人天 → 不值得,先按简单的来

关键认知:技术债不等于坏决策——明知道是权宜之计、记了账(ADR)、排了偿还计划,它就是「战略性的技术债」,是合理的工程决策;没记账的债务才是灾难(24 篇)。

6. 架构决策记录(ADR) ​

ADR 是把权衡「写下来」的工程实践——一条决策、一份背景、几项候选、一个结论、代价与回退方案:

markdown
# ADR-007:订单库存一致性采用可靠消息方案

## 状态
已接受(2026-08-01)

## 背景
下单需跨订单/库存/支付三个服务;高并发下 2PC 吞吐不足。

## 决策
订单与消息同库同事务(Outbox),异步投递,消费者幂等。

## 后果(代价)
- 正:吞吐高、无锁、无协调者单点
- 负:不一致窗口 ≤ 5 秒;需对账任务;需培训团队理解最终一致
- 回退:若业务要求瞬时一致,可升级为 TCC(库存侧已有冻结字段)

## 替代方案
- 2PC:拒绝,吞吐瓶颈 + 协调者单点(详见会议 2026-07-28)
- TCC:暂缓,预留冻结字段,库存侧先上 Outbox

ADR 的三种用途:决策当时强制你想清代价;新人接手时 3 分钟理解「为什么这样」;架构评审时是「推翻它」还是「尊重它」的依据。没有 ADR 的架构决策,三个月后就是「历史遗留问题」。

常见陷阱 ​

  • 用「最佳实践」替代权衡:没有「最佳」,只有「最合适」;把别人的选型当自己的答案,等于放弃思考。
  • 只列收益不列代价:答辩时只说方案 A 多好,不说它付了什么代价——评委一句话就戳穿。
  • 决策不记录:三个月后没人记得为什么选它,重构时反复推翻重来,团队为「失忆」付持续成本。
  • 过度设计(为未来做抽象):为「可能」的多态、扩展、配置写三层抽象,业务半年不动,抽象成为负担。
  • 优化不存在的瓶颈:为 P99 的 10ms 重构架构,而真正的瓶颈是慢 SQL——先测量再优化。
  • 把回退当失败:有回退方案且能快速回退,说明决策是好的;不能回退的决策才是危险决策。

练习建议 ​

  1. 基础:用「决策模板」(问题/候选/收益/代价/风险/决策)对比两个方案——如「短链系统用发号器还是哈希」,输出一份对比表。
  2. 进阶:为你熟悉的一个系统写一份完整 ADR:背景、候选方案(至少 2 个)、决策、后果、回退方案,并给一个「推翻它」的论证。
  3. 综合:举办一次「架构评审答辩」:准备 3 个方案(如订单一致性:2PC/TCC/Outbox),从一致性、延迟、成本、团队维护能力四个维度打分,给出最终决策与 ADR——这正是 /assess system-design L5 的考核形态。

用 /practice system-design 设计权衡与取舍 生成更多针对性练习。
