题目 1 · 需求澄清：把模糊需求变成清单（对应概念 01） ​

难度：基础

题目：产品经理丢给你一句话需求——「帮我做个短链系统」。请用四步法的第一步（需求澄清），输出一份可以直接拿去评审的澄清结果。

要求：

  • 至少问出 7 个澄清问题，并说明每个问题「想探明什么」（参考概念 01 的提问清单）
  • 输出功能需求清单（3 条）与非功能需求清单（至少 4 条，必须量化）
  • 明确写出「本次不做」的边界（至少 2 条）
  • 对「重定向用 301 还是 302」给出选择并说明理由

提示：前端锚点——这就是需求评审会：先问清楚「做什么、不做什么、做成什么样」，再谈技术选型。跳过这步直接画架构图 = 前端先写代码再补需求。

参考答案

一、澄清问题清单（7 个） ​

问题想探明什么假设答案（用于后续设计）
读多还是写多？比例多少？决定缓存方向、读写分离是否值得读多写少，读写比约 1000:1
实时性要求？数据多久可见？决定同步调用还是异步生成后立即可用；点击统计允许分钟级延迟
一致性要求多强？决定存储选型与架构复杂度短链映射强一致；统计最终一致
目标用户量级？峰值是平时几倍？决定是否要分布式DAU 100 万，峰值约为均值 4 倍
可用性几个 9？能接受挂多久？决定冗余、容灾、降级方案99.9%（年停机约 8.8 小时）
数据量多大、保留多久？决定存储成本与冷热分层短链保留 1 年，过期可归档
有哪些硬约束？排除不现实的方案只能用团队已熟悉的 MySQL + Redis

二、功能需求（做这些） ​

  1. 生成短链：传入长 URL，返回 8 位短码（如 t.cn/abc12ab）
  2. 重定向：访问短码，跳转到原始 URL
  3. 点击统计：记录每次点击的时间、来源、UA，可查询某个短链的总点击量

三、非功能需求（做成什么样——量化） ​

维度指标
性能重定向 P99 < 100 ms；生成接口 P99 < 200 ms
量级读 QPS 峰值 3000；写 QPS 峰值约 10
可用性99.9%（年停机 ≤ 8.8 小时）
一致性短链映射强一致；统计最终一致（允许 1 分钟延迟）
存储短链映射保留 1 年，之后归档冷存储
成本机器预算 ≤ 10 台 4 核 8G

四、明确不做（边界） ​

  1. 不做短链内容安全审核（恶意网址识别）——依赖第三方安全接口，本期只做跳转
  2. 不做自定义短码 / 短链有效期自定义——MVP 只支持系统生成的固定短码
  3. 不做用户账号体系与后台管理页面——只提供 OpenAPI

五、关键决策：重定向用 301 还是 302 ​

选 302（临时重定向），理由：

  • 301 会被浏览器永久缓存，后续访问不再回源 → 点击统计严重失真，而统计是本系统的核心功能之一
  • 302 每次回源，统计准确；代价是多一次往返 + 源站压力更大
  • 我们的读 QPS 峰值只有 3000（见题目 2 的估算），完全扛得住 302 的回源压力

这就是「业务决策先于技术决策」：如果需求是「内部一次性跳转、不关心统计」，那就选 301，因为省带宽又省机器。

评分要点（共 10 分，≥7 分合格） ​

  • [ ] 2 分：澄清问题 ≥ 7 个，且每个都说明了「想探明什么」（只列问题不给理由扣 1 分）
  • [ ] 2 分：功能需求与非功能需求分开列，非功能需求有量化数字（QPS / 可用性 / 延迟）
  • [ ] 2 分：明确写出「本次不做」的边界
  • [ ] 2 分：301 vs 302 给出结论 + 理由，且理由与「是否要统计」挂钩
  • [ ] 1 分：有读多写少的判断（决定缓存方向）
  • [ ] 1 分：有一致性分级（映射强一致、统计最终一致）
  • [ ] 扣分项：一上来就选组件（「用 Redis 做缓存」）却没回答清楚需求 → 直接扣 3 分

题目 2 · 容量估算：100 万 DAU 的短链系统（对应概念 02） ​

难度：基础

题目：基于题目 1 的需求，完整估算这个短链系统的三个维度：读 QPS、写入 QPS、1 年存储量、出口带宽。

已知假设：

  • 日活用户 DAU = 100 万
  • 每个用户日均访问（点击）短链 20 次
  • 每天新增短链 10 万条
  • 峰值系数取 4（早晚高峰）
  • 单次重定向响应约 2 KB（302 + 响应头）

要求：

  • 每一步都要写出算式和中间结果，不能直接给结论
  • 给出「日均 QPS → 峰值 QPS → 设计目标（含安全余量）」的完整链路
  • 存储估算要给出行大小的字段级拆解
  • 最后根据量级结论，判断「需不需要 Kafka / 分库分表」

提示：前端锚点——这就是「性能预算」：先算出数据量级，再决定用不用虚拟滚动。100 行和 100 万行的方案完全不同，QPS 100 和 QPS 10 万同理。

参考答案

1. 读 QPS（重定向是主读路径） ​

text
步骤 1：日总请求量 = DAU × 人均次数
        = 100 万 × 20 = 2000 万次/天

步骤 2：日均 QPS = 日总请求量 / 86400 秒
        = 2000 万 / 86400 ≈ 231 QPS

步骤 3：峰值 QPS = 日均 QPS × 峰值系数
        = 231 × 4 ≈ 924 → 取整约 1000 QPS

步骤 4：安全余量（活动、爬虫、突发）取 2~3 倍
        设计目标 = 1000 × 3 ≈ 3000 QPS

2. 写 QPS（生成短链） ​

text
日均写 QPS = 10 万条 / 86400 ≈ 1.16 QPS
峰值写 QPS = 1.16 × 4 ≈ 5 QPS
设计目标（含 3 倍余量）≈ 15 QPS

→ 读写比约 1000:1，典型的读多写少系统

3. 存储量（1 年） ​

先拆行大小（高估比低估好，漏掉索引是最常见的错误）：

text
短链映射表行大小：
  id          BIGINT        8 B
  code        VARCHAR(8)   10 B（8 字符，utf8mb4 下按实际算）
  url         VARCHAR(255) 200 B（按平均长度估，最长 1020 B）
  user_id     BIGINT        8 B
  created_at  DATETIME      5 B
  expired_at  DATETIME      5 B
  ─────────────────────────────
  业务字段合计             236 B
  加索引与填充因子（×1.6）→ 约 400 B

行数 = 10 万条/天 × 365 天 × 保留 1 年 = 3650 万行

存储 = 3650 万 × 400 B = 146 亿字节 ≈ 14.6 GB

4. 出口带宽 ​

text
单次响应 ≈ 2 KB
读 QPS 设计目标 = 3000

带宽 = 3000 × 2 KB × 8 bit = 48000 Kbps = 48 Mbps
加 3 倍余量（写入、页面资源、统计上报）→ 约 150 Mbps

→ 单台 1 Gbps 网卡绰绰有余，不需要 CDN 扛重定向流量

5. 量级结论与架构判断 ​

维度量级是否超出单机能力结论
读 QPS3000否（MySQL 主从读 5000~1 万、Redis 5~10 万）缓存 + 主从即可
写 QPS15否（MySQL 写 1000）单库写入
存储15 GB / 年否（单机 SSD 可放 TB 级）不分片
带宽150 Mbps否（千兆网卡 1 Gbps）不上 CDN

结论：这个系统不需要 Kafka、不需要分库分表、不需要 CDN。 单机/小规模集群 + 一层 Redis 缓存就够了。估算的价值就在于此——它拦住了过度设计。如果算出来是 10 万 QPS，才需要缓存集群 + 多副本 + 分片。

评分要点（共 10 分，≥7 分合格） ​

  • [ ] 2 分：读 QPS 推导完整（日总量 → 日均 → 峰值 → 含余量的设计目标）
  • [ ] 1 分：写 QPS 单独算了，并得出读写比
  • [ ] 3 分：存储有字段级行大小拆解，且考虑了索引/填充因子（只写「一行 400B」无拆解扣 2 分）
  • [ ] 2 分：带宽算了，且公式是 QPS × 响应大小 × 8
  • [ ] 2 分：给出量级结论，明确回答「要不要 Kafka / 分片 / CDN」
  • [ ] 加分：标注了假设来源（峰值系数 4、人均 20 次都是假设，不是事实）
  • [ ] 扣分项：算出 231.48 QPS 这种假装精确的数字 → 扣 1 分（量级对即可）

题目 3 · 从峰值 QPS 到机器数（对应概念 02） ​

难度：进阶

题目：沿用题目 2 的结论——峰值读 QPS 3000，单机（4 核 8G）压测实测能扛 800 QPS，平均响应时间 50 ms。请回答：

  1. 需要几台机器？写出计算过程。
  2. 数据库连接池 / Web 服务器线程数应该配多大？
  3. 有人提议「按峰值 2 倍预留，直接上 10 台」，你同意吗？为什么？

要求：

  • 机器数计算要体现 N+1 冗余原则
  • 并发数用 并发数 = QPS × 平均响应时间 推导
  • 第 3 问要给出「可扩展架构 vs 多买机器」的权衡结论

提示：前端锚点——就像「首屏预算 2.5s」要拆成 DNS/连接/下载各多少毫秒；QPS 是吞吐，并发数是在途请求数，两者靠响应时间换算。

参考答案

1. 机器数 ​

text
已知：
  峰值 QPS      = 3000
  单机容量      = 800 QPS（实测值，来自压测而非拍脑袋）

步骤 1：满足峰值所需台数 = ceil(3000 / 800) = ceil(3.75) = 4 台

步骤 2：N+1 冗余（挂 1 台仍能扛住峰值）
        4 台时挂 1 台剩 3 台 → 3 × 800 = 2400 < 3000，扛不住
        所以再加 1 台冗余：4 + 1 = 5 台
        验证：5 台挂 1 台剩 4 台 → 4 × 800 = 3200 ≥ 3000 ✅

结论：5 台（4 台扛量 + 1 台冗余）

2. 连接池 / 线程数 ​

text
并发数 = QPS × 平均响应时间
       = 3000 × 0.05 秒 = 150 个在途请求

含义：任意时刻最多约 150 个请求同时在飞
→ Web 服务器线程池、数据库连接池按 150 上下配置（再加 30% 余量 ≈ 200）即可

关键洞察：QPS 高不一定并发高。
  若响应时间从 50ms 恶化到 500ms：
  并发数 = 3000 × 0.5 = 1500 → 连接池瞬间打满，请求排队 → 雪崩
  → 这才是「接口变慢会导致整个服务不可用」的量化解释

3. 是否要直接上 10 台？ ​

不同意。 理由：

text
① 成本：机器数是真金白银，按 2 倍峰值预留 = 常年空转一半机器

② 估算本身是假设：DAU 100 万、人均 20 次、峰值系数 4 全是猜的。
   真实数据出来后，可能发现峰值只有 1500 QPS（那 10 台就浪费了 5 台）
   也可能发现是 6000 QPS（那 10 台也不够）

③ 正确的做法：架构上保证「随时能加机器」，而不是现在就买满
   - 应用层无状态（session 外置到 Redis）→ 可水平扩展
   - 前面挂负载均衡 → 加机器只需改 upstream 配置
   - 监控 QPS 逼近 4 × 800 = 3200 时触发扩容告警

结论：先上 5 台，把「水平扩展能力」和「扩容告警」做扎实。估算驱动的是「可扩展的架构」，不是「买够的机器」。

评分要点（共 10 分，≥7 分合格） ​

  • [ ] 3 分：机器数算对（5 台），且体现了 ceil(峰值/单机容量) + 冗余 的公式
  • [ ] 2 分：验证了「挂 1 台仍扛得住」（N+1 的真正含义，不是简单 +1）
  • [ ] 3 分：并发数用 QPS × RT 算对（150），并说明它决定连接池/线程数
  • [ ] 2 分：第 3 问给出明确立场 + 「用可扩展性代替过量采购」的论证
  • [ ] 加分：指出「RT 恶化 10 倍 → 并发数涨 10 倍 → 连接池打满 → 雪崩」的连锁反应
  • [ ] 扣分项：单机容量用「网上查的经验值」而不是压测值 → 扣 1 分

题目 4 · REST API 契约设计（对应概念 03） ​

难度：基础

题目：为「短链系统」设计对外 API 契约。需要覆盖：创建短链、查询短链信息、查询点击统计、删除短链、列出我的短链。

要求：

  • 遵循 REST 资源语义（URI 里不放动词）
  • 统一分页格式（说明选 offset 还是 cursor，为什么）
  • 统一错误响应格式（列出会用到的状态码与 body 结构）
  • 说明版本化策略，并给出 3 条向后兼容原则

提示：前端锚点——你在项目里封装的 api/ 目录（axios + service 层 + 类型定义）就是契约的消费端；本题设计的是契约的生产端。改接口 = 前后端联调成本。

参考答案

1. 资源与接口设计 ​

text
POST   /api/v1/links                     创建短链
GET    /api/v1/links/{code}              查询单个短链信息
DELETE /api/v1/links/{code}              删除短链
GET    /api/v1/links?page=2&page_size=20 列出我的短链（分页）
GET    /api/v1/links/{code}/stats?range=7d  查询点击统计

错误示范（URI 里出现动词/语义重复）：
  GET  /api/getLink?code=abc      ← 动词进 URI
  POST /api/links/createLink      ← 语义重复
  POST /api/links/getStats        ← 用 POST 表达查询

请求体示例：

json
// POST /api/v1/links
{ "url": "https://example.com/very/long/path", "expire_days": 365 }

// 201 响应
{
  "code": "abc12ab",
  "short_url": "https://t.cn/abc12ab",
  "origin_url": "https://example.com/very/long/path",
  "created_at": "2026-08-30T10:00:00Z",
  "expired_at": "2027-08-30T10:00:00Z"
}

2. 分页：选 offset 还是 cursor？ ​

列表接口用 offset（page + page_size），统计明细接口用 cursor。理由：

方案适用本系统场景
offset深翻页不频繁、需要跳页「我的短链」列表：数据量小（人均几十条），运营要跳页 → 选它
cursor高并发信息流、深翻页点击统计流水：数据量大、只往后翻 → next_cursor

统一约定：

text
请求：page（从 1 开始）、page_size（默认 20，最大 100）
响应：items[] + has_more（布尔）
      不返回 total —— 精确 count 在大数据量下代价极高，列表页通常不需要总量

3. 错误契约（统一信封） ​

json
{
  "error": {
    "code": "INVALID_URL",           // 机器可读，前端 error handler 依赖它
    "message": "URL 格式不合法",      // 人类可读，可直接展示
    "request_id": "req_8f3d2a"       // 排查用的链路 ID
  }
}

状态码约定：

状态码语义场景
400参数错误URL 格式不合法、缺必填字段
401未认证未带 Token
403无权限删除别人的短链
404不存在短码不存在
409冲突自定义短码重复
429限流创建频率超限（带 Retry-After 头）
500/503服务端错误数据库不可用

4. 版本化与兼容 ​

选路径版本 /api/v1：最直观、成本最低，且短链系统没有「URL 不能动」的强约束（不像某些 CDN 缓存键敏感的场景）。

向后兼容四原则：

  1. 只加字段，不删字段、不改字段语义（前端没升级也能跑）
  2. 新增可选字段必须有合理默认值（旧客户端拿不到时用默认值）
  3. 不改错误码语义（前端 error handler 写死在某个 code 上）
  4. 旧版本保留期写进契约（v1 保留 6 个月，提前 3 个月公告）

评分要点（共 10 分，≥7 分合格） ​

  • [ ] 2 分：URI 全是名词，无动词、无语义重复
  • [ ] 2 分：HTTP 方法用对（创建 POST、整体更新 PUT、部分更新 PATCH、删除 DELETE）
  • [ ] 2 分：分页有明确选型，且说明了理由（offset 适合跳页、cursor 适合深翻页）
  • [ ] 2 分：错误格式统一（code 机器可读 + message 人类可读），状态码覆盖 400/401/403/404/429
  • [ ] 1 分：给出了版本化策略
  • [ ] 1 分：列出 ≥ 3 条向后兼容原则
  • [ ] 加分：指出「不要在列表响应里返回 total」
  • [ ] 扣分项：错误响应里只有 {message} 没有机器可读的 code → 扣 1 分

题目 5 · 数据流图与延迟预算（对应概念 03） ​

难度：进阶

  2. 假设「点击统计」改为同步调用（在返回 302 前先上报统计），重新计算延迟

要求：

  • 延迟预算要给出分段明细表
  • 第 3 问要从「延迟」和「可用性」两个角度论证

提示：前端锚点——这就是首屏性能优化的「关键路径分析」：把端到端延迟拆成 DNS/连接/下载各多少毫秒，找出可以并行化或异步化的点。

  • 统计路径异步化（不进主链路，统计服务挂了也不影响跳转）

2. 延迟预算表 ​

方案 A：统计异步（推荐）

text
| 阶段                | 延迟    | 说明                          |
|--------------------|---------|-------------------------------|
| DNS 解析            | 5 ms    | 有缓存时更短                  |
| 网络往返（边缘→机房）| 15 ms   | 同城/同省                     |
| 负载均衡转发        | 2 ms    | L7 解析开销                   |
| 缓存查询（命中 95%）| 2 ms    | Redis 单次往返                |
| 业务逻辑 + 序列化    | 20 ms   | 应用处理                      |
| 返回 302            | 15 ms   | 网络往返                      |
|--------------------|---------|-------------------------------|
| 合计                | ≈ 59 ms | 目标 P99 < 100 ms，余量充足   |

加权后未命中路径：59 + (10 - 2) = 67 ms（额外回源 8 ms），仍达标

方案 B：统计改成同步调用

text
主路径 = 59 ms + 统计服务调用 50 ms = 109 ms

结果：
  ① 延迟：109 ms > 100 ms 的 P99 目标 → 超标
  ② 可用性：统计服务故障时，重定向**整个不可用** → 级联故障
     原本「统计挂了只是少几条数据」，现在变成「短链打不开」
  ③ 放大效应：统计服务 RT 抖动 ±30 ms，主路径 P99 直接跟着抖

3. 结论：统计走异步 ​

text
理由一（延迟）：同步会把 P99 从 59 ms 推到 109 ms，直接违背 SLO

理由二（可用性）：附属功能同步阻塞主路径 = 把统计的可用性绑到核心链路
                → 一个非核心服务能把整个系统拖垮（级联故障）

理由三（收益不对称）：统计晚 1 分钟没人关心，短链打不开所有人都关心

实现方式：
  重定向服务把点击事件投递到消息队列（或先写本地日志再批量上报）
  → 用户感知延迟回到 59 ms，统计服务可独立扩容、可短暂故障

通用原则：关键路径上只保留「用户必须等待」的操作，其余全部异步化或并行化。

3. 为什么必须单一写入者 ​

text
反例：多个服务各自 UPDATE orders SET status = 'xxx'

事故场景：
  ① 用户申请退款，退款服务把订单改成「已退款」
  ② 仓储系统没收到事件，仍按「已支付」发货
  ③ 结果：钱退了、货也发了 → 资损

根因：状态迁移没有唯一入口，各服务都可以裸改数据库，
      谁也不知道别人改了什么、改到哪一步。

正确做法：

  1. 单写者：只有「订单服务」能改订单状态，其他服务只能通过 API / 事件请求迁移
  2. 迁移入口收敛：一个方法（如 OrderStateMachine.transition(orderId, action, operator)）里做校验 + 改状态 + 记审计日志
  3. 审计日志：每次迁移记下「谁在什么时候、从什么状态、因什么动作、改成什么状态」
  4. 数据库兜底：用乐观锁（UPDATE ... WHERE status = '待支付'），让并发的非法迁移影响行数为 0

2. 同步延迟为什么可接受 ​

text
链路：MySQL → 消息队列 → ES / ClickHouse
延迟：正常 < 1 秒，抖动时 < 1 分钟

分场景论证：
  ① ES 搜索（客服后台）：客服查的是「用户刚刚咨询的订单」，
     通常已下单几分钟以上 → 秒级延迟无感
     兜底：搜索结果页提示「数据可能有秒级延迟」，并提供「按订单号精确查」按钮走 MySQL

  ② ClickHouse 报表（财务）：看的是「昨日/上月的 GMV」，
     T+1 甚至 T+1 小时都够用 → 分钟级延迟完全 OK

  ③ Redis 缓存（C 端详情）：读的是自己刚下的单，需要**强一致** →
     解法：写库后同步删缓存（Cache-Aside），下次读回源拿最新值
     → 只有「强一致」场景才需要额外手段，其余接受最终一致

原则：能用最终一致就别硬上强一致。为了「搜索结果晚 1 秒」而引入分布式事务，是把简单问题复杂化。

为什么不能把统计报表跑在业务库：

text
① 行存聚合慢：5000 万行 GROUP BY 在 MySQL 上要几十秒甚至几分钟
② 拖垮业务：大查询占满 IO 和连接，下单接口跟着变慢 → 生产事故
③ 锁与长事务：报表查询可能锁表，阻塞正常写入
→ 分析型负载必须与事务型负载隔离（OLAP 与 OLTP 分离）

2. 容量估算（复用题目 2、3） ​

text
读：日均 231 QPS → 峰值约 1000 → 设计目标 3000（3 倍余量）

3. 高层设计 ​

text

   用户 ──► DNS ──►│  负载均衡     │
                  └──────┬───────┘
                         │

         ▼               ▼                ▼

  │（生成，写） │  │（302，读）  │  │（异步消费）   │
  └──────┬─────┘  └──────┬─────┘  └───────┬──────┘

  └────────────┘ └────────┘ └────────┘  └──────────┘

三条路径：

  • 写路径：短链服务 → 发号器取 ID → 转 62 进制短码 → 写 MySQL → 删/写缓存

  • 统计路径：重定向后投递点击事件到 MQ → 统计服务消费 → 聚合入库

4. 深入设计：4 个关键决策 ​

决策点方案 A方案 B权衡结论与代价
短链 ID 生成MD5 哈希截取前 8 位发号器（雪花 ID）转 62 进制选 B。哈希有碰撞概率（要额外判重 + 重试），且长度不可控；发号器简单、无碰撞、趋势递增。代价：需要维护发号器的机器 ID，且短码是「递增可猜测」的（不安全的场景要加随机盐）
重定向码301（永久）302（临时）选 302。301 会被浏览器缓存，统计严重失真；302 统计准确。代价：多一次回源，读压力大 3 倍——但我们的量级只有 3000 QPS，扛得住
存储MySQL 单表分库分表选单表。1 年 3650 万行 × 400 B ≈ 15 GB，单机 SSD 完全放得下；code 建唯一索引即可。代价：未来若涨到 10 亿行需要迁移——但那时业务形态可能都变了，不为假想的未来买单
缓存本地缓存（进程内）Redis 集中缓存选 Redis。多实例本地缓存会互相不一致（用户 A 访问实例 1 命中、实例 2 未命中，行为不一致）；Redis 全局一份。代价：多一次网络往返（约 1~2 ms）+ 多维护一个组件
统计上报同步 RPC异步 MQ选异步 MQ。同步会把 P99 从 59 ms 推到 109 ms 且引入级联故障。代价：统计延迟 1 分钟（可接受），且要处理 MQ 积压与消息丢失

5. 异常场景与降级 ​

text
① 缓存雪崩（大批 key 同时过期）
   预防：TTL 加随机值（基础 1 天 + 随机 0~6 小时），避免集中过期
   兜底：Redis 宕机时走本地缓存（旧数据）；都没有则限流，返回 503 而不是打垮 DB

② Redis 整体宕机
   降级：读路径直连 MySQL（QPS 3000 对 MySQL 主从是可承受的，只是延迟从 2ms 升到 10ms）
   熔断：MySQL 压力超过阈值时限流，保护数据库不被冲垮
   注意：不要让「缓存挂了 = 服务挂了」，缓存是加速件不是必需品

③ 消息队列积压
   监控：消费 lag（积压量）是核心指标，lag 持续增长就要扩容消费者
   降级：统计服务停掉不影响主链路（本来就是异步的）→ 优先保重定向
   兜底：MQ 不可用时，点击日志先写本地文件，恢复后补传

④ 数据库宕机
   主从切换（秒级）；切换期间读路径可返回缓存里的旧值
   写入降级：返回「服务暂时不可用」，绝不静默丢弃用户的创建请求

难度：综合

题目：某接口（返回用户订单列表）P99 从 50 ms 涨到 2 s，P50 只从 20 ms 涨到 30 ms，QPS 和机器数都没变，最近一次发版是 3 天前。请给出排查思路（不是猜原因）。

要求：

  • 先用「延迟预算 + 关键路径」的方法拆解：列出这个接口经过的每一段，以及如何逐段测量
  • 解释「P99 涨、P50 几乎没涨」这个现象说明什么（这是本题的关键线索）
  • 给出排查顺序（先看什么、后看什么，以及每一步能排除什么）
  • 列出 5 个候选根因，并说明各自对应的验证方法（不能只列名词）

提示：前端锚点——这就是线上「某个页面突然变卡」的排查：先看是个别用户还是所有人、是网络还是渲染、是新代码还是数据量增长，而不是上来就加 React.memo。

参考答案

1. 延迟预算拆解：这个接口经过哪些段 ​

text
用户 → DNS/CDN → 负载均衡 → 应用服务 → [本地缓存?] → Redis → MySQL
                                    └─→ 下游服务（商品/用户服务）?

测量手段（按「能否直接拿到数据」排序）：
  ① 应用侧埋点（最快）：把接口内部拆成 4 段打点
     - 请求解析 + 参数校验
     - Redis 查询（耗时、命中率）
     - MySQL 查询（耗时、返回行数）
     - 下游 RPC 调用（耗时、成功率）
     → 输出 P50/P95/P99 分位，直接定位到段

  ② 链路追踪（Trace）：随机采样看几条慢请求的完整火焰图，
     一眼看出时间花在哪一段

  ③ 分段对比：拿「慢请求」和「快请求」的参数做对比
     （是不是某些用户/某些筛选条件特别慢 → 数据倾斜）

2. 关键线索：P99 涨、P50 几乎没涨 ​

text
P50：20 ms → 30 ms（+50%）
P99：50 ms → 2000 ms（+3900%）

这说明：绝大多数请求是正常的，只有 1% 的请求极慢
→ 排除「系统性整体变慢」的因素：
  ❌ 不是机器 CPU 打满（那样 P50 也会涨）
  ❌ 不是网络整体抖动
  ❌ 不是所有请求都走的新代码路径（新代码是全量生效的）

→ 指向「长尾 / 局部」因素：
  ✅ 某类特定参数的请求很慢（大用户、深翻页、特定筛选条件）
  ✅ 偶发的外部依赖超时（下游抖动、慢查询、锁等待）
  ✅ 资源池偶发打满（连接池、线程池排队）
  ✅ GC 停顿 / 页换出（概率性事件，只影响少量请求）

3. 排查顺序（每步都在缩小范围） ​

text
第 1 步：确认影响面——是全网还是部分用户/机房？
   看监控按机房、按实例、按客户端版本拆分
   → 若只有一个实例慢：机器问题（GC、磁盘、邻居吵闹）→ 摘掉该实例
   → 若所有实例都慢：继续第 2 步

第 2 步：确认是新代码还是数据增长
   对比发版前后的分位曲线；把「慢请求」的 trace 拉出来看是新逻辑还是旧逻辑
   → 3 天前发版 + P99 恶化，新代码嫌疑很大（但要用数据证实，不能靠时间巧合）

第 3 步：拿到慢请求样本，做参数对比
   把 P99 慢请求的 user_id / 分页参数 / 筛选条件拉出来统计
   → 若集中在少数 user_id：数据倾斜（大用户订单几万条 → 深翻页 / 大结果集）
   → 若集中在深翻页（page 很大）：offset 分页的深翻页问题
   → 若参数无规律：继续第 4 步

第 4 步：对慢请求做分段耗时对比
   慢请求 vs 快请求，逐段比（Redis / MySQL / RPC）
   → 定位到具体段后，进第 5 步

第 5 步：针对该段做专项排查
   MySQL 慢：看慢查询日志、执行计划（EXPLAIN）、锁等待
   Redis 慢：看慢命令（KEYS、大 key）、命中率是否下降
   下游慢：看下游自身的监控与超时重试次数

4. 五个候选根因与验证方法 ​

候选根因为什么会只影响 P99验证方法
深翻页 / 大结果集只有翻到后面几页的请求慢，绝大多数用户只看第 1 页统计慢请求的 page 参数分布；对 page=1000 手动复现，看 EXPLAIN 的扫描行数
慢 SQL / 索引失效只有带某些筛选条件的查询不走索引，其余正常开慢查询日志，抓到 SQL 后 EXPLAIN 看 type=ALL（全表扫描）；检查新代码是否改了查询条件导致索引失效
缓存命中率下降命中时 2 ms，未命中回源 200 ms；若命中率从 95% 掉到 99% 分位刚好未命中看 Redis 命中率曲线（按 key 前缀拆）；对比发版前后缓存 key 的生成逻辑是否变化
下游超时重试放大下游偶发抖动 → 超时 → 重试 → 耗时翻倍甚至 3 倍（50ms × 3 次重试 + 退避 = 秒级）看下游调用的成功率与 RT 分位；统计重试次数；检查发版是否新增了重试逻辑或改了超时时间
连接池/线程池排队池子没满时正常，偶发高峰时请求排队等待（排队时间不计入 SQL 耗时，只体现在总 RT）看连接池的 等待获取连接数 与 最大等待时间；对比线程数配置与并发数（QPS × RT）

5. 为什么「先加机器 / 先扩容缓存」是错的第一反应 ​

text
① 没定位就扩容 = 用成本掩盖问题：
   如果是深翻页导致全表扫描，加机器只是让「更多机器一起做慢查询」，
   P99 可能从 2s 降到 1.8s，但根本没解决，且成本翻倍

② 扩容会掩盖线索：
   加了机器后指标部分恢复，排查窗口关闭，下次数据量再涨时问题以更猛的形式回来

③ 有可能让它更糟：
   盲目加缓存 → 缓存与数据库不一致风险 + 缓存击穿风险
   盲目加机器 → 连接池按机器数放大 → 数据库连接数超限 → 数据库被拖垮

正确顺序：先量化（分段耗时）→ 再定位（具体到段）→ 后修复（针对性）
         → 最后才考虑「扩容是不是合理的兜底手段」
