题目 1 · L4 还是 L7：流量入口怎么分层（对应概念 05） ​

难度：基础

题目：一个电商系统，流量构成如下：Web/App API 请求峰值 3 万 QPS、静态资源（图片/CSS/JS）请求 20 万 QPS、内部 MySQL 与 Kafka 需要统一入口。请设计负载均衡分层方案。

要求：

  • 说明每一层用 L4 还是 L7，以及理由
  • 估算每层需要的机器数（给出单机容量假设与算式）
  • 写一份 Nginx L7 配置（加权轮询 + 健康检查 + 会话保持相关设置）
  • 指出「LB 自身」的高可用怎么做

提示：前端锚点——Webpack DevServer 的 proxy 就是一台迷你 L7 负载均衡（按路径转发）；生产环境的区别是要额外考虑算法、健康检查、会话保持和自身高可用四件事。

参考答案

1. 分层设计 ​

text
                        用户
                          │
                    ┌─────▼─────┐
                    │    CDN     │  静态资源 20 万 QPS 在边缘消化（见概念 09）
                    └─────┬─────┘
                          │ 回源 + 动态请求
                    ┌─────▼─────┐
                    │  WAF/清洗  │  DDoS 防护，挡在 LB 之前
                    └─────┬─────┘
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
   ┌────▼────┐      ┌─────▼─────┐     ┌─────▼─────┐
   │ L4 (LVS)│      │ L7 (Nginx)│     │ L4 (LVS)  │
   │ 内部组件 │      │  API 3万  │     │ 内部组件   │
   │ MySQL   │      └─────┬─────┘     │ Kafka     │
   └─────────┘            │           └───────────┘
                    ┌─────▼─────┐
                    │  应用集群   │
                    └───────────┘

为什么这么分：

流量层级理由
API 请求 3 万 QPSL7（Nginx）需要按路径路由（/api / /static / /ws）、Header 改写、灰度分流
静态资源 20 万 QPSCDN + L790%+ 在 CDN 边缘命中，回源部分走 L7 按 /static 分流到静态服务器
MySQL / Kafka 入口L4（LVS）内部组件只转发端口，不需要解析报文；L4 性能极高、开销最小

实践原则：能用 L4 就用 L4（更简单更快），需要按内容路由/Header 改写/灰度分流时才上 L7。数据库入口用 Nginx 做 L7 是典型误用。

2. 机器数估算 ​

text
假设（来自压测，不是拍脑袋）：
  Nginx（L7，4 核 8G）  单机 2 万 QPS（L7 要解析报文，比 L4 低一个量级）
  LVS（L4，4 核 8G）    单机 10 万 QPS（只转发不解析）
  应用服务（4 核 8G）    单机 800 QPS

① API 层 Nginx：
   ceil(3 万 / 2 万) = 2 台 + 1 台冗余 = 3 台

② 应用层：
   ceil(3 万 / 800) = 38 台 + 冗余（N+1，实际按 10% 冗余）≈ 42 台

③ 内部 L4（MySQL/Kafka）：
   内部 QPS 远低于外部，2 台主备即可（重点是冗余不是容量）

关键提醒：LB 转发所有流量，它的 CPU/网卡必须按「峰值 QPS + 余量」配置。
         常见事故就是「后端没崩，LB 先崩了」。

3. Nginx 最小配置 ​

nginx
# nginx.conf —— L7 负载均衡
upstream backend_api {
    # 加权轮询：新机器 weight 低，性能好的机器 weight 高
    server 10.0.0.11:8080 weight=3;
    server 10.0.0.12:8080 weight=3;
    server 10.0.0.13:8080 weight=1;   # 新扩容机器，先少分流量灰度

    # 主动健康检查：每 5s 探一次 /healthz，失败 2 次剔除，恢复 3 次回池
    check interval=5000 rise=3 fall=2 timeout=2000;
}

upstream backend_static {
    server 10.0.1.11:80;
    server 10.0.1.12:80;
}

server {
    listen 80;

    # 按路径分流（L7 的核心能力）
    location /api/ {
        proxy_pass http://backend_api;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;   # 后端拿真实客户端 IP
    }

    location /static/ {
        proxy_pass http://backend_static;
        expires 30d;                                # 静态资源长缓存
    }

    location /ws/ {
        proxy_pass http://backend_api;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;     # WebSocket 需要协议升级
        proxy_set_header Connection "upgrade";
    }
}

说明：生产环境几乎不用纯轮询，而是加权轮询 + 健康检查的组合；一致性哈希（hash $remote_addr consistent）只在需要会话保持/缓存亲和时才加——而会话保持本身是「补丁」，根治方案见题目 3。

4. LB 自身的高可用（VIP 漂移） ​

text
                虚拟 IP（VIP：对外只暴露这一个 IP）
                        │
        ┌───────────────┴───────────────┐
        ▼                               ▼
    LB 主（keepalived 节点1）        LB 备（keepalived 节点2）
        │         心跳（VRRP 组播）       │
        └───────────────┬───────────────┘
                        │
                    后端集群

主 LB 故障 → 心跳中断 → 备节点接管 VIP（约 1s）→ 客户端无感知

两个细节：

  1. 主备 vs 双活：双活需要会话同步、复杂度高；读多场景主备足够。
  2. 只做一层 LB 有风险：DDoS 到 L4 之前没有清洗层，LB 直接被打瘫 → 入口要分层（云 WAF/清洗 → LB → 后端）。

评分要点（共 10 分，≥7 分合格） ​

  • [ ] 2 分：区分了 L4 / L7 的适用场景，且给出「能用 L4 就用 L4」的原则
  • [ ] 2 分：机器数有算式（ceil(峰值 / 单机容量) + 冗余），单机容量标注为压测值
  • [ ] 2 分：Nginx 配置包含加权轮询 + 健康检查 + 按路径分流三要素
  • [ ] 1 分：proxy_set_header X-Real-IP 传真实 IP（否则后端只能看到 LB 的 IP）
  • [ ] 2 分：LB 自身高可用用主备 + VIP 漂移，且提到 DDoS 清洗层
  • [ ] 1 分：提醒了「LB 自身容量要按峰值 + 余量配置」
  • [ ] 扣分项：数据库入口用 Nginx 做 L7 转发 → 扣 2 分
  • [ ] 扣分项：健康检查接口里查数据库 → 扣 2 分（见题目 2）

题目 2 · 健康检查：/healthz 该检查什么（对应概念 05） ​

难度：进阶

题目：你们的 LB 每 5 秒探测一次 /healthz，连续 2 次失败就摘掉该实例。某天数据库抖动了 10 秒，结果所有应用实例被整批摘掉，流量全部打到 LB 直接 503，故障从「数据库抖一下」放大成「全站不可用」。

要求：

  1. 分析事故链条，指出根因
  2. 给出 /healthz 的正确设计（要包含什么、绝不检查什么）
  3. 区分「主动检查」与「被动检查」，给出推荐的参数配置
  4. 说明「就绪探针」与「存活探针」的区别（就绪 = 能否接流量，存活 = 要不要重启）

提示：前端锚点——这就是「健康检查接口不要做成全链路探测」：一个轻量心跳如果被塞进了重依赖，抖动就会被放大成雪崩。

参考答案

1. 事故链条与根因 ​

text
时间线：
  T+0s   数据库抖动，连接超时
  T+0s   /healthz 里检查了数据库连通性 → 全部实例返回 500
  T+5s   LB 第一次探测失败（计数 1）
  T+10s  LB 第二次探测失败（计数 2）→ 触发剔除阈值
  T+10s  所有实例被摘掉，LB 后面没有可用后端 → 全部请求 503
  T+15s  数据库恢复
  T+15s  实例恢复健康，但要连续 3 次成功（15 秒）才回池
  → 故障窗口：约 20 秒的全站不可用（原本只是数据库抖 10 秒）

根因：/healthz 检查了「下游依赖」而不是「自身存活」。
      数据库是所有实例共享的，一抖动就同时判所有实例死亡 →
      剔除动作不是「摘掉坏节点」，而是「摘掉整个集群」。

2. /healthz 的正确设计 ​

text
✅ 应该检查（轻量、只关乎自身）：
   ① 进程存活（能响应 HTTP）
   ② 关键资源轻量探测：
      - 连接池是否有可用连接（不看能否连上 DB，只看本地池状态）
      - 磁盘可写（临时目录）
      - 内存是否超过阈值
   ③ 必要的「启动完成」标记（初始化没跑完就不接流量）

❌ 绝不检查：
   ① 数据库连通性 ← 本题事故的元凶
   ② 下游 RPC 服务可用性
   ③ 缓存/消息队列连通性
   ④ 任何需要网络往返的重操作

判据：/healthz 必须在 10 ms 内返回，且**不依赖任何外部组件**。
     外部依赖的可用性由「熔断降级」处理，而不是靠摘实例。

示例实现（伪代码）：

python
@app.get("/healthz")
def healthz():
    # 只查自身：进程活着 + 连接池没被耗尽 + 磁盘可写
    if pool.available() == 0:
        return {"status": "unhealthy", "reason": "pool exhausted"}, 503
    if disk.free_gb() < 1:
        return {"status": "unhealthy", "reason": "disk full"}, 503
    return {"status": "ok"}, 200

注意这里不连数据库：连接池耗尽是「自身状态」，可以报；但「数据库连不上」属于外部故障，应该让请求正常进来、由业务逻辑走降级/熔断，而不是让 LB 摘实例。

3. 主动检查 vs 被动检查 ​

text
主动检查（LB 定期探测）：
  间隔 5s 发 GET /healthz，要求 200 且响应体含 "ok"
  → 连续 2 次失败剔除（不再转发）
  → 连续 3 次成功恢复（重新加入）

  参数权衡：
    间隔太短（1s）→ 探测本身成为负担，且更容易被抖动的误判
    失败次数太少（1 次）→ 一次网络抖动就摘除，误伤率高
    恢复次数太少（1 次）→ 实例刚起来还没预热就被打满，再次崩溃

  推荐配置：间隔 5s、失败 2 次剔除、成功 3 次回池

被动检查（根据真实请求结果）：
  后端连续返回 5xx → 熔断剔除
  连接超时次数超阈值 → 剔除
  → 优点：反映的是「真实用户体验」，而不是探测器的视角
  → 推荐：主动 + 被动同时开启，主动做兜底，被动做快速反应

4. 就绪探针 vs 存活探针 ​

探针回答的问题失败后果检查内容
就绪（Readiness）能不能接流量？从 LB 摘掉，不重启依赖是否就绪、是否正在优雅退出、负载是否过高
存活（Liveness）要不要重启？杀掉进程重启进程是否死锁、是否陷入死循环
text
关键区别与常见事故：
  把「数据库连不上」放进存活探针
  → 数据库抖动 → 所有实例被判定「不存活」→ 全部重启
  → 重启后仍然连不上 → 继续重启 → 重启风暴（crash loop）
  → 数据库恢复了，但应用在无限重启中，雪上加霜

正确做法：
  存活探针只查「进程是否还活着」（如 HTTP 200 即可，或死锁检测）
  就绪探针可以查依赖（因为失败只是摘流量，不会重启）
  依赖类失败 → 就绪探针摘流量 + 业务层熔断降级

5. 事故复盘结论 ​

text
改进项：
  ① /healthz 移除数据库检查（根因修复）
  ② 区分就绪/存活探针，依赖检查只放进就绪探针
  ③ 加「剔除比例上限」：一次最多摘掉 30% 的实例，
     超过则停止剔除并告警（防止「一键全摘」）
  ④ 加熔断降级：数据库连不上时返回兜底数据，而不是 503

评分要点（共 10 分，≥7 分合格） ​

  • [ ] 3 分：正确指出根因是「健康检查里查了共享的下游依赖」，且解释了为什么会被放大（所有实例同时判死）
  • [ ] 2 分：/healthz 设计给出「检查什么 + 不检查什么」的清单，且判据清晰（< 10 ms、不依赖外部组件）
  • [ ] 2 分：主动/被动检查都讲了，且给出推荐参数（5s / 2 次剔除 / 3 次恢复）
  • [ ] 2 分：就绪探针与存活探针的区别讲清楚（摘流量 vs 重启），且指出「依赖检查放进存活探针会导致重启风暴」
  • [ ] 1 分：复盘里提出了「剔除比例上限」这类防放大机制
  • [ ] 扣分项：仍建议在 /healthz 里查数据库 → 直接扣 4 分

题目 3 · 会话保持：从 sticky 到无状态化（对应概念 05） ​

难度：进阶

题目：一个电商网站把用户 session 存在应用实例的内存里，用 LB 的 IP Hash 做会话保持。最近出现两个问题：① 扩容新机器后，部分用户被重新哈希到新机器，登录态丢失；② 某台机器重启，它的用户全部掉线。请给出解决方案。

要求：

  1. 分析 sticky session 与 IP Hash 的失效场景（至少 3 个）
  2. 给出「根治方案」（无状态化）的具体做法，并对比三种 session 外置方案
  3. 说明改造后 LB 算法可以退化成什么，带来什么好处
  4. 指出哪些场景确实需要会话保持（不能一刀切说「sticky 永远错」）

提示：前端锚点——这就是把「服务端状态」从组件内部挪到外部 store：组件变成纯函数，随便扩缩容都不丢状态。

参考答案

1. 会话保持的失效场景 ​

方案失效场景后果
Sticky Session（LB 记映射）① 后端重启/扩容 → 映射失效
② 用户 IP 变化（移动网络切基站、WiFi 切 4G）
③ 分布不均（大客户 IP 集中，某台机器特别热）		登录态丢失、负载倾斜
IP Hash（哈希取模）① 扩容即失效：3 台扩到 4 台，hash % 3 变 hash % 4，约 75% 的用户被重新路由
② NAT 环境下大量用户共用同一出口 IP → 严重倾斜
③ 同上，IP 变化失效		大规模掉线
内存 session任何实例重启都导致该实例的用户全掉发版即掉线

核心问题：会话保持是把状态绑在机器上，而机器的生命周期是不可靠的（会重启、会扩缩容、会故障）——这就是「补丁」而非「根治」。

2. 根治方案：无状态化（状态外置） ​

text
改造前：
  用户 → LB（IP Hash）→ 实例 A（内存 session）

改造后：
  用户 → LB（轮询）→ 任意实例 ──► Redis（共享 session）
                                 或 JWT（签名令牌，无服务端存储）

三种方案对比：

方案做法优点缺点适用
Redis 集中存储session 存 Redis，实例只存 sessionId（Cookie）集中管理、可主动踢人、容量大多一次网络往返（约 1 ms）；Redis 挂了要降级默认推荐
JWT 无状态令牌用户身份与权限签名后放 token，服务端不存零存储、零查询，扩展性最好无法主动失效（签发后到过期前一直有效）；token 较大对「踢人」要求不高的场景
Cookie 存 session加密后放 Cookie与 JWT 类似，实现简单Cookie 大小限制（4 KB）、每次请求都带上极简场景

推荐组合：

text
① 访问令牌用 JWT（短期，15 分钟），减少 Redis 查询
② 刷新令牌存 Redis（长期，7 天），保证可以主动踢人和续期
③ 敏感操作（改密码、支付）强制查 Redis 校验

3. 改造后的收益 ​

text
① LB 算法退化为最简单的轮询（Round Robin）
   → 不需要一致性哈希、不需要 sticky 表，配置和心智负担都降到最低

② 任意横向扩缩容
   → 扩容时新机器立刻能接任何请求，不需要预热 session、不需要迁移

③ 发版不再掉线
   → 滚动发布时实例逐个重启，用户请求被 LB 分到其他实例，无感知

④ 故障恢复快
   → 某实例宕机，LB 健康检查摘掉它，用户请求自动分到健康的实例

4. 哪些场景确实需要会话保持 ​

「无状态化优先」不等于 sticky 永远错，以下场景可以接受会话绑定：

text
① WebSocket / 长连接
   连接本身就绑定在一台机器上（TCP 连接无法迁移）
   → 必须保证同一连接打到同一实例；但连接断开重连时可以重新分配

② 本地缓存亲和（缓存热点数据在本地内存）
   让同一 key 的请求打到同一实例，提高本地缓存命中率

参考答案

1. 分区键设计：保证同一订单的事件顺序 ​

text
错误做法：按事件类型分区、或随机分区
  分区0: [order#1 created] [order#5 created] ...
  分区1: [order#1 paid]    [order#3 created] ...
  → 同一订单的事件散在不同分区，不同消费者并行处理 → 乱序！

正确做法：用「订单号」做分区键（partition key）
  partition = hash(order_id) % partition_count

  分区0: [order#1 created] → [order#1 paid] → [order#1 shipped]
  分区1: [order#7 created] → [order#7 paid] ...
  → 同一订单的所有事件进同一个分区，由同一个消费者顺序处理 ✅

「分区内有序、分区间无序」的含义：

text
分区内有序：同一分区的消息按投递顺序消费 → 同一订单的状态迁移不会乱序
分区间无序：不同订单之间的先后顺序没有保证

为什么这样就够了：
  业务上只需要保证「同一订单的生命周期事件有序」，
  订单 A 和订单 B 谁先处理完全无所谓（没有业务依赖）
  → 用分区键把「需要保证顺序的粒度」圈起来，是 MQ 设计的核心技巧

2. 消费端幂等实现 ​

text
核心思路：消息带唯一键，处理前先查「已处理表」，处理与记录在同一事务里

① 消息体带唯一键：
   message_id（全局唯一，MQ 生成）
   业务键：order_id + event_type（如 "10086:order_paid"）

② 建已处理表（唯一索引兜底）：
   CREATE TABLE processed_message (
     biz_key     VARCHAR(128) PRIMARY KEY,   -- order_id:event_type
     message_id  VARCHAR(64),
     processed_at DATETIME
   );

③ 消费逻辑（事务内完成）：
python
def handle_order_paid(msg):
    biz_key = f"{msg.order_id}:order_paid"
    with db.transaction():
        # INSERT IGNORE：已存在则影响行数为 0，直接跳过
        affected = db.execute(
            "INSERT IGNORE INTO processed_message (biz_key, message_id, processed_at)"
            " VALUES (?, ?, NOW())", biz_key, msg.message_id)
        if affected == 0:
            return              # 已处理过，幂等跳过（重复投递无害）

        # 真正的业务逻辑：发货短信、扣库存等
        send_shipping_sms(msg.order_id)

        # 注意：业务处理与「已处理」记录在同一个事务里 → 原子
        # 要么都成功（记录 + 业务），要么都回滚（下次重新消费）

# 关键：不要把「记录已处理」和「执行业务」拆成两个事务，
#       否则业务成功、记录失败 → 下次重复消费，依然会重复发短信

3. 投递语义的取舍 ​

语义机制代价适用
至多一次收到即 ack，不重试可能丢消息可容忍丢失的日志/埋点
至少一次处理成功后 ack；失败不 ack 重新投递可能重复消费默认选择（配幂等）
恰好一次事务 / 幂等键去重性能与复杂度最高支付、账务等必须精确
text
生产推荐：至少一次 + 消费端幂等

为什么不直接上「恰好一次」：
  实现依赖端到端事务（MQ 与数据库之间做分布式事务），
  性能损耗大、实现复杂、故障排查难。
  而「至少一次 + 幂等」用一张去重表就解决了，简单可靠。

注意：「至少一次」意味着重复消费是**必然发生**的（网络重试、消费者重启、
       rebalance 都会触发），所以幂等**不是可选项，是必选项**。

4. 重试 + 死信队列流程 ​

text
消费失败 → 重试队列（延迟 1s / 5s / 30s 递增）→ 重试 3 次仍失败 → DLQ（死信队列）
                                                                    │
                                                          ┌─────────┴─────────┐
                                                          ▼                   ▼
                                                    告警：通知值班人员    人工分析/补偿
text
DLQ 设计要点：
  ① 死信消息保留原始内容 + 失败原因 + 重试次数 + 最后错误堆栈
  ② 提供「一键重投」工具：问题解决后批量把死信放回主队列
  ③ 告警策略：
     - 死信数 > 0 持续 1 分钟 → 告警（说明有消息处理不了了）
     - 死信数 5 分钟内增长 > 100 → 紧急告警（说明是系统性问题）
     - **死信堆积是重大事故的早期信号**：
       订单事件死信堆积 = 下游正在丢失订单处理

  ④ 常见死因：
     - 下游服务长时间不可用
     - 消息格式与代码不兼容（发版没做兼容）
     - 脏数据（如订单号为空、金额为负）

5. 消费者数量与分区数的关系 ​

text

  ① 同一分区内的消息由**同一个消费者**顺序处理
  ② 同组内分区数 ≥ 消费者数，否则多出来的消费者**空转**（拿不到分区）
  ③ 不同消费者组之间互不影响（短信组和统计组各自独立消费全量）

扩容无效的三种场景：
  ❌ 分区数 8，消费者扩到 12 → 有 4 个消费者空转，白扩容

  ❌ 瓶颈在数据库（如题目 4 的 1000 QPS）→ 扩消费者只会加剧 DB 压力

  ❌ 消息处理是严格顺序的且只有一个分区 → 永远只能单线程处理

1. 策略选择：Cache-Aside（旁路缓存） ​

text
选 Cache-Aside，理由：
  ① 实现最简单，应用代码完全掌控（读没命中就回源，写就删缓存）
  ② 只有真正被访问的数据才会进缓存（不会缓存冷数据，内存利用率高）
  ③ 写路径只需要「删缓存」而不是「更新缓存」，写放大最小

不选其他三个的理由：
  Read-Through：回源逻辑耦合进缓存组件，灵活性差，还要改造组件
  Write-Through：写 QPS 50 × 每次都写缓存 → 写放大，且很多写进去没人读
  Write-Behind：异步写库，Redis 宕机会丢更新 → 用户资料丢了是生产事故

2. 读路径与写路径 ​

text
【读路径】
  1. 查 Redis（key = user:profile:{user_id}）
  2. 命中 → 直接返回（约 1~2 ms）
  3. 未命中 → 查数据库（约 10 ms）→ 写入 Redis（设 TTL）→ 返回

【写路径】
  1. 更新数据库
  2. 删除缓存（注意是「删」不是「更新」）
  3. 下次读时自动回源写入新值

为什么写时「删缓存」而不是「更新缓存」：

text
① 更新缓存可能做无用功：改了昵称但用户半年不再访问 → 白写一次
② 并发写场景下，两个更新请求可能以错误顺序写入缓存（A 先改库 B 后改库，
   但 B 先写缓存 A 后写缓存 → 缓存里是 A 的旧值，且长期不修正）
③ 删缓存更简单：下次读自然会拿到最新值

3. 两种更新顺序的故障后果 ​

text
方案 A：先删缓存，再更新数据库
  时序：① 删缓存成功 ② 数据库更新失败
  后果：缓存空了，数据库还是旧值
        → 下次读回源，读到**旧值**并写回缓存
        → 缓存里长期是旧数据，直到下一次写入（可能几小时后！）
  严重度：❌ 高（长期不一致）

  更糟的并发场景：
  ① 请求 A（写）删缓存
  ② 请求 B（读）未命中 → 读数据库（旧值）→ 写入缓存（旧值）
  ③ 请求 A 更新数据库（新值）
  → 缓存是旧值，数据库是新值，长期不一致

方案 B：先更新数据库，再删缓存 ← ✅ 推荐
  时序：① 数据库更新成功 ② 删缓存失败
  后果：缓存里是旧值
        → 但 TTL 到期后会重新回源，且下一次写入会再次删缓存
  严重度：✅ 低（短暂不一致，有 TTL 兜底）

方案 C：延迟双删（先删 → 更新库 → 等 1s → 再删）
  适用场景：对一致性要求较高，且存在「读请求在写请求中间回源」的竞态
  代价：多一次删除操作，且「等 1s」的时长是经验值，不严谨

结论：默认用「先更新库，再删缓存」；一致性要求极高时直接绕过缓存读主库（用性能换正确，本身就是一种权衡）。

4. 压力与命中率计算 ​

text
已知：
  读 QPS = 5000
  数据库读能力 = 2000 QPS

要求：数据库承受的读压力 ≤ 2000 QPS（留 50% 余量更安全，按 ≤ 1000 算）

回源 QPS = 读 QPS × (1 - 命中率)
  要求：5000 × (1 - 命中率) ≤ 1000
  → 1 - 命中率 ≤ 0.2
  → 命中率 ≥ 80%

按数据库全部读能力算（不留余量）：
  5000 × (1 - h) ≤ 2000 → h ≥ 60%

结论：命中率必须 ≥ 80%（留余量），≥ 90% 才健康
      命中率从 95% 掉到 85% → 回源从 250 涨到 750 QPS，翻 3 倍
      → 命中率是缓存系统的「血压」，必须监控

5. TTL 的作用 ​

text
TTL 是最后的兜底防线：
  ① 应对「删缓存失败」：缓存总有到期时间，不会永远错
  ② 应对「未知的更新路径」：如果有别的服务绕过应用直接改了数据库，
     TTL 到期后缓存会自动纠正
  ③ 防止冷数据常驻内存：长期不访问的数据自动淘汰

TTL 设置：
  基础 1 天 + 随机 0~6 小时（防止大量 key 同时过期造成雪崩，见题目 7）
  一致性要求高的场景：TTL 短一些（如 5 分钟）

⚠️ 绝不设置「永不过期」除非是热点 key 的特殊策略（见题目 7）

6. 哪些数据不该放进缓存 ​

text
❌ 强一致数据：余额、库存、订单状态
   → 缓存不一致 = 资损。这类数据要么读主库，要么用带锁/事务的方案

❌ 写多读少的数据：写 QPS > 读 QPS
   → 每次写都要删缓存，缓存几乎没有命中收益，纯属自找麻烦

❌ 大 value（> 1 MB）：
   → 单 key 过大会拖垮网络与内存，且序列化开销大

❌ 极少被访问的数据：
   → 占用内存却不产生命中，降低整体命中率

✅ 适合缓存：读多写少、可容忍短暂陈旧、数据量适中的热点数据
   （用户资料、商品详情、配置信息、字典表）

评分要点（共 10 分，≥7 分合格） ​

  • [ ] 2 分：策略选对（Cache-Aside），且说明了为什么不选其他三种（各一条理由）
  • [ ] 3 分：更新顺序分析完整（方案 A 长期不一致、方案 B 短暂不一致），且推荐先库后删
  • [ ] 2 分：命中率有计算过程（回源 QPS = 读 QPS × (1 - 命中率)），并给出健康阈值（≥ 90%）
  • [ ] 1 分：TTL 的作用讲清楚（兜底防线 + 防雪崩的随机值）
  • [ ] 1 分：列出不该缓存的数据（强一致 / 写多读少 / 大 value / 冷数据）
  • [ ] 1 分：写路径是「删缓存」而非「更新缓存」，且说明了并发写乱序的风险
  • [ ] 扣分项：推荐「先删缓存再更新库」→ 直接扣 3 分
  • [ ] 扣分项：缓存没有 TTL → 扣 2 分

题目 7 · 缓存三兄弟：穿透、击穿、雪崩（对应概念 07） ​

难度：进阶

题目：某商品详情接口（读 QPS 3 万，Redis 缓存）近期出了两次故障：

  • 故障一：有人用随机商品 ID 狂刷（这些 ID 都不存在），数据库被打垮
  • 故障二：一个爆款商品（占 30% 流量）的缓存正好在过期瞬间，大量请求同时回源，数据库 QPS 瞬间冲到 2 万

请分别诊断并给出解决方案。

要求：

  1. 诊断两个故障分别属于哪一类（穿透 / 击穿 / 雪崩）
  2. 针对每类给出至少两种解决方案，并说明各自的代价
  3. 补充第三种故障「雪崩」的场景、原因与解法（含 TTL 随机值的具体设置）
  4. 给出缓存监控指标表（指标 / 健康值 / 异常信号）
  5. 计算：如果 Redis 整体宕机，3 万 QPS 全部回源，数据库会怎样？该怎么兜底？

提示：前端锚点——这就是「缓存失效瞬间流量全部冲向数据库」的三种变体，解法统一为「错峰 + 兜底 + 挡墙」。

参考答案

1. 诊断 ​

text
故障一 = 缓存穿透
  特征：查询【根本不存在】的 key → 每次都不命中 → 每次都打数据库
  原因：恶意攻击（随机 ID 狂扫）或业务 bug（查已删除的数据）

故障二 = 缓存击穿
  特征：一个【热点 key 恰好在过期瞬间】被大量请求同时访问
  原因：爆款商品（占 30% 流量）+ 缓存到期 → 全部同时回源

第三种（还没发生但必须预防）= 缓存雪崩
  特征：【大批 key 同一时间集体过期】或 Redis 整体宕机
  原因：批量导入数据时设了相同 TTL；或 Redis 集群故障

2. 解决方案与代价 ​

故障一：缓存穿透

方案做法代价
① 空值缓存查询结果为「不存在」时，也缓存一个空值（"" 或特殊标记），TTL 设短（1~5 分钟）占用少量内存；攻击者换一批随机 ID 仍会穿透（但已被大幅削弱）
② 布隆过滤器把所有合法商品 ID 放进布隆过滤器，请求先过过滤器，不存在的直接返回有误判率（不存在的可能判成存在，但不会反过来）；数据新增时要同步更新过滤器；实现复杂度更高
③ 参数校验 + 限流ID 格式校验（如必须是数字且在合理范围）；对同一 IP 的请求限流只能挡低级攻击

推荐：① + ② 组合（空值缓存挡大部分，布隆过滤器做兜底）。

故障二：缓存击穿

方案做法代价
① 互斥锁（回源加锁）缓存未命中时，先抢分布式锁（Redis SETNX）；抢到的去查库并写缓存，没抢到的等待几十毫秒后重试读缓存未抢到锁的请求要等待（增加延迟）；锁本身要处理死锁（设过期时间）
② 热点 key 永不过期 + 异步刷新热点 key 不设 TTL（物理不过期），另起一个定时任务或消息触发异步刷新需要识别「哪些是热点 key」；刷新失败时数据会陈旧
③ 提前续期在 value 里存一个「逻辑过期时间」，请求发现逻辑过期就触发异步刷新，先返回旧值（类比 stale-while-revalidate）会短暂返回旧数据（通常可接受）

推荐：① 互斥锁（实现直接、延迟可控），爆款场景叠加 ②。

3. 雪崩的场景与解法 ​

text
场景：
  ① 批量导入/预热了 100 万个商品，全部设置 TTL = 1 小时
     → 1 小时后集体过期，3 万 QPS 全部回源
  ② Redis 集群故障（主节点宕机、网络分区）
     → 所有请求回源

解法（错峰 + 兜底 + 挡墙）：
  ① 错峰：TTL 加随机值
     错误：TTL = 3600（全部同时过期）
     正确：TTL = 3600 + random(0, 1800)
           → 过期时间均匀分布在 1~1.5 小时之间，不会集体到期

  ② 兜底：多级缓存
     Redis 挂了 → 本地缓存（进程内）仍能提供旧数据
     → 本地缓存的 TTL 也要短（如 60 秒），避免长期不一致

  ③ 挡墙：限流 + 熔断降级
     回源请求超过阈值 → 直接返回兜底数据（如默认商品信息）或排队
     → 宁可降级，也不能让数据库被打垮（数据库挂了 = 全站不可用）

4. 缓存监控指标表 ​

指标健康值参考异常信号与排查方向
命中率读多系统 > 90%跌破 80%：① 缓存键是否带动态参数？② TTL 是否被改短？③ 是否有批量删除？④ 是否有大促流量激增？
大 key（> 1 MB）无单 key 过大 → 拖垮网络与内存；拆分或压缩
慢命令（> 10 ms）无排查 O(N) 命令（KEYS、大集合全量操作）
内存使用率< 70%逼近上限触发 LRU 淘汰风暴 → 命中率骤降
过期淘汰率（evicted）平稳突增 = 数据量大增或 TTL 设太短
回源 QPS远小于总读 QPS突然上涨 = 命中率下降或缓存故障

监控的价值是把「缓存失效」从事故变成报表：命中率每天看，而不是等数据库告警了才回头看缓存。

5. Redis 整体宕机的后果与兜底 ​

text
计算：
  读 QPS = 30,000
  数据库读能力 = 2,000 QPS（题干：击穿时冲到 2 万已经打垮了）
  回源倍数 = 30,000 / 2,000 = 15 倍

后果：
  数据库瞬间承受 15 倍于容量的读压力
  → 连接池打满 → 查询排队 → RT 从 10ms 涨到秒级
  → 应用线程池被拖满 → 不只是商品详情，所有接口都不可用
  → 数据库可能直接崩溃，恢复需要分钟级甚至更长

兜底方案（按顺序执行）：
  ① 本地缓存兜底（毫秒级生效）
     每个实例保留一份最近 60 秒的热点数据
     → Redis 挂了仍能挡住大部分流量（命中率可能只有 60%，但足以保护数据库）

  ② 熔断 + 限流（秒级生效）
     回源请求超过 2000 QPS 就熔断，直接返回兜底数据或友好提示
     → 宁可部分功能降级，也不能让数据库崩溃

  ③ Redis 高可用（根本方案）
     主从 + 哨兵：主节点宕机自动切从（秒级）
     Redis Cluster：数据量超单机时才需要
     → 让「Redis 整体宕机」变成小概率事件

  ④ 熔断恢复要「慢启动」
     Redis 恢复后不要立刻放全量流量进去（空缓存会导致再次击穿）
     → 逐步放量（如 10% → 50% → 100%），或提前预热热点 key

评分要点（共 10 分，≥7 分合格） ​

  • [ ] 2 分：三类故障诊断正确（不存在 = 穿透、热点过期 = 击穿、批量过期/宕机 = 雪崩）
  • [ ] 3 分：每类给出 ≥ 2 种方案，且说明代价（只列方案名不给代价扣 1 分/类）
  • [ ] 2 分：雪崩解法覆盖「错峰（随机 TTL）+ 兜底（多级缓存）+ 挡墙（限流熔断）」，随机 TTL 有具体设置
  • [ ] 1 分：监控指标表 ≥ 4 项，含命中率、大 key、慢命令、内存
  • [ ] 2 分：Redis 宕机有量化计算（15 倍压力）+ 分级兜底（本地缓存 → 熔断 → Redis 高可用 → 慢启动预热）
  • [ ] 加分：提到「熔断恢复要慢启动，避免空缓存再次击穿」
  • [ ] 扣分项：把「穿透」和「击穿」混淆 → 扣 2 分

题目 8 · 分片键选择与全局 ID（对应概念 08） ​

难度：进阶

题目：用户表达到 2 亿行（单表已经 500 GB），查询慢、写入也慢。需要分片。业务查询有：① 按 user_id 查「我的订单」；② 按 order_id 查「订单详情」；③ 客服后台按手机号查用户；④ 财务按城市统计 GMV。

要求：

  1. 先判断：该不该分片？给出在分片之前应该先做的事（至少 3 项）
  2. 如果确实要分片，选分片键并论证（要分析每个查询会落在单片还是广播）
  3. 分片后的全局 ID 方案：对比自增 ID / UUID / 雪花算法，给出选择与理由
  4. 解决「按手机号查用户」和「按城市统计 GMV」的跨分片需求
  5. 给出扩容预案，并说明为什么「先垂直后水平」

参考答案

1. 先别急着分片：分片是最后手段 ​

text
在分片之前，按顺序把这些做完（很多系统做完就够了）：

① 索引优化：慢查询是否走了索引？EXPLAIN 看是否有全表扫描
   → 2 亿行的表，加对索引可能就能救回来

② 读写分离 + 缓存：读多写少的话，主从 + Redis 能卸掉 90% 的读压力
   → 分片主要解决「写」和「单机容量」，读压力优先用缓存

③ 垂直拆分（按业务拆库）：用户库 / 订单库 / 商品库 各自独立
   → 简单（只是换库）、收益立竿见影（热库分离、独立扩容）
   → 很多系统「垂直拆完 + 归档冷数据」就够了，根本走不到水平分片

④ 归档冷数据：2 亿行里可能 1.5 亿是 1 年前的冷数据
   → 把冷数据搬到归档库，主表立刻瘦身到 5000 万行

只有以上都做了还扛不住（单机写 QPS > 5000、单表 > 1 亿行且还在涨），才考虑分片。
因为分片一旦落地：join 要应用层做、事务要分布式事务、聚合要汇总——SQL 能力全面降级。

2. 分片键选择：按 user_id 哈希分片 ​

text
候选一：按 order_id 分片
  ① 按 user_id 查「我的订单」→ 不知道订单在哪个片 → **广播 8 个片**（打全库）
  ② 按 order_id 查详情 → 单片 ✅
  → 高频查询（我的订单）变成广播，性能反而不如不分片 ❌

候选二：按 user_id 分片 ← ✅ 选这个
  ① 按 user_id 查「我的订单」→ 单片查询 ✅（占读流量的 80%）
  ② 下单（写）→ 按 user_id 均匀散开 ✅
  ③ 按 order_id 查详情 → 广播 ❌（但可以用「ID 里编码分片位」解决，见下）
  → 高频查询都是单片，低频查询可接受广播

三特性检验：
  高基数 ✅：user_id 取值上亿，散得开
  均匀分布 ✅：哈希后各片数据量接近（不像按 city 分，北京占 40%）
  访问亲和 ✅：最频繁的「我的订单」天然带 user_id

按 order_id 查详情的优化（避免广播）：

text
方案：把分片位编码进 order_id
  雪花算法的 10 位机器 ID 里，用 3 位表示分片号（最多 8 片）
  → 拿到 order_id 就能解析出分片号 → 单片查询 ✅
  代价：分片数变更时（8 → 16）这个编码会失效，需要兼容处理（双读或灰度迁移）

3. 全局 ID 方案对比 ​

方案全局唯一趋势递增无中心评价
数据库自增 ID❌ 各片自增会撞车✅❌分片后直接失效
UUID✅❌ 完全无序✅作为主键随机写 → B+ 树页分裂频繁 → 插入性能骤降 ❌
雪花算法✅✅✅推荐：三项全中
发号器服务（DB/Redis 取号段）✅✅❌有序但引入中心组件，多一个故障点
text
雪花算法结构（64 位 long）：
┌────────┬──────────────┬──────────┬──────────┐
│ 1 bit  │ 41 bit       │ 10 bit   │ 12 bit   │
│ 符号位 │ 毫秒时间戳    │ 机器 ID  │ 序列号   │
│ (0)    │ (可用 69 年)  │ (1024 台)│ (每毫秒 4096 个) │
└────────┴──────────────┴──────────┴──────────┘

为什么「趋势递增」重要：
  B+ 树索引按主键顺序组织，递增 ID 是「追加写」（顺序 IO），
  UUID 是「随机写」（随机 IO + 页分裂），插入性能差一个量级。

唯一风险：时钟回拨（服务器时间倒退会生成重复 ID）
  工程处理：回拨时间短就等待，回拨时间长就报警 + 切换备用机器 ID

4. 跨分片需求怎么解决 ​

text
需求③：客服按手机号查用户

  方案：二级索引（ES）或映射表
    ① 在 ES 里维护「手机号 → user_id」的索引（由 MySQL 的变更事件同步）
    ② 查询时先查 ES 拿到 user_id，再按分片键单片查询 MySQL
    → 两次查询，但都不是广播

  为什么不广播：每广播一次 = 打全库一次，客服后台并发虽低，
                但如果做成高频接口就是性能债

需求④：财务按城市统计 GMV

  方案：汇总表 / 列式仓库
    ① 定时任务（每小时/每天）把各片的订单聚合到一张汇总表（宽表）
    ② 或同步到 ClickHouse，报表直接查列式库
    → 统计类需求本来就该用 OLAP 方案，行存跑聚合慢一个量级
    → 这也是「OLTP 与 OLAP 分离」原则的体现（见 L1 题目 8）

5. 扩容预案与「先垂直后水平」 ​

text
为什么先垂直后水平：
  垂直拆分（按业务拆库）：只是换库，不动路由、不动分片键，
                        复杂度低一个量级，收益立竿见影
  水平拆分（分片）：要定分片键、改路由层、处理跨片查询与事务，
                   是「最昂贵的架构变更」，且几乎不可逆（换分片键 = 数据全量迁移）

扩容预案（设计阶段就要想好，而不是扩容时才考虑）：

  方案 A：2 倍预分配
    一开始就分 16 片，但只部署 8 台机器（每台放 2 片）
    扩容到 16 台时，只需把片迁到新机器，**哈希规则不变**（仍是 % 16）
    → 代价：初期管理 16 片的逻辑（但都在 8 台机器上）

  方案 B：一致性哈希
    扩容时只迁移 1/N 的数据（如 8 → 16 片，只迁 1/16）
    → 代价：实现复杂度高，且数据分布可能不均（要用虚拟节点）

  推荐：中小规模用方案 A（简单可控），超大规模再上一致性哈希

  扩容执行步骤（无论哪种方案）：
    ① 双写（新旧两套路由同时写）
    ② 存量数据迁移（按片批量，可暂停可回滚）
    ③ 数据校验（行数 + 金额/关键字段合计）
    ④ 灰度切读（1% → 10% → 100% 流量）
    ⑤ 观察 7 天后下线旧路由与双写

题目 9 · CDN 与静态资源缓存（对应概念 09） ​

难度：基础

题目：一个新闻网站，日活 500 万，每人每天浏览 20 篇文章，每篇文章平均 3 张图片（每张 300 KB），JS/CSS 资源合计 800 KB（首次加载）。请设计 CDN 缓存方案。

要求：

  1. 计算日流量与带宽需求，论证「为什么必须用 CDN」
  2. 给出不同资源的 Cache-Control 配置（index.html / hash 资源 / 图片 / 用户私有数据）
  3. 解释「hash 文件名 + 长 TTL」为什么优于「固定文件名 + 短 TTL」
  4. 说明缓存键的组成，并指出「URL 带动态参数」会导致什么后果
  5. 给出发布流程（构建 → 上传 → 更新入口 → 预热 → 回滚）

提示：前端锚点——这是前端最熟悉的一节：npm run build 产出的 app-8f3d2a.js 就是为了配合 CDN 缓存。现在从后端视角重新理解它。

参考答案

1. 流量与带宽计算 ​

text
已知：
  DAU = 500 万，人均浏览 20 篇/天，每篇 3 张图 × 300 KB
  JS/CSS 合计 800 KB（首次加载，之后被浏览器缓存）

① 图片流量：
  日图片请求 = 500 万 × 20 × 3 = 3 亿次/天
  日图片流量 = 3 亿 × 300 KB = 900 亿 KB ≈ 858 TB/天

  日均带宽 = 858 TB × 8 bit / 86400 秒
          = 858 × 1024 GB × 8 / 86400 ≈ 81.6 Gbps
  峰值（×3）= 约 245 Gbps

② 静态资源流量（JS/CSS）：
  假设 DAU 中 20% 是当天新访客（缓存失效）：
  日资源请求 = 500 万 × 20% = 100 万次
  日资源流量 = 100 万 × 800 KB ≈ 0.76 TB/天 → 带宽约 0.07 Gbps（可忽略）

③ 结论：图片占了 99.9% 的带宽

④ 为什么必须用 CDN：
  源站带宽需求 = 245 Gbps（峰值）
  单机千兆网卡 = 1 Gbps → 需要 245 台机器**只用来扛图片**
  且这些机器 99% 的时间在重复传输同一批热点图片（严重浪费）

  上 CDN 后（命中率 95%）：
    回源带宽 = 245 × 5% ≈ 12 Gbps（源站只需 12~15 台机器）
    边缘带宽 = 245 × 95% ≈ 233 Gbps（由 CDN 厂商的分布式节点承担）
  → 成本下降一个量级，且用户延迟从「跨省回源 100ms+」降到「就近命中 20ms 内」

2. Cache-Control 配置 ​

资源配置理由
index.html（入口）Cache-Control: no-cache每次回源校验（ETag/Last-Modified），保证用户拿到最新入口；绝不能长缓存，否则发版后用户永远访问旧页面
app-8f3d2a.js / *.css（hash 文件名）Cache-Control: public, max-age=31536000, immutable内容变则 hash 变 → 新 URL 新缓存；内容不变则永久命中
图片（内容不变）Cache-Control: public, max-age=2592000（30 天）图片文件名通常不带 hash，用较长但有限的 TTL；配合版本号或目录区分（ /v2/xxx.jpg）
用户私有数据（个人信息、订单详情）Cache-Control: private, no-store绝不进 CDN。设成 public 会导致「用户 A 看到用户 B 的数据」——严重安全事故
实时数据（库存、余额）Cache-Control: no-store实时性数据被缓存会导致超卖

3. hash 文件名 + 长 TTL vs 固定文件名 + 短 TTL ​

text
方案 A：固定文件名 + 短 TTL（app.js + max-age=300）
  问题：
    ① 命中率低：5 分钟就过期，回头用户多时命中率可能只有 50%
    ② 一致性差：TTL 内发了新版，用户仍拿旧的；TTL 刚过又集体回源
    ③ 发版要靠 purge：每次发版都要全网清除 CDN 缓存，
       而 purge 是重操作（有延迟、有失败率），天天 purge 说明策略设计错了

方案 B：hash 文件名 + 长 TTL（app-8f3d2a.js + max-age=1 年）← ✅
  原理：
    构建时根据文件内容生成 hash（contenthash）
    内容变 → hash 变 → 全新 URL → CDN/浏览器视为新资源，必然回源一次
    内容不变 → hash 不变 → 永久命中缓存，零回源

  优势：
    ① 「缓存失效」从「按时间猜」变成「按内容确定」
    ② 命中率接近 100%（内容不变永远命中）
    ③ 发版不需要 purge：新版本是新的 URL，老版本自然过期
    ④ 回滚简单：把 index.html 指回旧 hash 即可，旧资源还在

  这是前端构建产物 + CDN 的**最佳实践**，任何静态资源分发都该抄这个模式

4. 缓存键与动态参数的坑 ​

text
缓存键（Cache Key）默认 = 完整 URL（含查询参数）

后果演示：
  请求 1：GET /api/news?t=1725000000
  请求 2：GET /api/news?t=1725000001
  → 两个不同的缓存键 → 两次回源 → 命中率归零，CDN 形同虚设

  再比如：URL 里带用户 ID、时间戳、随机数、追踪参数（utm_source 等）
  → 每个请求一个缓存键 → 缓存空间爆炸 + 命中率归零

解法：
  ① 动态参数挪到 Header / Cookie（不进 URL）
  ② 或明确配置 CDN「忽略指定查询参数」（如忽略 utm_* 、t）
  ③ 或把动态参数放在 hash 之后（`#` 后的部分不会发给服务器）

5. 发布流程 ​

text
① 构建
   npm run build → 产出 app-8f3d2a.js 等带 hash 的文件

② 上传（**先传资源，再传入口**）
   把新 hash 的资源上传到对象存储 / CDN 源站
   ⚠️ 顺序很重要：如果用户先拿到新 index.html，而新资源还没上传，
      会 404 → 白屏

③ 更新入口
   上传新的 index.html（指向新 hash 的资源）
   index.html 配置为 no-cache → 用户下次访问立即拿到新入口

④ 预热（可选，针对大促/大版本）
   主动请求一次关键资源，让各边缘节点提前缓存
   → 避免「突发流量首次访问全部未命中」打爆源站

⑤ 灰度与回滚
   灰度：按 IP/地域/Cookie 分流，1% → 10% → 100% 观察
   回滚：把 index.html 改回指向旧 hash 的资源（旧资源还在 CDN 上，未过期）
          → 回滚只需替换一个入口文件，秒级生效

⑥ 事故兜底
   如果真的缓存了错误内容：CDN 管理台 purge（全网清除）
   → 但记住：purge 是最后手段，不是日常手段

3. 三级缓存设计 ​

text
请求 → 本地缓存（命中 0.1 ms，未命中 ↓）
     → Redis（命中 1~2 ms，未命中 ↓）
     → MySQL（10 ms）→ 写回两级缓存

① 本地缓存（进程内，60 秒 TTL）
   放什么：TOP 1000 爆款商品（占 60% 流量）
   为什么：爆款高度集中，本地缓存能挡掉 60% 的请求，
           且**零网络开销**，是抗大促的第一道防线
   代价：更新不及时（60 秒内可能是旧价格）
         → 缓解：价格变更时通过消息广播通知各实例失效

② Redis 集中缓存（TTL 1 天 + 随机 6 小时）
   放什么：全量热点商品（不只是 TOP 1000）
   更新策略：Cache-Aside，改价格时「先更新库，再删缓存」
   高可用：Redis Cluster 分片（数据量 + 吞吐都需要），每主带一从

③ 数据库（MySQL 16 分片）
   真相源，只处理回源与写

热点 key 防击穿（爆款商品的缓存过期瞬间）：

text
问题：爆款商品（占单品 QPS 可能 5 万）缓存过期 → 5 万请求同时回源 → 打垮 DB

方案：**热点 key 永不过期 + 异步刷新**
  ① 识别热点：实时监控 key 访问频次，TOP N 自动标记为热点
  ② 热点 key 不设 TTL（物理不过期），value 里存「逻辑过期时间」
  ③ 请求发现逻辑过期 → 先返回旧值 + 触发异步刷新（加分布式锁，只有一个线程回源）
  → 用户永远拿到数据（可能旧几秒），数据库永远不会被击穿

  为什么不只用互斥锁：5 万个请求排队等锁，用户体验是「转圈 3 秒」
  而「返回旧值 + 异步刷新」是「立刻看到内容（价格可能晚 1 秒更新）」
  → 商品详情场景下，后者体验远好于前者

大促防雪崩：

text
① 错峰：TTL 加随机值（基础 1 天 + random(0, 6h)），避免批量过期
② 预热：大促开始前 1 小时，主动把 TOP 10 万商品的详情写入 Redis
        → 避免「零点流量涌入时全部未命中」
③ 兜底：本地缓存保留 60 秒旧数据，Redis 挂了仍能扛 60 秒
④ 挡墙：回源请求限流（超过阈值直接返回兜底数据或排队）
        → 宁可让用户看到「稍后重试」，也不能让数据库崩溃

4. 库存扣减：为什么不只靠缓存 ​

text
❌ 错误方案：库存放 Redis，用 DECR 扣减
  问题：Redis 是缓存，不是存储
  ① Redis 宕机/主从切换 → 未同步的扣减丢失 → **超卖**
  ② 缓存没有事务，扣减成功但订单创建失败 → 库存回不来 → **少卖**
  ③ 缓存与数据库不一致 → 对账时发现「Redis 里的才是真的」→ 数据漂移

✅ 正确方案：数据库扣减 + 缓存加速读

  方案 A（严谨，推荐）：
    UPDATE sku_stock
    SET stock = stock - 1
    WHERE sku_id = ? AND stock >= 1;
    -- 关键：WHERE 条件带 stock >= 1，由数据库的行锁保证原子性
    -- 返回影响行数 = 1 表示扣减成功，= 0 表示库存不足
    → 不超卖（数据库行锁 + 条件更新），不需要额外的分布式锁

  方案 B（高并发优化）：
    ① 大促前把库存「分段」：1 万件库存分成 100 段，每段 100 件
    ② 每段一个缓存 key，请求随机选一段扣减 → 把热点行锁打散成 100 个
    ③ 某段扣完就换下一段
    → 把单行锁竞争降低 100 倍

  方案 C（极致性能，秒杀场景）：
    ① Redis 预扣减（快速失败，挡掉 99% 的无效请求）
    ② 扣减成功的请求发到 MQ，异步创建订单 + 数据库最终扣减
    ③ 数据库是真相源，Redis 只是「快速过滤器」
    → 注意：这引入了最终一致，需要幂等和对账机制

  通用原则：
    **库存是强一致数据，真相源必须在数据库。**
    缓存可以用来加速读、快速失败、预扣减，但不能作为最终依据。
    缓存不一致 = 超卖 = 资损。

5. 大促预案（5 万 → 50 万 QPS，10 倍） ​

  ① 全链路压测，摸清单机容量（不要用「网上查的经验值」）

     → 连接池要配到能承受 1 万并发，否则排队成为瓶颈
