16 · ReAct 推理循环 ​

前置：上下文工程与压缩 · 预计：1.5~2 小时

概念简介 ​

第 01 篇给出的最小骨架有个正式名字:ReAct(Synergizing Reasoning and Acting),2022 年由 Yao 等人提出。它解决一个很具体的问题:纯推理(CoT)容易幻觉,纯行动(直接调工具)容易瞎撞,把两者交织起来效果显著好于任一单独方案。

ReAct 的形式很简单,要求模型每一步输出一个三元组:Thought(我在想什么)→ Action(我要做什么)→ Observation(外部世界返回了什么)。Thought 不是给用户看的装饰,它是模型的草稿纸:把中间推理外显成 token,下一步就能读到自己刚才的判断,在长链条任务里不迷失。

但学术范式和工程实现之间隔着一条鸿沟。论文里模型会乖乖输出 Action: search["xxx"],生产里它会包 markdown 代码块、会多打一个全角冒号、会在 JSON 里写注释、会连续三次用同样的参数调同一个工具。ReAct 的全部工程难点,在于「如何让这个循环在模型不守规矩时依然收敛」。

核心内容 ​

1. 三元组:Thought / Action / Observation ​

元素谁产生作用工程关注点
Thought模型外显中间推理,决定下一步要不要展示给用户;要不要长期留在上下文
Action模型选择工具 + 给出参数解析健壮性;参数校验;未知工具怎么办
Observation外部环境工具执行的真实结果格式裁剪;错误信息要可读

关键认知:Observation 来自真实世界,不由模型编造。这是 ReAct 抑制幻觉的机制——推理链条里被强制插入了不可伪造的事实。工具说「文件不存在」就是不存在,模型不能靠再想一下把它想成存在。

2. 为什么「边说边做」优于「先想完再做」 ​

直觉上先规划完整步骤更理性,实践里恰恰相反:

  • 规划依赖未知信息。你不知道搜索会返回什么,所以第二步及以后的规划大概率是错的。每一步都重新看一眼现场,比一开始就押注全部路径稳。
  • 错误能早暴露。交织式第一步错了,第二步的 Observation 就会打脸;批处理式要等全部执行完才发现跑偏。
  • 上下文更省。交织式只需要保留「当前状态 + 下一步」。

代价也要说清楚:交织式没有全局视角,无法回头,容易陷进局部最优。ReAct 的适用区间是**路径不确定但步数不多(3~10 步)**的任务;复杂长任务要先规划,那是第 17 篇的主题。

3. 手写 ReAct 循环 ​

用原生 openai SDK 实现,格式约定用最朴素的文本协议(比 JSON 更容易让小模型遵守):

python
# pip install openai tiktoken
import json, re
from openai import OpenAI

client = OpenAI()

def search(query: str) -> str:
    """search(query): 搜索网页,返回前 3 条摘要"""
    return f"[模拟结果] 关于「{query}」的资料..."

def calc(expr: str) -> str:
    """calc(expr): 计算数学表达式"""
    return str(eval(expr, {"__builtins__": {}}))   # 生产务必换 AST 安全求值

TOOLS = {"search": search, "calc": calc}

SYSTEM = """你是一个用 ReAct 格式工作的助手。每次只走一步,严格输出:

Thought: 你的推理
Action: 工具名({"参数": "值"})

工具结果会以 Observation: 开头回给你。任务完成时输出:
Thought: 已有答案
Answer: 最终回答

可用工具:search(query)、calc(expr)。
"""

def react(task: str, max_steps: int = 8) -> str:
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user", "content": task}]

    for _ in range(max_steps):
        reply = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=messages,
            temperature=0.0,        # 格式敏感任务,必须是 0
            stop=["Observation:"],  # 防止模型自己幻觉出 Observation
        ).choices[0].message.content
        messages.append({"role": "assistant", "content": reply})

        if m := re.search(r"Answer:\s*(.+)", reply, re.S):   # 1) 结束条件
            return m.group(1).strip()

        action = re.search(r"Action:\s*(\w+)\s*\((.*?)\)\s*$", reply, re.S | re.M)
        if not action:                                        # 2) 格式错误也回灌
            messages.append({"role": "user", "content":
                "Observation: 格式错误。必须输出一行 Action: 或 Answer:。"})
            continue

        try:
            name, raw = action.group(1), action.group(2)
            result = TOOLS[name](**json.loads(raw))
        except KeyError:
            result = f"错误:没有名为 {name} 的工具,可用:{list(TOOLS)}"
        except json.JSONDecodeError as e:
            result = f"错误:参数不是合法 JSON({e})"
        except Exception as e:        # 3) 工具异常转成观察,绝不抛出循环外
            result = f"错误:工具执行失败:{type(e).__name__}: {e}"

        messages.append({"role": "user", "content": f"Observation: {result}"})

    return "超出步数上限,任务未完成"    # 4) 必须有熔断

四个工程细节:stop=["Observation:"] 防止模型自编工具结果;工具异常转 Observation 而非崩溃;格式错误回灌让模型自我纠正;末尾必须有熔断返回值。

4. 解析健壮性:模型输出永远不守规矩 ​

上面的正则在生产里会漏,常见的违规形态要逐条兜:

python
import re, json, ast

def parse_action(text: str):
    """宽容解析 Action,失败返回 None"""
    text = re.sub(r"```(?:\w+)?|```", "", text)     # 形态 1:包了 markdown 代码块
    text = text.replace("：", ":").replace("（", "(").replace("）", ")")
    m = re.search(r"Action\s*:\s*(\w+)\s*\((.*?)\)\s*$", text, re.S | re.M)
    if not m:
        return None
    name, raw = m.group(1), m.group(2).strip()
    try:
        return name, json.loads(raw)
    except json.JSONDecodeError:                    # 形态 2:单引号、尾随逗号
        try:
            return name, ast.literal_eval(raw)
        except (ValueError, SyntaxError):
            return None

判断标准很直接:解析失败率超过 1% 就该换方案。优先级:① 换原生 Function Calling(第 06 篇),模型被 Schema 约束,最稳;② 换 response_format 结构化输出;③ 保留文本协议,但加一个修复器——解析失败时把原始输出和报错丢回便宜模型重写这一步。

默认建议:能用原生 Tool Calling 就别手写文本协议。ReAct 文本格式的价值主要在教学、以及兼容不支持 function calling 的小模型。

5. 死循环检测与双预算熔断 ​

Agent 最烧钱的事故不是答错,是转圈:同一工具、同样参数,重复几十次。

python
from collections import Counter
import tiktoken

def run_guarded(task, max_steps=8, token_budget=20000, repeat_limit=3):
    messages = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": task}]
    enc, seen, used = tiktoken.get_encoding("cl100k_base"), Counter(), 0

    for _ in range(max_steps):
        reply = call_llm(messages)                    # 同上的 chat 调用
        used += len(enc.encode(reply))
        messages.append({"role": "assistant", "content": reply})

        parsed = parse_action(reply)
        if parsed:
            name, args = parsed
            # 动作指纹必须含参数,否则换个措辞就不算重复了
            fp = f"{name}:{json.dumps(args, sort_keys=True, ensure_ascii=False)}"
            seen[fp] += 1
            if seen[fp] >= repeat_limit:              # 先警告一次,再强制收口
                messages.append({"role": "user", "content":
                    f"Observation: 你已用相同参数调用 {name} 三次,结果不会变。"
                    "请换思路,或基于已有信息输出 Answer。"})
                if seen[fp] > repeat_limit:
                    return "检测到重复动作,已终止", "repeat_abort"
            result = execute(name, args)              # 带异常捕获的执行
        else:
            result = "格式错误,请输出 Action: 工具名({...})。"
            seen["__parse_fail__"] += 1
            if seen["__parse_fail__"] >= 3:
                return "连续三次解析失败", "parse_abort"

        messages.append({"role": "user", "content": f"Observation: {result}"})
        used += len(enc.encode(str(result)))
        if used > token_budget * 0.8:                 # 到阈值前压缩,不是等它爆
            messages = compress(messages)             # 第 15 篇:历史摘要/裁剪
        if used > token_budget:
            return "超出 token 预算", "token_abort"

    return "超出步数上限", "step_abort"

终止原因(ok/step_abort/token_abort/repeat_abort/parse_abort)必须落日志,它们是调优最重要的信号:重复终止说明工具设计有问题,解析终止说明提示词有问题。参数经验:max_steps 问答类 5~8、代码修改类 15~25、深度研究类 30+;repeat_limit=3 允许一次重试;token_budget 按可接受的成本倒推。

6. LangGraph 里的 ReAct ​

生产不用手写,官方 prebuilt 实现:

python
# pip install langgraph langchain-openai
from langgraph.prebuilt import create_react_agent
from langgraph.errors import GraphRecursionError
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool

@tool
def search(query: str) -> str:
    """搜索网页并返回摘要。"""
    return f"[模拟结果] {query}"

agent = create_react_agent(
    model=ChatOpenAI(model="gpt-4o-mini", temperature=0),
    tools=[search],
    prompt="你是一个严谨的研究助手。不确定时优先搜索,不要编造。",
)

try:
    # recursion_limit 就是步数熔断,默认 25,必须显式设置
    out = agent.invoke({"messages": [("user", "checkpointer 有什么用?")]},
                       config={"recursion_limit": 12})
except GraphRecursionError:
    # 触顶不是异常,是「该降级」的业务信号
    out = {"answer": "这个问题需要更多步骤,先把我已知的整理给你..."}

create_react_agent 内部就是「模型节点 ⇄ 工具节点」两节点图加条件边:有 tool_calls 就去工具节点,否则结束。理解这点后,第 20 篇的显式状态机就是它的泛化。

常见陷阱 ​

  • 把 Thought 原样展示给用户:里面有模型的犹豫、猜测、甚至错误假设。要展示就单独开「思考中」通道并标注是过程不是结论(第 21 篇讲流式渲染)。
  • 让模型自己写 Observation:不加 stop 时,模型会顺着 Action: search(...) 自己续写「Observation: 找到了...」,整个循环变成自娱自乐。这是新手最隐蔽的 bug。
  • 工具异常直接抛出:一次网络抖动炸掉整个 Agent。工具层异常必须转成 Observation,给模型换路的机会。
  • 只设步数不设 token 预算:8 步循环,每步塞 50K 网页全文,一样烧爆。两个预算都要有。
  • 死循环检测只看工具名:指纹必须包含参数,换个措辞就不算重复的检测等于没做。
  • 步数上限设 50 然后放任:上限是保险丝不是配置。正常任务经常触顶,说明该引入规划(第 17 篇),而不是调大上限。

练习建议 ​

  1. 跑通并打破它:把手写循环跑起来,故意给一个「搜不到答案」的问题,观察它如何自我纠正、如何撞上重复检测,并把 messages 完整打印读一遍。
  2. 实现格式修复器:解析失败时调用一次便宜模型重写这一步再重新解析,统计修复成功率。
  3. 对比两种实现:20 个任务分别用手写循环和 create_react_agent 跑,对比成功率、平均步数、token 消耗。

前端对照 ​

前端概念Agent 对应物说明
while 事件循环 / rAFAgent 主循环都是「取状态 → 执行 → 回写状态」的迭代结构
reducer 的 actionAction一个「意图 + 参数」的描述对象,不直接执行副作用
useEffect 依赖数组动作指纹去重依赖没变就别跑第二次,否则死循环
React Error Boundaryexcept -> Observation局部错误就地兜住并转成可渲染状态,不炸整个应用
虚拟列表的窗口回收token 预算 80% 压缩到阈值前主动回收,而不是等内存爆
AbortController步数/token 熔断主动取消一个失控的异步过程

最值得记住的一条:前端里重复渲染同一个组件最多是掉帧,Agent 里重复调用同一个工具是真金白银。前端同学对死循环的敏感度通常停留在「页面卡死」,在 Agent 里必须升级成「每一轮都是一次计费的 API 调用」。
