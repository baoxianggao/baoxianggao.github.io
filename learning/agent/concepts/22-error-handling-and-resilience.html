22 · 错误处理与韧性设计 ​

前置：流式输出与前端集成 · 预计：2 小时

概念简介 ​

第 07 篇和第 16 篇讲过一个反直觉的做法:工具报错不要抛异常,要当成观察回灌给模型,让它换个参数或换条路。那是「模型能自己修的失败」。这一篇讲另一类——重试也修不好、只能靠工程兜底的失败:限流、超时、第三方服务挂掉、无权限、数据不存在。 Agent 比普通服务更容易失败,原因很直白:一次用户请求会依次穿过模型 API、若干个工具、数据库和第三方服务,它是一条长链路,每一步都是新的失败点。更麻烦的是它是有状态的多步过程——第 5 步挂了,前 4 步的检索结果、已生成的内容、已执行成功的写操作,全都不该被丢掉。

所以韧性设计的目标不是「永不失败」,而是三件事:用户拿到降级结果而不是 500;烧掉的钱和已完成的步骤不白费;失败原因能定位,而不是日志里只留一行 NoneType。

核心内容 ​

1. 先分类:三类错误的处理方式完全不同 ​

混在一起处理是新手最典型的错误。笼统地 except Exception: retry 会把「余额不足」重试三次,把「限流」打成 500。

层典型错误是否可重试谁来处理
模型侧限流 429、超时、5xx、审核拒绝、上下文超长限流/超时/5xx 可;审核拒绝与超长不可(前者换了模型也一样,后者要先压缩,见第 15 篇)重试 + 降级模型
工具侧参数校验失败、执行异常、目标服务超时、结果为空参数错不可重试(重试也一样错);网络类可回灌模型 + 换工具
业务侧无权限、数据不存在、余额不足、超出配额一律不可重试直接终止,明确告知

代码上用带元数据的异常层次表达这些差异,后面所有策略都读这些字段:

python
class AgentError(Exception):
    """所有 Agent 错误的基类,三个字段决定后面怎么处理它"""
    def __init__(self, layer: str, user_message: str, retryable: bool = False):
        super().__init__(user_message)
        self.layer, self.user_message, self.retryable = layer, user_message, retryable

class RateLimited(AgentError):                 # 可重试:等一会儿再来
    def __init__(self, retry_after: float):
        super().__init__("model", "现在请求有点多,请稍后再试", retryable=True)
class ToolFailed(AgentError):                  # 可重试:网络抖动重试一次通常就好
    def __init__(self, tool: str, detail: str):
        super().__init__("tool", f"「{tool}」暂时不可用", retryable=True)
        self.detail = detail          # 详细原因只进日志,不进 user_message

业务侧的 NoPermission、NotFound、QuotaExceeded 写法相同,一律 retryable=False——重试不会让权限凭空出现。关键设计:user_message 和诊断信息必须分开。前者是产品文案,后者只进日志和 trace。这条纪律能同时解决安全和可维护性问题。

2. 分层兜底:节点内回灌,图外层兜底 ​

第一层兜底在节点内部(工具异常转成观察,让模型自己修),第二层在图的外层(模型修不好、或异常发生在模型调用本身时,由编排层决定降级还是终止):

python
def tool_node(state):          # 工具异常就地转成观察,让模型自己修
    results = []
    for call in state["messages"][-1].tool_calls:
        try:
            out = dispatch(call)
        except AgentError as e:      # 把「能不能重试、该怎么改」告诉模型
            out = {"error": e.detail or str(e), "hint": "可重试" if e.retryable
                   else "不要重复相同调用,换一种方式"}
        except Exception as e:                        # 兜住所有未分类异常
            out = {"error": f"{type(e).__name__}: {e}", "hint": "工具异常,可换其他工具"}
        results.append({"role": "tool", "tool_call_id": call.id,
                        "content": json.dumps(out, ensure_ascii=False)})
    return {"messages": results}

async def run_agent(task: str, thread_id: str) -> RunOutcome:
    steps = []                     # 已完成的步骤:失败时它们仍有价值
    cfg = {"configurable": {"thread_id": thread_id}}
    try:
        async for event in graph.astream({"messages": [("user", task)]}, config=cfg):
            steps.append(next(iter(event)))
    except AgentError as e:        # 模型层无法自愈,进入外层降级
        return await degrade(task, steps, e)
    return RunOutcome(answer=last_answer, steps_done=steps)

第二层是外层编排,判断标准:能在节点内修的就地修,修不了的冒泡到外层降级。不要在每个节点写 try: ... except: return "抱歉出错了"——那会让上层完全不知道发生了什么,也无法区分「答完了」和「没答完」。

3. 重试的边界与幂等 ​

重试是成本最低的韧性手段,也是最容易造成事故的手段。判断标准只有一条:这个操作重复执行两次,结果是否一致?

python
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception
# 只重试标记为 retryable 的错误;reraise 让上层还能拿到原始异常类型
@retry(retry=retry_if_exception(lambda e: isinstance(e, AgentError) and e.retryable),
       stop=stop_after_attempt(3),                          # 再多重试只会放大故障
       wait=wait_exponential(multiplier=1, min=1, max=10),  # 退避 1/2/4s,封顶 10s
       reraise=True)
async def call_model(messages):
    return await client.chat.completions.create(model="gpt-4o-mini", messages=messages)

参数为什么这么设:3 次是经验值——1 次不够覆盖偶发抖动,5 次以上在真实故障(服务整体不可用)时会把压力叠加到已经过载的下游;指数退避必须有上限,否则第 5 次可能睡几分钟;reraise=True 让上层的分类逻辑还能拿到原始异常类型。

写操作绝对不能靠重试兜底。扣款、发邮件、创建工单,重试前必须先确认前一次到底成了没有:

python
import hashlib, json

# 幂等键 = hash(工具名 + 参数 + 用户),sort_keys 保证参数顺序不影响结果
key = hashlib.sha256(json.dumps({"tool": tool, "args": args, "user": uid},
                                sort_keys=True).encode()).hexdigest()

async def execute_write(key: str, fn, **args):
    if not await store.setnx(f"idem:{key}", "running", ttl=600):    # 原子占用
        return {"error": "相同请求正在处理或已处理,请勿重复提交"}
    try:
        result = await fn(**args)                                   # 真正执行
        await store.set(f"idem:{key}", json.dumps(result), ttl=86400)  # 记住结果,重放时返回
    except Exception:
        await store.delete(f"idem:{key}")   # 失败要释放,否则这个键永久堵死
        raise
    return result

补偿(saga)是幂等失效时的最后一道防线:为每个不可逆操作预先写好反向操作(创建订单 → 取消订单),失败时按相反顺序执行。代价是双倍代码和「补偿本身也可能失败」的新问题,所以优先级永远是「能幂等就不要用补偿」。

4. 超时、部分结果与断路器 ​

python
# 部分结果:外层返回值至少带 steps_done(已完成步骤,仍有价值)、degraded
# (降级过的步骤,交给前端标注)、error(面向用户的原因)三个字段
async def with_timeout(coro, seconds: float, default):   # 超时 = 「这一步没做完」
    try:
        return await asyncio.wait_for(coro, seconds)
    except asyncio.TimeoutError:
        return default

tool_out = await with_timeout(fetch_docs(q), 10.0, default={"error": "检索超时"})   # 三档:工具 10s、模型调用 60s、任务 300s

三档超时的取值逻辑:工具超时按该工具 P99 的 2 倍设;模型超时按「能接受的首字延迟 + 预期输出长度 × 单 token 耗时」估;任务总超时按产品承诺倒推。任何一档缺失,都会退化成用户手动刷新。

部分结果是最容易被忽略的一点:第 4 步超时不应该让前 3 步的成果消失。steps_done 就是为此存在的——前端据此渲染「已完成 3/5 步,以下是已完成部分」。

断路器用于防止「下游已经挂了,你还在持续调用」:

python
import time

class CircuitBreaker:        # 连续失败 threshold 次后熔断,冷却期内快速失败
    def __init__(self, threshold: int = 5, cooldown: float = 30.0):
        self.threshold, self.cooldown, self.failures = threshold, cooldown, 0
        self.opened_at = 0.0

    def call(self, fn, *args, **kwargs):
        # 冷却结束后自动半开:放一个请求去试探
        if time.time() - self.opened_at < self.cooldown:
            raise ToolFailed(fn.__name__, "熔断中,快速失败")
        try:
            result = fn(*args, **kwargs)
        except Exception:
            self.failures += 1
            if self.failures >= self.threshold:
                self.opened_at = time.time()          # 达到阈值,开启熔断
            raise
        self.failures = 0                             # 成功即清零
        return result

断路器的价值不是「少调几次」,而是让上游快速拿到失败信号从而走降级路径,而不是陪着下游一起卡到超时。它必须按「工具实例」而非全局共享。

5. 降级策略:换模型、换工具、保守回答 ​

python
from langchain_openai import ChatOpenAI

# with_fallbacks 在主模型抛异常时依次降级
model = ChatOpenAI(model="gpt-4o", temperature=0).with_fallbacks(
    [ChatOpenAI(model="gpt-4o-mini", temperature=0)])

三档降级,按代价从低到高:

  1. 换更小的模型:能力下降但任务还能完成,适合分类、抽取、格式化。注意 with_fallbacks 不区分错误类型——审核拒绝、上下文超长这类「换模型也一样」的错误不该进降级链,否则一次审核拒绝就会静默把整个系统切到小模型。
  2. 换工具:搜索引擎挂了换成向量库检索(第 12、13 篇),都挂了就用缓存。
  3. 降级为保守回答:什么都用不了时,约束模型基于已有信息作答:以下工具当前不可用:{failed_tools}。请基于已有信息回答:1. 明确说明哪些内容未能核实;2. 不要猜测具体数值、日期、价格;3. 信息不足以回答时,直接说无法完成并说明原因。

第 3 档是最后防线,价值在于把「系统挂了」变成「信息不全但诚实的回答」。宁可说「这部分我没查到」,也别让模型编个数字填上。

6. 向用户暴露进度的正确姿势 ​

python
# 未分类异常一律泛化;response 里只有 code(聚合用)+ 文案 + trace_id(报障用)
msg = exc.user_message if isinstance(exc, AgentError) else "服务暂时不可用"
emit({"type": "error", "code": type(exc).__name__, "message": msg, "trace_id": tid})
  • 不要暴露内部堆栈。第 21 篇的 error 事件里只放 code + 面向用户的 message + trace_id,诊断信息走日志。
  • 进度要说「做到了哪一步」,不要说「正在处理」。「已检索 3 篇文档,正在核对数据」才是有用信息,第 21 篇的 tool_call/tool_result 事件正是为此设计的。
  • 降级要显式告知。静默降级是最危险的设计——用户以为拿到的是完整答案,实际是残缺的。发一个 degraded 标记让前端标注「部分信息未能核实」。

常见陷阱 ​

  • 笼统重试:except Exception: retry(3)。把「无权限」重试三次,把「参数错」重试三次,唯一的效果是放大故障和烧钱。重试前必须分类。
  • 写操作不加幂等键:网络超时后重试,用户被扣了两次款。所有会产生外部副作用的工具都必须过幂等表。
  • 静默降级或全局熔断:换到小模型、跳过工具却不告诉用户,用户以为答案是完整的;断路器按全局而非按工具实例共享,一个工具挂了熔断所有工具,把局部故障放大成全局故障。

练习建议 ​

  1. 故障注入:给三个工具分别注入「超时」「500」「参数校验失败」,观察哪些自己恢复了、哪些炸了、哪些静默给出了错误答案。
  2. 幂等实验:写一个会扣款的模拟工具,在「执行成功但响应超时」的时序下重试,验证幂等键挡住了第二次扣款;去掉再跑一次。
  3. 降级对照:同一批任务,对比「失败即终止」与「三档降级」两种策略的完成率、用户满意度和 token 成本。

前端对照 ​

前端概念Agent 对应物说明
React Error Boundary分层兜底就近兜住子树错误,兜不住才冒泡
请求重试 + 指数退避tenacity retry退避必须有上限,且只重试幂等请求
表单重复提交拦截幂等键POST 双击两次不能创建两条记录
乐观更新回滚补偿(saga)回滚本身也可能失败,能幂等就别用补偿

最需要扭转的一个习惯:前端的错误处理终点是「展示一个错误提示」,Agent 的错误处理终点是「给出一个降级后的可用结果」。前端可以合理地让用户刷新重试,因为刷新的成本几乎为零;Agent 刷新一次意味着重跑整条链路、重新烧一遍钱,而且大概率得到同样的失败。
