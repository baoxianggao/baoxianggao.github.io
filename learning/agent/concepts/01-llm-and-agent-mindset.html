01 · LLM 与 Agent 心智模型 ​

前置：无 · 预计：1.5~2 小时

概念简介 ​

绝大多数人第一次接触大模型,是从聊天框开始的:输入一个问题,得到一段回答。这个心智模型会一直拖累你——你会不自觉地把 Agent 理解成「会聊天的机器人」,然后在工程实践中反复撞墙。

真正的分界在这里:ChatBot 的目标是生成一段文本,Agent 的目标是完成一个任务。为了完成任务,Agent 必须能调用外部世界的能力(工具)、能看到自己行动的结果(观察)、能根据结果决定下一步(循环)。LLM 在其中扮演的不是「回答者」,而是「决策者」——它在每一步判断「现在该做什么」。

本篇不写代码框架,只做一件事:把「LLM 是什么」和「Agent 是什么」这两件事在脑子里拆清楚。后面 28 篇都是这个心智模型的展开。

核心内容 ​

1. LLM 的本质:一个超强的「下一个词预测器」 ​

剥掉所有包装,LLM 做的事情只有一件:给定前文,预测下一个最可能出现的 token。训练目标就是这么朴素。

python
# 概念示意:LLM 的底层接口其实非常窄
# 输入:一段文本(下文称 prompt)
# 输出:续写的文本
#
# 你看到的「对话」「推理」「写代码」,全部建立在这个能力之上
prompt = "中国的首都是"
# 模型续写 -> "北京。它是全国的政治中心..."

理解这一点有三个直接推论:

  • 它没有「记忆」。所谓记忆,是把历史对话重新拼进输入。对话越长,输入越长。
  • 它不会「查资料」。所有事实都压缩在参数里,过期、失真、编造(幻觉)都由这个机制导致。
  • 它不会「执行」。它只能输出文本。想让它真的发邮件、查数据库,必须在它外面接一层执行器——这就是工具。

把 LLM 想成一个「被关在盒子里、只能递纸条进出的聪明人」。Agent 工程做的所有事情,本质上都是在设计这张纸条怎么写、怎么读、怎么根据回信决定下一张纸条。

2. Token:计费、限流与截断的统一单位 ​

模型不按「字」或「词」处理文本,而是按 token。token 是子词(subword)级别的片段。

python
# 安装:pip install tiktoken
import tiktoken

enc = tiktoken.get_encoding("cl100k_base")  # GPT-4 / GPT-4o 系列

text = "Agent 开发是一个系统工程"
ids = enc.encode(text)

print(f"文本: {text}")
print(f"token 数: {len(ids)}")          # 通常远少于字数
print(f"token 片段: {[enc.decode([i]) for i in ids]}")

为什么这件事重要:

维度影响
计费输入输出都按 token 收费,长上下文直接烧钱
上下文窗口模型一次能处理的 token 上限(如 128K、200K、1M)
截断超出窗口的内容会被静默丢弃,导致「前面说的话它忘了」
延迟输出 token 是逐个生成的,输出越长越慢

工程含义:上下文是一种稀缺资源。Agent 设计里大量的工作(记忆压缩、检索裁剪、历史摘要)都是围绕「如何在有限的 token 预算里塞进最有价值的信息」展开的。这是第 15 篇的主题。

3. 采样参数:控制输出的确定性 ​

同一段 prompt,每次调用结果可能不同,因为模型输出的是概率分布,再按策略采样。

python
from openai import OpenAI

client = OpenAI()

resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "用一句话解释什么是 Agent"}],
    temperature=0.0,   # 0 = 每次几乎一致;1+ = 更有创意但更飘
    top_p=1.0,         # 核采样:只从累计概率达到 p 的候选里采样
    max_tokens=200,    # 输出上限,防止失控
    seed=42,           # 固定种子可提升可复现性(不保证完全一致)
)
print(resp.choices[0].message.content)

选型直觉:

  • temperature = 0:用于分类、抽取、格式化输出、工具参数生成——一切要求稳定的场景。
  • temperature = 0.7~1.0:用于写作、头脑风暴、生成多样性候选。
  • 工具调用场景一律用低温。参数一旦飘,解析就失败,这是新手最常见的稳定性问题。

4. Agent 与 ChatBot 的分界:多出来的那三个东西 ​

一个最小可用的 Agent,比 ChatBot 多三样东西:

组件作用类比
工具(Tools)让模型能作用于外部世界手脚
观察(Observation)把工具执行结果回灌给模型眼睛
循环(Loop)模型根据观察决定下一步,直到任务完成意志
用户输入
   │
   ▼
┌──────────────────────────────────────┐
│              Agent 循环               │
│                                       │
│  LLM 决策 ──> 选择工具 ──> 执行工具   │
│     ▲                                 │
│     └────── 观察结果回灌 ─────────────┘
│                                       │
│  直到模型认为「任务完成」→ 输出最终答案 │
└──────────────────────────────────────┘
   │
   ▼
最终输出

ChatBot 是这条链路的「零次循环」特例:直接输出,不看结果,不迭代。

5. 一个 30 行的 Agent 骨架(先用伪代码建立直觉) ​

不依赖任何框架,先看清楚最小闭环长什么样:

python
# 最小 Agent 骨架(示意,不可直接运行)
def run_agent(user_task: str, tools: dict, llm, max_steps: int = 10):
    messages = [
        {"role": "system", "content": "你是一个能使用工具的助手。需要时调用工具,不需要时直接回答。"},
        {"role": "user", "content": user_task},
    ]

    for step in range(max_steps):                 # 循环:关键差异点
        reply = llm.chat(messages, tools=tools)   # 1. 让模型决策

        if not reply.tool_calls:                  # 2. 模型决定不调工具 -> 任务完成
            return reply.content

        for call in reply.tool_calls:             # 3. 执行工具
            result = tools[call.name](**call.arguments)
            messages.append({                     # 4. 把结果作为观察回灌
                "role": "tool",
                "name": call.name,
                "content": str(result),
            })

    return "超出步数上限,任务可能未完成"            # 5. 必须有熔断

这段代码里藏着 Agent 工程的全部核心议题:

  • for step in range(max_steps) → 循环控制与熔断(第 16、27 篇)
  • reply.tool_calls → Function Calling(第 06 篇)
  • tools[call.name](...) → 工具设计与错误处理(第 07 篇)
  • messages.append(...) → 上下文与记忆管理(第 14、15 篇)
  • str(result) → 观察的格式与裁剪(第 15 篇)

后面每一篇,都是把这个骨架的某一个环节做深、做稳、做可靠。

6. 能力边界:什么时候不该用 Agent ​

这是最容易被跳过、但最该先想清楚的一节。Agent 不是万能的。

适合用 Agent 的任务:

  • 路径不确定,需要多步探索(如「帮我查一下这个报错的原因并修复」)
  • 需要组合多种工具/数据源
  • 容忍一定的不确定性和耗时
  • 有明确的完成判据

不适合用 Agent 的任务:

  • 路径完全固定 → 直接写传统代码,更快更便宜更可靠
  • 要求 100% 确定性 → LLM 是概率系统,做不到
  • 延迟敏感(< 500ms)→ 多轮循环天然慢
  • 单次成本敏感的超高调用量场景

一个实用的判断标准:如果这件事你能写清楚 if-else,就不要用 Agent。 Agent 的价值在于处理「你写不出 if-else」的部分。

常见陷阱 ​

  • 把 Agent 当 ChatBot 用:只做单轮问答,却付出了多轮复杂度的代价。先问「这个任务真的需要循环和工具吗」。
  • 忽视上下文成本:无脑把整个对话历史、整个文档塞进 prompt。上下文越长越贵、越慢,而且中间部分容易被模型「忽略」(lost in the middle 现象)。
  • temperature 默认值直接上生产:很多 SDK 默认 0.7~1.0,工具参数生成会飘。工具调用场景务必显式设为 0。
  • 没有熔断:Agent 陷入「调用工具 → 结果不满意 → 再调用」的死循环,一次请求烧掉大量 token。步数上限和超时是必需项。
  • 混淆「模型的知识」和「系统的知识」:模型不知道你的数据库里有什么。它只知道你放进上下文里的东西。

练习建议 ​

  1. token 直觉训练:用 tiktoken 统计一段 1000 字中文、一段 1000 行代码的 token 数,感受它们的比例差异。再算算 128K 上下文大概能装多少。
  2. temperature 对比实验:同一个抽取任务(如「从这段文字里提取人名和日期,输出 JSON」),分别用 temperature=0 和 1.0 各跑 10 次,统计格式正确率。
  3. 手写一个 3 工具 Agent:只用官方 SDK(不用框架),实现一个能查天气、能算数学、能查词典的 Agent,跑通上面的骨架代码,体会「观察回灌」这一步发生了什么。

前端对照 ​

前端概念Agent 对应物说明
事件循环Agent 主循环都是「取一个任务 → 执行 → 回到循环」的结构
副作用(API 调用)工具调用组件不直接改数据,交给外部;LLM 不直接执行,交给工具
statemessages / 上下文整个 Agent 的「状态」就是那一条 messages 数组
受控组件结构化输出不让模型自由发挥,用 Schema 约束输出形状
防抖/节流步数上限、超时熔断防止失控的兜底机制
加载态/流式渲染流式输出逐 token 返回,前端增量渲染(第 21 篇)

一个关键差异值得记住:前端的状态是可枚举、可断言的;Agent 的状态是一条会不断增长的文本。前端调试可以打断点看变量,Agent 调试只能读 messages 的完整内容——这就是为什么可观测性(第 24 篇)在这个领域格外重要。
