13 · 检索质量优化 ​

前置：RAG 基础流水线 · 预计：2 小时

概念简介 ​

第 12 篇给了一条能跑通的 RAG 流水线,然后留了个尾巴:它经常召回不准。用户的词和文档的词不重合时查不到、错误码和专有名词查不到、明明库里有答案却排在第 30 位。这些都是基础 RAG 的固有缺陷,不是配置不当。

本篇讲怎么修。但在讲具体手段之前必须先说清楚一件事:优化的前提是能测量。没有标注集和指标,「我加了个 rerank,感觉好多了」是毫无价值的判断——你无法区分真实提升和运气,也无法在下次改动引入回退时发现它。所以本篇的结构是「先诊断、再优化、全程有指标」。

核心内容 ​

1. 先诊断:召回差通常差在哪一步 ​

所有优化之前,先做一个二分判断:正确的块到底有没有被召回来。

python
def diagnose(store, question: str, gold_ids: set[str], k: int = 50) -> dict:
    """k 故意取大:这一步只关心「在不在」,不关心「排第几」。"""
    hits = store.similarity_search(question, k=k)
    ids = [h.metadata.get("chunk_id", "") for h in hits]
    ranks = [i for i, cid in enumerate(ids, 1) if cid in gold_ids]
    return {"in_top_k": bool(ranks), "best_rank": ranks[0] if ranks else None}
  • in_top_k=False(k=50 都召不回) → 召回问题。答案块的向量和查询就是不像,排序手段救不了,要去改切分、改查询、加关键词路。
  • best_rank 在 1~5 → 检索没问题,别折腾检索了,去看 prompt 和生成。
  • best_rank 在 10~50 → 排序问题,这是 rerank 的用武之地。

四类根因与对应手段:

症状根因对策
用词不同,意思相同查询和文档不在同一套词表查询改写 / HyDE
错误码、专有名词查不到向量不擅长精确匹配BM25 混合检索
答案被切碎在多个块里切分策略父子块 / 调整 chunk size
能召回但排得靠后双编码器精度不足rerank 精排

2. 查询改写与 HyDE:让查询去靠近文档 ​

python
from openai import OpenAI
client = OpenAI()

def multi_query(q: str, n: int = 3) -> list[str]:
    """多查询改写:同一个意图的几种说法,各自检索后合并去重。"""
    r = client.chat.completions.create(model="gpt-4o-mini", temperature=0, messages=[{
        "role": "user",
        "content": f"把下面的问题改写成 {n} 个语义相同但措辞不同的检索查询,每行一个,不要编号:\n{q}"}])
    return [x.strip() for x in r.choices[0].message.content.splitlines() if x.strip()]

def hyde(q: str) -> str:
    """HyDE:先让模型编一段「假答案」,用假答案去检索。"""
    r = client.chat.completions.create(model="gpt-4o-mini", temperature=0, messages=[{
        "role": "user",
        "content": f"假设你是文档作者,写一段 100 字以内能直接回答下面问题的内容,不要说『根据文档』:\n{q}"}])
    return r.choices[0].message.content

原理一句话:文档是陈述句,问题是疑问句,两者的向量天然有偏差。改写和 HyDE 都是把「问句」往「陈述」的方向推。假答案在用词上比原始提问更接近真实文档,所以能命中。

工程判断:

  • HyDE 更便宜:1 次 LLM + 1 次 embedding;多查询是 1 次 LLM + N 次检索。
  • HyDE 对导航类查询有害。用户问「退款政策在哪一章」,模型编出的假答案会描述退款政策的具体内容,反而把检索带偏。多查询在这种场景更安全。
  • 两者都必须配去重:三个查询召回同一批块等于没做,合并后按 chunk_id 去重再融合排序。
  • 简单问题别用。多一次 LLM 调用换 200ms 延迟,对「退款要几天」这种直白问题纯属浪费。按查询复杂度路由:短查询直检,长/复杂查询才改写。

3. 混合检索:BM25 补上向量不擅长的精确匹配 ​

python
import jieba
from rank_bm25 import BM25Okapi

class BM25:
    def __init__(self, texts: list[str], ids: list[str]):
        self.ids = ids
        # 中文必须分词:不分词的话整句话会被当成一个「词」,BM25 直接失效
        self.bm25 = BM25Okapi([list(jieba.cut(t)) for t in texts])

    def search(self, query: str, k: int = 10) -> list[str]:
        scores = self.bm25.get_scores(list(jieba.cut(query)))
        return [self.ids[i] for i in sorted(range(len(scores)), key=lambda i: -scores[i])[:k]]

def rrf(*ranked: list[str], k: int = 60) -> list[str]:
    """RRF 融合:只用名次不用分数,天然免疫两路分数量纲不同。"""
    fused: dict[str, float] = {}
    for lst in ranked:
        for rank, doc_id in enumerate(lst, start=1):
            fused[doc_id] = fused.get(doc_id, 0.0) + 1.0 / (k + rank)
    return [d for d, _ in sorted(fused.items(), key=lambda x: -x[1])]

为什么用 RRF 而不是加权求和:BM25 的分数无上界(取决于词频和文档长度),余弦相似度在 [-1, 1],两者直接加权必须先归一化,而归一化方式本身又是一个要调的超参,还随数据分布漂移。RRF 只看名次,1/(k+rank) 这一项就把量纲问题绕过去了。

  • k=60 是原论文的经验值,对结果的影响很小,不要在这上面花时间调。
  • BM25 侧需要维护一个独立的倒排索引,内存里的 BM25Okapi 重启就没了,生产要么持久化要么用支持混合检索的库(Qdrant 的 sparse vector、Elasticsearch)直接做。
  • LangChain 的 EnsembleRetriever(retrievers=[bm25_r, vec_r], weights=[0.4, 0.6]) 用的是分数加权融合,不是 RRF。想用 RRF 就用上面那个函数。

4. Rerank:用交叉编码器做二次排序 ​

双编码器(embedding)交叉编码器(rerank)
输入query 和 doc 各自编码两者拼在一起过一遍模型
文档侧可预计算是否,每次都要重算
角色全库粗排,取 top-50对 top-50 精排,取 top-5
python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")     # 中文效果好的开源选择

def rerank(query: str, docs: list[str], top_n: int = 5) -> list[int]:
    """返回精排后保留下来的下标。注意输入是候选集,不是全库。"""
    scores = reranker.predict([[query, d] for d in docs])
    return sorted(range(len(docs)), key=lambda i: -scores[i])[:top_n]

不想自己部署模型的话,托管 rerank API(Cohere Rerank、Jina Rerank、Voyage)按次计费,接入成本和调一次 HTTP 一样。中文场景选模型时务必确认它支持中文,Cohere 的多语言模型和只支持英日的版本效果差距极大。

两条必须记住的判断:

  • rerank 不能替代召回。它只重排已经召回的候选,召回不到的 rerank 救不回来。所以顺序永远是「先扩召回(recall@50)→ 再精排」,而不是「直接 rerank top-5」。
  • 候选集大小决定性价比。候选 3~10 倍于最终 k 是常见配置;候选 200 条做 rerank,成本和延迟都会失控,而收益相比 50 条已经很小。

5. 父子块与自查询检索器 ​

第 12 篇留了个两难:chunk 小了丢上下文,大了语义被稀释。父子块直接绕开这个矛盾——用小块的向量做匹配,命中后返回它所属的大块:

python
from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore
from langchain_text_splitters import RecursiveCharacterTextSplitter

retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=InMemoryStore(),                    # 生产换成 Redis 或数据库存父子关系
    child_splitter=RecursiveCharacterTextSplitter(chunk_size=200),   # 小块:定位精准
    parent_splitter=RecursiveCharacterTextSplitter(chunk_size=1200), # 大块:上下文完整
)
retriever.add_documents(docs)                    # 索引小块,存储大块,自动建立映射

代价是多一个 docstore 组件,以及索引体积变大(父子两份都要存)。判断标准:如果你的文档里有大量跨句指代(「这个功能」「上述配置」),父子块的收益会非常明显。

自查询检索器让模型自己从问题里抽出过滤条件:

python
from langchain.chains.query_constructor.base import AttributeInfo
from langchain.retrievers.self_query.base import SelfQueryRetriever

fields = [
    AttributeInfo(name="lang", description="文档语言,取值 zh 或 en", type="string"),
    AttributeInfo(name="updated_at", description="最后更新日期,格式 YYYY-MM-DD", type="string"),
]
sq = SelfQueryRetriever.from_llm(LLM, vectorstore, "产品手册片段", fields, enable_limit=True)
sq.invoke("2024 年之后更新的中文退款政策")
# 模型解析为: query="退款政策" + filter=And(eq("lang","zh"), gt("updated_at","2024-01-01"))

这个能力很诱人,但生产上要谨慎:模型会幻觉出不存在的字段名,或者把取值写成文档里没有的形式,而失败是静默的——过滤条件为空,退化成全库搜索。更可控的做法是用第 03 篇的结构化输出自己解析成 filter 对象,校验字段名后再传给向量库。

6. 用命中率和 MRR 量化你的优化 ​

python
def evaluate(cases: list[dict], retrieve, k: int = 10) -> dict:
    """cases: [{"q": "问题", "gold_ids": {"c12"}}, ...] —— 这是全部优化的地基。"""
    hit, mrr = 0, 0.0
    for c in cases:
        got = [d.metadata["chunk_id"] for d in retrieve(c["q"], k)]
        ranks = [i for i, cid in enumerate(got, 1) if cid in c["gold_ids"]]
        if ranks:
            hit += 1
            mrr += 1.0 / ranks[0]        # MRR 只看第一个命中的名次
    return {"recall@k": hit / len(cases), "MRR": mrr / len(cases)}

两个指标分工明确:recall@k 衡量召回能力(正确的块在不在前 k 个里),MRR 衡量排得够不够靠前(第一个命中的名次倒数)。rerank 几乎不影响 recall@k,只会拉高 MRR;混合检索和查询改写主要提升 recall@k。看哪个指标没动,就知道该换哪一步。

方法上的四条:

  1. 先攒 30~50 条标注(问题 + 正确 chunk_id)。没有这个,所有优化都是盲调。从线上日志里挑真实问题,别自己编。
  2. 每次只改一个变量,跑评估,记录数字。同时改三个,结果好不知道是谁的功劳,结果差也定位不到。
  3. 推荐顺序:混合检索 → 父子块 → rerank → 查询改写。前两步提升召回天花板,后两步优化排序和表达。倒着做等于在漏水的桶上刷漆。
  4. 召回率提升不等于答案质量提升。两个都要测:指标用 recall@k/MRR,答案质量用人工或 LLM-as-judge(注意 judge 本身有偏差,不能当唯一依据)。

常见陷阱 ​

  • 没有标注集就开调:「加了 rerank 感觉好多了」无法复现、无法归因、也无法发现回退。先花半天攒 30 条标注。
  • 直接 rerank top-5:rerank 只重排已有候选,召回不到的一律救不回来。必须先把候选集扩到 30~50。
  • BM25 不做中文分词:整句话被当成一个词,BM25 完全失效,表现为「加了混合检索毫无变化」。
  • 多查询改写不做去重:三个查询召回同一批块,多了两次检索成本,召回集合一个没变。
  • 一次性上全部手段:不知道哪个有效、哪个在拖后腿,成本还翻了几倍。按第 6 节的顺序逐个加,每个都用指标验证。
  • 只看召回率不看答案质量:召回率涨了但答案变差(候选变多引入噪声),这种情况很常见,两条曲线都要看。

练习建议 ​

  1. 建标注集:从你的真实业务日志里挑 40 条问题,人工标出每道题对应的正确 chunk_id。这是本篇所有后续工作的前提。
  2. 手段逐个加:在标注集上依次跑「基础 RAG」「+混合检索」「+父子块」「+rerank」「+查询改写」,每一步都记录 recall@10、MRR 和单次查询耗时,做成一张对比表。
  3. 找反例:从测试里挑出 5 个「加了所有优化仍然召回不到」的查询,逐个归类到第 1 节的根因表,判断它们是数据问题(内容根本不在库里)还是方法问题。

前端对照 ​

前端概念Agent 对应物说明
电商搜索的二次排序rerank先粗排取候选,再精排决定最终顺序
联想词 / 同义词扩展查询改写 / HyDE用户输入的词和库里的词对不上
倒排索引 + 语义召回混合BM25 + 向量混合检索关键词保精确,语义保泛化
搜索结果高亮片段父子块用小片段定位,展示时带上更大上下文
多条件筛选器(价格+品牌)自查询检索器的元数据过滤从用户表述生成结构化过滤条件
A/B 实验指标(CTR)recall@k / MRR优化必须由指标驱动,不能靠感觉

一个共同的思维模型值得记住:前端的搜索优化和这里的检索优化,本质上都是「先保证候选集里有正确答案,再把它排到前面」。差别在于,前端的排序规则是你写的、可解释的(按销量、按时间、按价格),而这里的排序来自模型,你只能调输入和候选集,无法直接改规则。所以评估集在这里的地位比在前端高得多——它是唯一能告诉你「改动是变好还是变坏」的东西。
