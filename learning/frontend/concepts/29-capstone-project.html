29 · 综合实战项目 ​

前置：28 可访问性与国际化 · 预计：2.5~3 小时

概念简介 ​

这是本技能的收尾篇，也是 L5（专家/架构师）考核的项目载体：设计并实现一个「中型 B 端管理系统」——运营中台，用「架构评审 + 性能治理 + 质量体系」三条主线把 01-28 全部概念串成一个可交付的真实系统。B 端管理系统是最典型的架构考场：多角色权限、表格/表单密集、部分模块需要实时性、安全与合规要求明确，能完整暴露一个架构师的全部决策能力。

项目的评判标准不是「功能写完」，而是每个决策都有论证：为什么选这个框架、为什么状态这样分层、为什么性能预算设这个值、验收标准为什么可度量。真实项目没有标准答案，只有「论证充分、自洽、可验证」的答案——这正是 L5 与 L3 的分水岭。完成本项目后，用 /assess frontend L5 触发考核，本项目的架构文档、监控大盘、代码库就是考核材料。

核心内容 ​

1. 项目范围与分层架构决策 ​

运营中台：登录/权限（RBAC）、用户管理、订单列表（实时）、数据报表、公告发布。

决策项选型理由（论证要点）权衡（放弃了什么）
框架React 18 + Vite（或 Vue 3 + Vite 双轨可选）生态成熟、团队已熟、Vite 冷启动快放弃 Next.js 的服务端能力（本系统登录后场景，无 SEO 需求）
状态管理客户端 Zustand + 服务端 TanStack Query分层：服务端状态不进 Store（21 篇决策树）放弃 Redux Toolkit（样板多、无增量收益）
数据获取Query + WebSocket（订单实时）拉取缓存 + 推送增量各司其职放弃轮询（延迟与流量不可接受）
构建/工程pnpm workspace + Turborepo组件库/工具包跨应用共享、affected 构建放弃多仓库（原子提交与复用优先）
样式设计 Token 三层体系（24 篇）品牌换色零业务改动放弃 CSS 框架（定制成本高于收益）
测试Vitest + Testing Library + Playwright三层测试齐备、覆盖率门槛 80%放弃快照测试（脆弱且噪音大）
CIGitLab CI（内网）预览环境 + 流水线门禁 + 变更集发布放弃外部 SaaS（内网部署约束）
监控自建 RUM（web-vitals）+ Sentry性能分位 + 错误全量放弃商业 RUM（成本与数据出网顾虑）
安全CSP + SameSite + 依赖审计纵深防御（27 篇）放弃极端隔离方案（成本收益比差）

2. 架构权衡论证：为什么这样选 ​

为什么不选 SSR/微前端：系统是登录后场景——无 SEO 需求（否掉 SSR/SSG 的主收益）、单团队维护（不满足微前端的组织前提，22 篇的适用性判据）。这两个「否」不是能力不足，而是需求不匹配——架构评审最看重的是「为什么不用」，因为它暴露是否真的理解了选型边界。

为什么状态必须分层：订单列表是服务端状态（Query 管缓存与失效），列表勾选/弹窗是客户端状态（Zustand），筛选条件进 URL（可分享可回退）。三份状态三个家，数据流图上每一跳都单一来源——这是 21 篇决策树的落地。评审时的关键答辩点是乐观更新与 WebSocket 推送在缓存层的合并顺序。

为什么 Monorepo + Token 体系：组件库与工具包在多个内部系统间复用是刚需（24/23 篇）。Token 层是「换肤零改动」的保险，Turborepo 是「大仓不慢」的保险——两者缺一，Monorepo 的成本就压过收益。

3. 分阶段实施计划 ​

阶段 1 · 工程底座（架构搭建） ​
  • 初始化 pnpm workspace（apps/web + packages/ui + packages/utils + packages/config）
  • 设计 Token 三层体系 + 基础组件（Button/Input/Modal/Switch），接 Storybook
  • CI 骨架：lint → 单测 → 构建 → 预览环境；提交即部署
  • 验收标准：pnpm install 单机 < 1min；新组件开发时 turbo run build --filter=...[origin/main] 只构建受影响包；CI 全绿 < 5min；Storybook 可交互
阶段 2 · 核心功能（架构落地） ​
  • 登录/RBAC：路由守卫 + 权限指令化（按钮级权限）
  • 用户管理 CRUD：Query 数据流 + 乐观更新 + 失效模型（21 篇完整闭环）
  • 列表页工程：表格 + 筛选（URL 状态）+ 分页（placeholderData 不闪加载）
  • 验收标准：覆盖率 ≥ 80%；无任何接口数据进 Store；切筛选不闪加载态；乐观更新失败可回滚（有测试用例证明）
阶段 3 · 实时模块（数据流进阶） ​
  • 订单列表：WebSocket 增量推送 + 消息序号去重 + Query 缓存合并
  • 断线重连 + 心跳 + 恢复拉取（同步策略的完整生产形态）
  • 验收标准：断网 30s 重连后数据无重复无丢失（脚本验证）；推送延迟 p95 < 1s；消息重放场景有专门测试
阶段 4 · 性能治理（度量先行） ​
  • 自建 RUM：LCP/INP/CLS/TTFB 采集 + p75/p95 聚合 + 性能大盘
  • 性能优化闭环：虚拟列表（万行表格）、路由懒加载、包体积分析
  • Lighthouse CI 性能预算接入流水线
  • 验收标准：生产环境 LCP p75 < 2.5s、INP p75 < 200ms、CLS < 0.1；预算违规拦截发布（有记录证明拦截过劣化提交）
阶段 5 · 监控与告警（治理闭环） ​
  • Sentry 接入：release 版本化 + source map 私有上传 + 错误去重
  • 告警规则：窗口聚合 + 双条件 + 分级（P1/P2/P3），每条带处置预案
  • 发布回归流程：灰度发布 + 新旧版本指标对比（26 篇「从报警到修复」完整演练一次）
  • 验收标准：模拟注入一个错误，5min 内收到 P2 告警且能定位到具体代码行；source map 不出现在公网；告警规则文档齐备
阶段 6 · 安全与无障碍合规 ​
  • 安全：CSP 强制执行 + Cookie 全属性 + 富文本白名单清洗 + 依赖审计进 CI
  • 无障碍：WCAG 2.2 AA——焦点管理、对比度、键盘全流程、axe CI 零违规
  • i18n：ICU 消息 + 中英双语 + RTL 验证（组件库选型时已确认支持）
  • 验收标准：axe 自动化零违规 + 手动清单通过（键盘全流程 + NVDA 抽查）；CSP 无生产违规报告；OWASP ZAP 扫描无高危
阶段 7 · 发布与沉淀（交付闭环） ​
  • 灰度发布（10% → 50% → 100%）+ 每步指标对比
  • 文档沉淀：架构决策记录（ADR）、数据流图、监控大盘截图、性能基线报告
  • 验收标准：发布全程指标无劣化；ADR 覆盖每个选型决策；性能基线报告含 3 个以上优化前后的对比数据

5. 与 L5 考核的关系 ​

本项目即 L5 考核的载体：/assess frontend L5 会基于本技能全部概念与项目产出出题（架构决策答辩、评审问题定位、性能/安全治理方案）。建议交付时准备三份材料：架构决策文档（每个选型的论证与权衡，2 节的内容展开）、监控与治理报告（阶段 4-5 的度量与排障记录）、代码库（分层清晰、注释完整、测试达标）。做完即用 /assess frontend L5 验证。

6. 核心代码骨架：权限守卫与 RUM 埋点（评审时的"证据"） ​

评审看的不只是文档，还有代码是否真的按架构落地。两个关键骨架：

jsx
// 权限守卫（阶段 2）：按钮级权限统一收敛到守卫层，业务组件零权限代码
import { useAuthStore } from '@/stores/auth'

// 约定：路由 meta 声明所需权限，守卫统一裁决
export function RequirePermission({ permission, fallback = null, children }) {
  const hasPermission = useAuthStore((s) => s.permissions.includes(permission))
  if (!hasPermission) return fallback // 无权限渲染降级，绝不渲染组件本身
  return children
}

// RUM 埋点骨架（阶段 4）：接 26 篇的采集器，按用户维度采样
import { onLCP, onINP, onCLS, onTTFB } from 'web-vitals'

export function initRum(sampleRate = 0.1) {
  const uid = currentUser()?.id ?? 'anonymous'
  if (hash(uid) % 100 >= sampleRate * 100) return // 采样先行，未采样用户零开销
  const report = (metric) =>
    navigator.sendBeacon('/rum', JSON.stringify({ uid, ...metric }))
  onLCP(report); onINP(report); onCLS(report); onTTFB(report) // 挂原生指标
}

10. 评审答辩：常见问题与答案要点 ​

  • 「为什么不用 Next.js？」：登录后系统无 SEO 收益；SSR 的服务器成本与全栈约束对纯客户端系统是负债（25 篇选型表）。
  • 「为什么状态不全部放 Store？」：服务端状态有缓存、失效、重试语义，Store 只有「读写」——用 Query 层是给数据装上 21 篇的失效模型。
  • 「性能预算值怎么来的？」：先采集基线（阶段 4 先度量），再按「业务可接受的最差体验」定 p75 预算，不是拍脑袋。
  • 「如果团队要同时维护 3 个系统怎么办？」：组件库与工具包已在 Monorepo 共享（23 篇）；若 3 个系统独立交付节奏冲突，再评估微前端（22 篇判据）——先论证后行动。

常见陷阱 ​

  • 只写功能不写文档：架构决策没有记录，评审时无法论证「为什么」，L5 考核直接失分。
  • 性能优化在功能稳定前启动：在未上线的系统上优化，等于给不存在的用户调参数——先度量后优化（阶段 4 才开始）。
  • 验收标准不可量化：「性能好」「界面规范」无法验收；每个标准都要有数字与证据。
  • 跳过 CI 与监控：演示环境能跑 ≠ 生产可用；监控与告警是「发布后的事故保险」。
  • 过度设计：为单团队系统引入微前端、为登录后系统上 SSR——选型论证应明确记录「为什么不用」。
  • 安全合规最后一天才做：CSP 与 WCAG 是改造级成本，必须在组件选型期就决定（阶段 2 前完成选型评审）。

练习建议 ​

  1. 基础：完成阶段 1-2——工程底座 + 登录与用户管理核心功能，达到对应验收标准。
  2. 进阶：完成阶段 3-5——实时模块 + 性能治理 + 监控告警，跑通一次「从告警到修复」演练。
  3. 综合：完成阶段 6-7——安全与无障碍合规、灰度发布，输出全套架构文档，用 /assess frontend L5 完成考核。

对照其他技能 ​

  • Android：对应的综合实战是「MVVM + 协程 + Room + 性能优化」完整 App；iOS 同（SwiftUI + Combine）；鸿蒙同（ArkUI 全栈应用）。
  • Python/Java：对应的综合实战是「分层架构 + 测试 + CI + 安全加固」的服务端项目——本项目的架构决策方法（选型论证、验收标准、分阶段实施）完全可迁移。
