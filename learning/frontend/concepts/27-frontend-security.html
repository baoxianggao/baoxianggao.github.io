27 · 前端安全 ​

前置：26 性能监控与错误治理 · 预计：1.5~2 小时

概念简介 ​

前端是攻击链的最外层防线，也是防御成本最低的关口。资深工程师的安全观不是「背几个漏洞名词」，而是威胁建模：每个输入入口（用户输入、URL 参数、接口数据、第三方脚本、依赖包）都可能成为攻击面，每个输出出口（DOM、cookie、跳转、iframe）都可能成为载荷落点。本篇按「攻击面 → 防御机制 → 治理流程」组织，聚焦 XSS、CSRF、点击劫持、供应链四类高发风险。

关键认知：前端安全无法独立成立。前端能做的是「限制损失面」（输出编码、CSP、最小权限），真正的安全边界（鉴权、数据校验、密钥）永远在服务端。所有前端校验都只是体验优化，不是安全控制——这条认知能避免绝大多数「前端加密=安全」的误区。

核心内容 ​

1. XSS：三类攻击面与分层防御 ​

存储型（数据进库再渲染）、反射型（URL 参数直接渲染）、DOM 型（innerHTML 拼接）。防御分层：输出编码兜底 + 上下文正确 + CSP 纵深。

jsx
// React 默认转义是安全网：{} 插值永远不会执行 HTML
// 但 React 的原始 HTML 注入属性（dangerouslySetInnerHTML）与 Vue 的 v-html 会绕过它——这是 XSS 第一大入口
function CommentList({ comments }) {
  return comments.map((c) => (
    // ✅ 默认转义，注释内容再恶意也只是文本
    <p key={c.id}>{c.content}</p>
  ))
}

// 业务上确实要渲染富文本时：白名单 + 清洗，禁止"信任接口数据"
import DOMPurify from 'dompurify'
const SAFE_TAGS = ['p', 'b', 'i', 'a', 'ul', 'ol', 'li', 'strong', 'br']

function RichText({ html }) {
  // 先清洗再渲染：只保留白名单标签，a 标签必须强制 https 且 rel=noopener
  const clean = DOMPurify.sanitize(html, {
    ALLOWED_TAGS: SAFE_TAGS,
    ALLOWED_ATTR: ['href', 'title'],
    ALLOWED_URI_REGEXP: /^(?:https?:)?\/\//i, // 拦截 javascript: 伪协议
  })
  return <div dangerouslySetInnerHTML={{ __html: clean }} />
}

CSP（内容安全策略）是 XSS 的第二道闸门：即使渲染漏洞被突破，CSP 也能阻止载荷执行：

nginx
# 生产环境最小权限 CSP（响应头，而非 meta 标签——meta 不支持 report-only）
Content-Security-Policy: default-src 'none'; script-src 'self' https://cdn.example.com; style-src 'self'; img-src 'self' data:; connect-src 'self' https://api.example.com; frame-ancestors 'none'; base-uri 'self'

script-src 默认禁用内联脚本与 eval 类执行——代价是需要改造旧代码（内联事件处理器、动态拼接代码的函数）。上线策略：先 Content-Security-Policy-Report-Only 观察违规报告，再切换强制执行。

2. CSRF 与 SameSite ​

CSRF：攻击者诱导已登录用户在不知情下发起跨站请求。现代防御第一道防线在浏览器——Cookie 的 SameSite 属性：

js
// 服务端设置会话 Cookie（关键属性）
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax
// SameSite=Lax：跨站 GET 顶级导航带 cookie，跨站 POST 不带——挡住绝大多数 CSRF
// 严格场景用 Strict；还需放宽的服务（如支付回调）用双重校验：CSRF Token + 自定义头

前端配合：敏感写操作一律 POST + 自定义请求头（X-Requested-With: fetch），浏览器预检机制让跨站请求带不上自定义头——双重校验后 CSRF 基本关闭。注意：SameSite 只保护 Cookie 类凭据，Bearer Token（localStorage）不在此列——Token 泄露面靠「不用 localStorage 存会话 + 过期短」控制。

3. 点击劫持与 X-Frame-Options ​

攻击者把目标页面用透明 iframe 叠在自己页面上，诱导用户点击「中奖」实际点了「删除」。防御在响应头，两层都要：

nginx
# 旧式：X-Frame-Options 只支持 DENY/SAMEORIGIN
X-Frame-Options: SAMEORIGIN
# 新式（优先）：CSP 的 frame-ancestors 支持更细的域名白名单
Content-Security-Policy: frame-ancestors 'self' https://partner.example.com
# 两者都设置：老浏览器认 XFO，新浏览器认 frame-ancestors

反制还差最后一步：页面内 JS 防嵌套（if (window.top !== window.self) top.location = self.location）——头防不住同源 iframe，JS 兜底防非法嵌入。

4. 依赖安全：供应链是最大的盲区 ​

npm 生态的供应链攻击路径：恶意包名仿冒（typosquatting）、依赖投毒（热门包被劫持后发恶意版本）、安装脚本（postinstall 里挖矿/偷环境变量）。防御清单：

bash
# 1) 锁文件必须提交且 CI 强制校验（frozen-lockfile），杜绝"飘移安装"
# 2) 定期审计，阻断高危
pnpm audit --prod
# 3) 关键构建阶段验证包完整性签名（npm audit signatures）
# 4) 私有镜像 + 白名单源：只允许内网镜像，禁直连公网 registry
# 5) 运行时权限最小化：postinstall 脚本在 CI 里默认拒绝（ignore-scripts 开启，按需放行）

最小权限延伸到所有第三方：广告 SDK、统计脚本、埋点脚本都拥有整个页面的 DOM 权限——给第三方脚本单独域名 + CSP 限制（script-src 只允许它们自己的域名，它们拿不到 connect-src 之外的目标），是成本最低的供应链止损。

5. 原型污染与 SSRF：两个"间接"漏洞 ​

原型污染（Prototype Pollution）：JSON.parse 本身安全，但递归 merge 用户输入时 __proto__ 键会污染 Object.prototype——一次污染全站对象行为异常：

js
// ❌ 危险：递归合并外部输入
function deepMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (typeof source[key] === 'object' && source[key] !== null) {
      target[key] = deepMerge(target[key] ?? {}, source[key]) // __proto__/constructor 会被带入
    } else {
      target[key] = source[key]
    }
  }
  return target
}
// ✅ 防御：拒绝合并原型链相关键，或用 structuredClone 后只合并可枚举白名单字段
function safeMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (key === '__proto__' || key === 'constructor' || key === 'prototype') continue
    /* ...正常合并逻辑... */
  }
}

SSRF 严格说是服务端漏洞，但前端是入口：用户提交的 URL（头像链接、代理请求）被服务端 fetch 时，可能打到内网（http://169.254.169.254/ 云元数据）。前端职责：对 URL 输入做协议/域名校验，并在架构上明确「前端不做服务端代理，所有 URL 请求走受控的 BFF」——前端「碰不到」内网就是最好的防御。

6. 安全审计流程 ​

  1. 威胁建模（设计期）：列出输入面/输出面/资产/信任边界，写进架构文档。
  2. 自动化扫描：SAST（eslint-plugin-security、代码扫描）进 CI，依赖审计（pnpm audit）每次合并前跑。
  3. 人工测试：安全用例进测试库（XSS 载荷、CSRF 场景、CSP 违规用例），用 OWASP ZAP 对预览环境跑 DAST。
  4. 评审门禁：涉及鉴权、用户输入、外部调用、文件操作的改动，按 code-review 规则里的安全触发清单走专项审查。

常见陷阱 ​

  • React 的原始 HTML 注入属性（dangerouslySetInnerHTML）/ v-html 当常规手段：所有富文本渲染都不做白名单清洗。
  • CSP 配了但形同虚设：script-src 允许 'unsafe-inline' 且放行任意域名，等于没配。
  • Cookie 缺 HttpOnly/Secure/SameSite：被 XSS 后会话直接泄露。
  • 前端校验当安全边界：表单校验、前端加密都拦不住直接打接口的攻击者。
  • 第三方脚本权限过大：统计脚本与主站同域同权，被劫持即全站沦陷。
  • 忽略供应链：锁文件不提交、镜像不校验、安装脚本无条件信任。

练习建议 ​

  1. 基础：为现有应用配置 CSP（先 Report-Only 观察再强制执行），修复全部违规；补全 Cookie 安全属性。
  2. 进阶：搭本地靶场复现存储型 XSS、CSRF、点击劫持三种攻击，写清「攻击路径 → 防御点 → 验证方法」。
  3. 综合：对应用做一次完整威胁建模（输入面/输出面/依赖清单），输出《安全基线清单》并接入 CI 扫描（SAST + 依赖审计 + CSP 测试）。

对照其他技能 ​

  • Android：WebView 的 JS 注入防护与最小化文件访问权限，对应 XSS 与供应链；证书校验对应 CSP 的「不信任默认」。
  • iOS：ATS（App Transport Security）强制 HTTPS，对应 CSP 的传输层要求。
  • 鸿蒙：权限声明最小化 + Web 组件安全属性，对应「最小权限」原则。
  • Python/Java：服务端侧才是真正的安全边界（鉴权/校验/限流），前端所有「防护」在服务端都有更严格版本。
