10 · React 组件设计模式 ​

概念简介 ​

组件设计是 React 项目里长期值钱的能力。库会换代,Hooks 会进化,但"组合优于继承、状态提升、受控/非受控、Compound Components、Headless UI"这些模式是组件化的底层语法——它们决定了组件库的扩展性:别人的组件 3 天接入你的需求,你的组件需要改源码才能满足别人的场景。

本篇梳理六个模式及其演进关系:组合与继承、受控与非受控(以及两者互换)、Render Props 与 HOC 的对比与式微、Compound Components(Context 做隐式连接)、Headless UI(逻辑与视图分离,当下最强的扩展模式)、组件 API 设计原则。核心视角:每个模式解决什么问题、代价是什么、什么时候该用下一个。

核心内容 ​

1. 组合优于继承:props 插槽与 children ​

React 没有继承体系(类继承几乎总是反模式),扩展靠组合:用 children、具名插槽(props 传元素)、render 函数把"可变部分"交给调用方。

jsx
function Card({ title, actions, children }) {
  return (
    <section>
      <header>
        <h2>{title}</h2>
        <div>{actions}</div> {/* 插槽:调用方注入操作区 */}
      </header>
      <div>{children}</div> {/* 主体内容 */}
    </section>
  );
}
// 调用方组合,而非子类化:
<Card title="订单" actions={<button onClick={pay}>去支付</button>}>
  <OrderList />
</Card>
// 与"改 Card 源码加一个 orderList 属性"的对比:插槽让库组件永不感知业务

权衡:插槽的自由度代价是"组合陷阱"(children 深层嵌套时的渲染透传成本,见 06 篇 memo 失效)——但多数场景,可扩展性收益远大于这个成本。

2. 受控/非受控:状态归属的两种选择 ​

  • 非受控:DOM 自己管状态,React 只管初值(defaultValue),用 ref 读取——简单、少渲染,但外部无法干预。
  • 受控:状态在 React 手里(value + onChange),外部完全可控——可校验、可联动,代价是每次输入都渲染。
jsx
import { useRef, useState } from 'react';

// 受控组件:单一真源在父级
function ControlledInput({ value, onChange }) {
  return <input value={value} onChange={(e) => onChange(e.target.value)} />;
}
// 非受控组件:状态在 DOM 里,React 不参与每键更新
function UncontrolledInput({ defaultValue }) {
  const ref = useRef(null);
  return (
    <input ref={ref} defaultValue={defaultValue} onBlur={() => console.log(ref.current.value)} />
  );
}
// 转换模式:同一组件两种模式都支持(如 Ant Design 的 Input)
// 关键代码:有无 value prop 决定受控与否
function FlexibleInput({ value, onChange, defaultValue }) {
  const isControlled = value !== undefined; // 有 value 就是受控,没有就非受控
  return (
    <input
      value={isControlled ? value : undefined}
      defaultValue={isControlled ? undefined : defaultValue}
      onChange={onChange}
    />
  );
}
// 坑:从非受控切到受控(或反之)会报 React 警告;模式切换只在挂载前决策,不要运行时切换

权衡:表单简单用非受控(性能好),需要校验/联动/初始值来自异步数据用受控。生产表单优先受控——可测试性(状态可断言)比性能重要。

3. Render Props 与 HOC:两种复用方式的对比 ​

两者都是"逻辑复用"的旧方案,现在大部分场景被 Hooks 取代,但组件库中仍大量存在,需要读懂。

jsx
// Render Props:把渲染逻辑交给调用方,逻辑通过函数参数传递
function MouseTracker({ children }) {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  return <div onMouseMove={(e) => setPos({ x: e.clientX, y: e.clientY })}>
    {children(pos)} {/* children 即函数:数据 → 渲染 */}
  </div>;
}
// HOC:包一层工厂,注入 props,返回增强组件
function withLogger(Wrapped) {
  return function Logged(props) {
    useEffect(() => { console.log('渲染:', props); });
    return <Wrapped {...props} />;
  };
}
// 对比:Render Props 无名称冲突、依赖显式;HOC 会吞 props、隐式注入、多层嵌套地狱(HOC 套 HOC)
// 现代替代:两者都让位于自定义 Hook——组合、无嵌套、类型友好
function useMouse() {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  return { pos, handlers: { onMouseMove: (e) => setPos({ x: e.clientX, y: e.clientY }) } };
}

决策:新代码用 Hooks 表达逻辑复用;读旧代码时,把 Render Props/HOC 翻译成 Hook 心智来理解。

4. Compound Components:Context 做隐式连接 ​

模式:父组件 + 若干子组件通过 Context 隐式共享状态,调用方自由排布子组件顺序与样式。典型:Select/List/Modal 系列。

jsx
import { createContext, useContext, useState } from 'react';

const SelectContext = createContext(null);

function Select({ children, onSelect }) {
  const [open, setOpen] = useState(false);
  const [value, setValue] = useState(null);
  return (
    // 状态只经 Context 传给内部子组件,调用方无法直接触达
    <SelectContext.Provider value={{ open, setOpen, value, choose: (v) => { setValue(v); setOpen(false); onSelect?.(v); } }}>
      {children}
    </SelectContext.Provider>
  );
}
Select.Trigger = function Trigger({ children }) {
  const { open, setOpen, value } = useContext(SelectContext); // 隐式连接
  return <button onClick={() => setOpen(!open)}>{value ?? children}</button>;
};
Select.Options = function Options({ children }) {
  const { open } = useContext(SelectContext);
  return open ? <div className="options">{children}</div> : null;
};
Select.Option = function Option({ children, value }) {
  const { choose } = useContext(SelectContext);
  return <div onClick={() => choose(value)}>{children}</div>;
};
// 调用方:结构自由,语义清晰
<Select onSelect={(v) => console.log(v)}>
  <Select.Trigger>选择城市</Select.Trigger>
  <Select.Options>
    <Select.Option value="sh">上海</Select.Option>
    <Select.Option value="hz">杭州</Select.Option>
  </Select.Options>
</Select>

权衡:Context 让子组件免于 props 透传,但子组件只能在该父组件内使用(脱离即报错),且状态藏在 Context 里调试不直观——用 useContext 前检查 null 并给出明确报错信息。

5. Headless UI:逻辑与视图彻底分离 ​

当下最强的扩展模式:组件只提供逻辑与状态(Hook 或 render-props),样式完全由调用方掌控。解决了"设计系统要换肤,组件库锁死样式"的矛盾。

jsx
// Headless:useDropdown 只管状态与键盘交互,不管任何 DOM 结构
function useDropdown() {
  const [open, setOpen] = useState(false);
  const [highlightedIndex, setHighlightedIndex] = useState(-1);
  return {
    open,
    toggle: () => setOpen((o) => !o),
    close: () => setOpen(false),
    highlightedIndex,
    setHighlightedIndex,
    getTriggerProps: () => ({
      'aria-haspopup': 'listbox',
      'aria-expanded': open,
      onClick: () => setOpen((o) => !o),
      onKeyDown: (e) => {
        if (e.key === 'Escape') setOpen(false);
        if (e.key === 'ArrowDown') setHighlightedIndex((i) => i + 1); // 键盘导航是 Headless 的核心价值
      },
    }),
    getMenuProps: () => ({ 'aria-hidden': !open }),
  };
}
// 使用方:完全掌控结构、类名、动画 —— 品牌化样式零冲突
function BrandDropdown() {
  const dropdown = useDropdown();
  return (
    <div>
      <button className="brand-button" {...dropdown.getTriggerProps()}>菜单</button>
      {dropdown.open && <ul className="brand-menu" {...dropdown.getMenuProps()}>
        <li>条目一</li><li>条目二</li>
      </ul>}
    </div>
  );
}
// 生产代表:Radix UI / Headless UI / react-aria —— 逻辑标准化(无障碍、键盘),样式自由化

权衡:Headless 的自由度意味着没有开箱样式,接入成本高;适合设计系统团队或样式要求强烈的产品;中小项目用成品组件库(Ant Design)更快——选型是"控制权 vs 效率"的交换。

6. 组件 API 设计原则 ​

组件库的公共 API 是契约,按四个原则设计:单一职责(一个组件一个意图)、最少惊讶(命名与行为符合直觉)、默认安全(无障碍、错误显式)、渐进可控(默认可用,高级能力通过 props/插槽开启)。

jsx
// 原则落地示例:一个按钮的 API 设计决策
interface ButtonProps {
  variant: 'primary' | 'secondary' | 'danger'; // 有限枚举,避免魔法字符串扩散
  size: 'sm' | 'md' | 'lg';
  loading?: boolean;        // 渐进增强:默认无
  onClick?: () => void;
  children: React.ReactNode;
  disabled?: boolean;
  // 反模式:type: string(自由字符串 → 组合爆炸)
  // 反模式:onClick 里隐式节流/埋点(副作用应显式注入,而非内置)
}
// 设计检验三问:新需求能否不加 props 满足?(组合) | 新 props 是否会让老用法行为变化?(破坏性) | 行为是否可预测?(最少惊讶)

生产原则:公共 API 一旦发布就是债务,加 props 永远简单,改语义永远痛苦——用"semver 纪律 + 文档示例 + 行为测试"保护契约。

常见陷阱 ​

  • 类继承扩展组件:class X extends Base,扩展点耦合在生命周期里,改 Base 就破坏所有子类;用插槽/组合/Headless 替换。
  • 受控非受控运行时切换:value 从 undefined 变 defined 触发 React 警告且状态丢失;挂载前定模式,或设计成"始终受控"。
  • HOC 套 HOC:多层包装后 props 来源不明、ref 穿透丢失(需要 forwardRef 修补);新代码用 Hook,读旧代码先还原成 Hook 心智。
  • Compound 子组件脱离父组件:子组件 Context 为 null 时静默崩溃;useContext 必须判空并抛错,提示正确用法。
  • 组件内置业务逻辑:把埋点、权限判断、数据请求写死在通用组件里,复用方无法剥离;副作用用 props/插槽注入,组件保持纯渲染。
  • API 设计贪多:一个组件 40 个 props,组合爆炸且行为互斥;用子组件拆分 + 有限枚举 + 文档,克制是组件 API 的第一美德。

练习建议 ​

  1. 基础:把你们项目里一个 30+ props 的组件,按"单一职责 + 有限枚举"重构,拆出子组件与插槽,并列出新 API 的破坏性变化。
  2. 进阶:实现一个 Compound 组件(如 Tabs:TabList/Tab/TabPanel,Context 共享激活项),再加键盘方向键切换,验证"子组件自由排布 + 状态隐式共享"。
  3. 综合:用 Headless 模式实现一个无障碍下拉(ARIA 完整、键盘导航、Escape 关闭),再套两套不同视觉风格的皮肤,产出一份《组件模式选型清单》:什么场景用插槽/Compound/Headless/Hook。

对照其他技能 ​

  • Android/Kotlin:Compose 的 @Composable slot 与 trailingLambda 对应 children 插槽,remember 上下文对应 Context 连接;Compose 的 Slot API 设计原则与 Headless 理念同源(逻辑与样式分离)。
  • iOS/SwiftUI:ViewBuilder 与 @ViewBuilder 闭包对应 children 插槽,@Environment 对应 Context 注入;SwiftUI 的 modifier 链对应"渐进可控"的 API 设计。
  • 鸿蒙/ArkTS:@Builder 的传参与插槽语义对应 children,@Provide/@Consume 双向对应 Context——ArkUI 的组件通信原语与 React 模式一一对应。
  • Python:无组件概念,但 __enter__/__exit__ 上下文管理器与 dataclass 的字段组合对应"组合优于继承"的 Python 版(ABC 继承同样易碎)。
  • Java:Swing 的 LayoutManager 与嵌套容器对应组合模式,AbstractListModel 接口化设计对应 Headless 的"逻辑接口化";模板方法模式(HOC 的近亲)同样被组合替代。
