03 · 异步编程深入 ​

前置：02 JS 语言机制深入 · 预计：2~2.5 小时

概念简介 ​

await fetch() 谁都会写,但"为什么微任务先于渲染""Promise.all 为什么会慢于预期""并发 100 个请求为什么把接口打挂"——这些问题的答案在事件循环的机制里。资深工程师的异步能力不在语法,而在时序心智模型:哪个队列、什么时机、什么优先级。

本篇深入四层:事件循环的宏任务/微任务/渲染时机、Promise 状态机(自己实现一遍就什么都懂了)、async/await 与 Generator 的关系、以及生产最缺的并发控制(limit 并发、超时、竞速)。最后对照 Node 的事件循环差异——浏览器里能跑通的生产代码,Node 里时序会不同。

核心内容 ​

1. 事件循环:宏任务、微任务与渲染时机 ​

浏览器事件循环每轮:tasks(宏任务,一次取一个)→ microtasks(微任务,清空整个队列)→ 渲染(在需要时)。微任务包括 Promise.then、queueMicrotask、MutationObserver;宏任务包括 setTimeout、事件回调、requestAnimationFrame(渲染前)。

js
console.log('1');
setTimeout(() => console.log('2'), 0); // 宏任务,下一轮
Promise.resolve().then(() => console.log('3')); // 微任务,本轮立即
queueMicrotask(() => console.log('4')); // 微任务
console.log('5');
// 输出:1 5 3 4 2 —— 微任务无条件抢在宏任务前

关键机制:微任务在每轮宏任务结束后清空,且清空过程中新加的微任务也会被继续执行。这意味着微任务可以无限追加、饿死渲染——一个死循环的 Promise.resolve().then(loop) 比 setTimeout 死循环更难被杀掉。

渲染时机:渲染在宏任务与微任务之后、下一宏任务之前(大致每 16.7ms 一帧)。这也是"DOM 修改后立即读 offsetHeight 读到旧值"的机制来源——改 DOM 不马上生效,布局在渲染阶段才跑。

2. Promise 状态机与实现 ​

Promise 三态:pending → fulfilled | rejected,只能转移一次。实现的核心:then 回调要异步执行、状态转移时唤醒等待者队列、值要透传。

js
// 最小 Promise 实现,理解状态机与回调队列
class MiniPromise {
  constructor(executor) {
    this.state = 'pending'; // pending | fulfilled | rejected
    this.value = undefined;
    this.queue = []; // { onFulfilled, onRejected }
    // 状态只允许转移一次
    const settle = (state, value) => {
      if (this.state !== 'pending') return; // 幂等:已经定值不可再变
      this.state = state;
      this.value = value;
      this.queue.forEach(({ onFulfilled, onRejected }) => {
        queueMicrotask(() => { // 回调必须异步执行(微任务)
          const handler = state === 'fulfilled' ? onFulfilled : onRejected;
          handler?.(this.value);
        });
      });
    };
    executor(
      (v) => settle('fulfilled', v),
      (r) => settle('rejected', r),
    );
  }
  then(onFulfilled, onRejected) {
    this.queue.push({ onFulfilled, onRejected }); // 简化版:不支持链式透传
    return this;
  }
}
// 生产要点:Promise 天然防"回调多次执行",这就是为什么"resolve 之后 return"是防御性习惯

生产启示:Promise.resolve().then() 每次产生 1 个微任务;await 展开成 then 链,嵌套太深(then 套 then)就是微任务爆炸,性能差且难读——永远用 async/await 平铺。

3. async/await 与 Generator ​

async 函数 = Generator + 自动驱动的状态机。await 等价于 yield + 由运行时自动调用 .then() 恢复执行。Generator 可以被暂停/恢复,async 只是把它封装成"自动推进到结束"。

js
// 手写 async/await 的最小等价:Generator + 驱动器
function* genFlow() {
  const user = yield fetch('/api/user');    // 挂起点
  const orders = yield fetch(`/api/orders?uid=${user.id}`);
  return orders;
}
function run(generator, initialValue) {
  const iter = generator(); // 惰性:调用不执行,next() 才推进
  function step(value) {
    const { done, value: yielded } = iter.next(value); // 把值交还给挂起点
    if (done) return yielded;
    return Promise.resolve(yielded).then(step); // await 的本质:then 恢复
  }
  return step(initialValue);
}
run(genFlow).then((orders) => console.log(orders));

生产启示:async/await 的错误处理必须 try/catch 或顶层 .catch——await 抛错时,整个函数栈变成 rejected Promise,静默丢弃就是"接口挂了页面没反应"的经典来源。

4. 并发控制:all / race / allSettled 与限流 ​

js
// 并发上限控制:生产必备。100 个请求全发出去 = 打挂接口 + 浏览器连接池排队
async function limitConcurrency(tasks, maxConcurrent) {
  const results = new Array(tasks.length); // 按序收结果
  let index = 0;
  const workers = Array.from({ length: Math.min(maxConcurrent, tasks.length) },
    async () => {
      while (index < tasks.length) {
        const current = index++;            // 原子取号,天然无锁
        results[current] = await tasks[current]();
      }
    },
  );
  await Promise.all(workers);
  return results;
}

// 用法与语义对比
const tasks = Array.from({ length: 20 }, (_, i) => () => fetch(`/api/page/${i}`).then((r) => r.json()));
const pages = await limitConcurrency(tasks, 4);   // 最多 4 路并发,按序返回
await Promise.allSettled(tasks);                  // 全部完成,带成功/失败明细,不因单个失败中断
Promise.race([fetch('/api/slow'), timeout(3000)]); // 竞速:超时兜底(注意 race 赢了也要处理另一路的错误,否则 unhandledrejection)

权衡:Promise.all 失败即弃(其余请求结果被丢弃但请求仍发出),适合"全有或全无";allSettled 适合批量导入、埋点上报这类"逐个结算"场景;限流还要考虑:失败重试的退避、按序返回 vs 完成即返回的内存差异。

5. 对比 Node 事件循环 ​

Node 基于 libuv,每轮顺序:timers(定时器) → pending callbacks → idle/prepare → poll(I/O 轮询,阻塞等待) → check(setImmediate) → close callbacks,微任务在每个阶段之间清空,process.nextTick 在微任务之前。

js
// Node 与浏览器时序差异的经典证据
setTimeout(() => console.log('timer'), 0);
setImmediate(() => console.log('immediate'));
// 输出顺序不稳定:取决于 poll 阶段进入时的耗时,与浏览器"setTimeout 必在 nextTick 后"语义不同
process.nextTick(() => console.log('nextTick')); // 永远最先(微任务队列之前)

生产启示:同一段"宏任务后取数据"逻辑在浏览器与 Node 下顺序可能不同;process.nextTick 深递归会饿死 I/O(它在每个阶段前都要清空)——浏览器里没有对应物,写同构代码时避免依赖它。

常见陷阱 ​

  • 微任务饿死渲染:在 then 里无限追加微任务(如轮询写成微任务递归),渲染永远排不上,页面白屏但 CPU 100%;用 setTimeout/MessageChannel 让出主线程。
  • Promise.all 竞态条件:失败即弃但请求仍在跑,后续结果落入 unhandledrejection;批量场景用 allSettled 并逐个判断。
  • race 输家的错误:Promise.race 只处理赢家,输家 reject 会触发 unhandledrejection 报警;给每个成员先 .catch(() => {}) 吞掉再 race。
  • async 里没 try/catch:await 失败直接抛给调用方,顶层未捕获时静默;封装时用统一的错误边界处理函数。
  • 并发无上限:循环里直接 Promise.all(requests.map(fetch)) 一梭子全发;必须限流 + 超时 + 重试退避。
  • await 串行化:await a(); await b(); 两个无依赖请求串行,耗时相加;用 const [ra, rb] = await Promise.all([a(), b()])。

练习建议 ​

  1. 基础:写一段代码验证"微任务清空后才渲染":依次执行宏任务、微任务、修改 DOM,用 requestAnimationFrame 回调打印顺序,解释结果。
  2. 进阶:不借助标准库,用 MiniPromise 实现 Promise.all(支持空数组、失败即弃、按序返回),跑通成功/失败/混合用例。
  3. 综合:实现一个带超时、失败重试(指数退避)和并发上限(5)的批量请求模块,用于列表分页预取;用它替换项目里的无限制 Promise.all,对比接口层 QPS。

对照其他技能 ​

  • Android/Kotlin:协程的 Dispatchers.Main 即事件循环主线程,launch/async 对应宏任务/并发控制,withContext 对应切换线程池——limitConcurrency 对应 Semaphore 或 channelFlow 的 buffer。
  • iOS/Swift:DispatchQueue.main.async 与 RunLoop 即事件循环,async let/TaskGroup 对应 Promise.all;Swift 的 Task.sleep 对应 setTimeout 的挂起语义。
  • 鸿蒙/ArkTS:TaskPool 与 @Concurrent 对应并发控制,Promise.all 语义与 JS 完全一致(TS 同源),但 UI 线程挂起要用 async 函数配合 @State 更新。
  • Python:asyncio.gather 对应 Promise.all、asyncio.wait_for 对应超时;事件循环是单线程多路复用,与 JS 同构,但 Python 的协程没有"微任务清空后才渲染"的 UI 帧概念(它是通用 I/O 循环)。
  • Java:CompletableFuture.allOf 对应 Promise.all,CompletableFuture 的 thenApply 链对应微任务链,虚拟线程(JDK21)则是把"并发上限"问题交给运行时,而非手写限流。
